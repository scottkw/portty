HARD-02 (CONTEXT decision HARD-02): a paste over 32 KiB goes out as one input frame. Every input reader keeps coder/websocket's 32768-byte default read limit as its DoS guard, so the oversized frame closes the socket and the paste is lost. The CLI has the same off-by-one: a 32 KiB stdin read plus the type byte makes a 32769-byte frame. Split input on the sending side, keep every server limit, pin the limit with a test, and correct the proxy comment that calls this harmless.

## Flagged decisions and assumptions

- **Why wave 2:** 07-02 edits frontend/src/lib/relayClient.ts and its test (RelayClient resume option). This plan edits `sendInput` in the same files, so it runs after 07-02. Read 07-02-SUMMARY.md for what changed there, and keep it intact.
- **Where the limit is:** no input reader calls SetReadLimit, so each one uses coder/websocket's 32768-byte default per message: the relay server read pump, the daemon proxy's client side (remote_ws_proxy.go) and the host share server. Over the limit, coder/websocket fails the read and closes the connection with StatusMessageTooBig. The frame is not merely dropped: the whole socket goes, and the paste with it. Every server limit stays unchanged (CONTEXT: DoS guard).
- **One cap, two languages:**
  - Go: `relay.MaxInputPayload = 32767` in protocol.go, next to ReplayChunk, with a doc comment: 32768 (coder/websocket's default read limit, kept by every input reader as the DoS guard) minus the type byte, and senders split longer input.
  - Frontend: `MAX_INPUT_PAYLOAD = 32767` in relayClient.ts beside the frame constants, with a comment naming relay.MaxInputPayload.
- **Frontend split:**
  - `encodeInputFrames(text): Uint8Array[]` encodes once with TextEncoder and slices the bytes into payloads of at most MAX_INPUT_PAYLOAD, each prefixed with MSG_INPUT. Empty text gives an empty array.
  - `sendInput` keeps its reconnect-mode `state !== 'open'` gate and its readyState check, then sends each frame in order.
  - It replaces the single-frame encoder, which is only used by sendInput and its three tests; convert those tests.
  - One place covers all three surfaces: TerminalPanel's `term.onData` → `client.sendInput` is the only input path, and local tabs, peer tabs (WebShareSessionView → TerminalPanel, remote) and the browser view (WebShareSessionView → TerminalPanel, wsURL) all use it (checked at planning time: no other sender of MSG_INPUT in frontend/src).
- **UTF-8 boundaries (CONTEXT asked to confirm):** byte-level splitting is correct.
  - A WebSocket delivers one connection's messages in order.
  - The relay, proxy and share server each write every frame's payload to the PTY (or upstream) before reading the next.
  - So the PTY receives the same byte stream, and a multibyte character split across two frames is reassembled by the reader of the PTY.
  - The test asserts the byte-exact concatenation with a character straddling the boundary.
- **CLI:** `internal/attach/loop.go` readStdin (remote attach, the reconnecting loop) and `internal/attach/attach.go` StdinPump (local attach via AttachSession, cmd_attach.go ~360) each allocate a 32 KiB read buffer. Size both with relay.MaxInputPayload. Nothing else changes; the detach-key scan still works per read.
- **Proxy comment:** `internal/daemon/remote_ws_proxy.go` ~70-71 says the viewer side's limit is harmless because the host limits input anyway. Replace it with what is true:
  - the client side keeps coder/websocket's default 32768-byte read limit as a DoS guard;
  - a larger frame closes the viewer socket;
  - every sender (relayClient.ts encodeInputFrames, internal/attach stdin reads) splits input into frames of at most relay.MaxInputPayload bytes plus the type byte.
  - Comment only, no code change.
- **Guard tests on all three input readers (plan check W-2).** SC2's "a single input frame over 32 KiB is still dropped" must hold wherever viewer input is read, and each reader has a cheap existing harness:
  - relay server: `setupTestServer`/`dialWS`, in Task 1;
  - remote WS proxy client socket: `newFixtureRemotePeerWithWS` echo peer, `newDaemonAPIWithUpstreamCert`, `depositCap`, `dialProxy`, as `TestRemoteSessionWS_FrameCopy` uses them;
  - host share server: `dialShared` in internal/webserver/revoke_test.go, which returns the connection and the PTY input pipe.
  - The tests use none of the production splitting code; they send raw frames of 32768 and 32769 bytes.
  - Through the proxy, the over-limit frame must close the viewer's socket. coder/websocket closes it with StatusMessageTooBig (1009) when the read limit trips; record the status seen. The fixture peer must never echo a 32769-byte message back.
