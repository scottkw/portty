## Flagged decisions and assumptions

- **Why the offset alone is not enough (found at planning time; the reason for the snapshot).**
  - App.tsx renders only the ACTIVE `__websession__` tab (the `activeId.startsWith('__websession__')` branch, about line 1098). Switching tabs unmounts WebShareSessionView, then TerminalPanel, whose mount-effect cleanup calls `term.dispose()`.
  - The returning tab therefore starts with an empty xterm. A delta replay into an empty terminal would show only the output since the offset, so everything before it would be missing (SC3 forbids that).
  - So, per the decision's own rule (keep the offset across unmount, no hidden sockets), the panel also keeps the terminal's content. It serializes the xterm buffer on unmount and writes it back on remount, then dials with the snapshot's offset. A snapshot and its offset always describe the same stream point, so delta-after-restore is exact.
- **Rejected alternative:** keeping hidden peer panels mounted with their sockets suspended. It conflicts with the decision's stated reason ("lower cost than hidden mounted panels") and would rewrite App.tsx's render branch and its CR-03 source-shape tests in App.open-remote.test.tsx. App.tsx and WebShareSessionView.tsx are not touched by this plan.
- **Where the store lives (Claude's discretion; the CONTEXT example was "a per-tab map in App or the RelayClient cache").** A small module-level store in `frontend/src/lib/peerSnapshots.ts`, keyed by session id:
  - `takePeerSnapshot(id)` returns and deletes the entry.
  - `putPeerSnapshot(id, snap)` refreshes the entry's position and evicts the oldest entry beyond `PEER_SNAPSHOT_MAX = 8`.
  - A closed tab's leftover entry is safe (still self-consistent; reopening that session even gets a delta) and bounded by the cap, so App needs no cleanup hook.
  - In memory only, never persisted.
  - **Key is the session id alone (plan check I-2, checked at planning time).** Session ids come from `generateID` in internal/pty/native.go: 16 bytes from crypto/rand, hex-encoded (128 bits). They are unique across both Macs in practice, so a peer tab and any other peer's tab never share a key, and no peer-host prefix is needed.
- **Which panels keep snapshots:** desktop peer tabs only, i.e. TerminalPanel props `remote === true` with no `wsURL` (WebShareSessionView passes `remote={isRemoteWebTab}` and no wsURL for peer tabs; the browser view uses `wsURL`). Local tabs and the browser view never take or put one.
- **Exact offset (the subtle part).** RelayClient advances `offset` when a frame arrives, but xterm parses writes asynchronously. At unmount some received bytes may still be queued, not yet in the buffer. So the cleanup:
  1. reads `client.resumePoint()` (null unless an offset meta made the position valid);
  2. calls `client.close()`, so no more output arrives;
  3. issues `term.write('', cb)`. An empty write's callback runs after everything queued before it (the same trick as guestTerminal.ts applyHostGrid). Only inside that callback does it serialize, `putPeerSnapshot`, and then dispose the serializer and the terminal.
  - A remount that happens before the callback finds no snapshot and gets a full replay, which is correct, just slower.
- **Serializer:**
  - A dedicated `SerializeAddon` instance, loaded only for snapshot-keeping panels and kept in its own variable. It is separate from the Phase 97 plugin hot-swap `serializeAddonRef`, which the plugin arm disposes when `pluginConfig.serialize` is off, as it always is for peer tabs.
  - Call `serialize()` with defaults (scrollback, alternate buffer and modes included).
  - `@xterm/addon-serialize` ^0.14.0 is already a dependency, so there are no installs.
- **Restore order on mount:**
  1. `applyHostGrid(term, snap.cols, snap.rows, recomputeScale)`;
  2. `term.write(snap.data)`;
  3. construct RelayClient with `resume: snap.offset`.
  - The host's 0x02 grid push and replay frames queue behind the snapshot.
  - With `hasRendered` true, a `replay: 'full'` meta calls `onReset` → `resetForFullReplay(term)` (RIS in stream order), so the full fallback clears the restored content first. This is the existing 05-12 path.
- **RelayClient API (additive):**
  - opts gains `resume?: number`. When it is a safe non-negative integer, set `offset` to it, `offsetValid = true` and `hasRendered = true`, and give the first dial the same `?resume=` / `&resume=` suffix redial builds. Factor that suffix into one private helper used by both.
  - New public `resumePoint(): number | null` returns `offset` when `offsetValid`, else null.
  - Nothing else changes. Note: 07-04 later edits `sendInput` in the same file, which is why it runs in wave 2.
- **Fidelity proof:** use real `@xterm/xterm` plus `@xterm/addon-serialize` in jsdom, as `frontend/src/lib/__tests__/replayFidelity.test.ts` already does with a real Terminal.
  - If a fidelity case exposes a SerializeAddon gap that the restore cannot close (for example a lost wrapped-line flag that changes later rows), do not weaken the test. Record it in the SUMMARY and stop with a blocker report. Tabs without a snapshot keep today's full replay.
- **Executor constraints:**
