## Flagged decisions and assumptions

- **D-01 (locked, user-approved): unknown leading flags.** An unknown leading flag prints the error plus usage to stderr and exits 2; it never starts the GUI. The allowlist is exactly the three macOS launch-service shapes `-psn_*`, `-NS*`, `-Apple*` (case-sensitive prefixes). `--help`/`-h` and the daemon flags keep their current handling. Rated **costly** in CONTEXT (launchMode is the entry point for every launch on the remote Mac), so the allowlist is pinned by a TestLaunchMode case per shape. Already settled by the user: no `checkpoint:decision`.
- **Usage-error shape (Claude's discretion).** launchMode keeps its `(mode, cliArgs, err)` signature. An unknown flag returns `modeHelp` with a non-nil error; main's `modeHelp` branch prints `portty: ` and the error before `usage()` and then exits 2 when the error is set. This reuses the existing help path instead of adding a fourth mode constant.
- **--version/-v (decided autonomously in CONTEXT).** launchMode returns `modeCLI` with cliArgs exactly `[version]`; runCLI's existing `version` case prints `Version`, and cliNeedsDaemon already skips the daemon for `version`.
- **kill and rename (decided autonomously in CONTEXT).** Both call `lookupSession(client, args[0])` and pass the resolved `SessionInfo.ID` to the daemon. resolveSession's own errors already carry the `portty: ` prefix, so cmdKill/cmdRename return them unwrapped; daemon call failures keep the `portty kill: ` / `portty rename: ` wrap. CONTEXT's specific idea is confirmed in code: the daemon's `PATCH /sessions/{id}/name` handler looks up the path value as an ID only (internal/daemon/api.go handleRenameSession), so rename-by-name was broken too.
- **Removed test (Chesterton's Fence).** The test named TestDispatchFlagRouting in dispatch_test.go re-implements the old dispatch condition inline instead of calling launchMode (it dates from when dispatch lived in main()). It asserts that `-v` and `--verbose` launch the GUI, which D-01 reverses, and it would keep passing while asserting the opposite of the new behaviour. Its cases move into TestLaunchMode (where they call the real function) and the function is deleted. TestDispatchHelpShort and TestDispatchNoArgs do not contradict anything and stay.
- **wails dev is unaffected.** Wails v2.10.2 dev mode passes `assetdir`, `devserver`, `frontenddevserverurl` and `loglevel` as environment variables (internal/app/app_dev.go reads `os.Getenv` first); the app gets command-line flags only when the developer passes `-appargs`. Every self-exec in this repo (`internal/daemon/process.go`, `internal/daemon/service.go`) passes `daemon` as the first argument, a CLI command.
- **Never launch the GUI on the host.** The built-binary checks run only `--version`, `-v` and `--bogus`, only after TestLaunchMode passes in the same `set -e` script, and with `HOME` pointed at a temp dir (runCLI computes `daemon.DefaultSocketPath()`, which creates the config dir under `$HOME`). Never run the built binary with no arguments or with a `-psn_`/`-NS`/`-Apple` argument on the host: that opens the GUI on the user's Mac. The real launch-services check is TESTING.md M-156 in the Tart VM (added by 16-04).
