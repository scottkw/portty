# 09-07 fix: the quit path gives up quickly on a hung daemon

## The failure

In V-05b the v1.1 daemon was SIGSTOPped while a Restart Now ensure was running. Cmd-Q took 30.2 s to show the Quit dialog, and Quit Everything took 54.76 s to exit. The bar is a few seconds (09-CONTEXT, criterion 9.5).

A stopped daemon still accepts connections, because the kernel queues them. It never answers, so every call waited for the client's 30 s timeout:

- The Quit dialog waited for `ListSessions()` (App.tsx `app:quit-requested`).
- `QuitAll` cancelled the ensure ctx. The ensure's daemon calls ignored that ctx (09-01-SUMMARY's note), so `AnswerDaemonRestart` held `daemonMu` until its call in flight timed out. Then it made more calls. `QuitAll` waited behind it for `daemonMu`.

## The fix

1. **The ensure's client calls are ctx-aware** (`internal/daemon/client.go`, `process.go`).
   - `DaemonClient.WithContext(ctx)` returns a copy that builds every request with `http.NewRequestWithContext`.
   - `ensureDaemon` binds its client to the ensure ctx. Quit All's cancel therefore ends the call in flight at once: the health, version, session and readiness reads, and the restart's `/shutdown`.
   - A count read under a cancelled ctx comes back as -1. That is not an answer, so `ensureDaemon` returns `ctx.Err()` before it would ask the restart question. The GUI's `ensure` also returns before `checkDaemonAPI` once the ctx is cancelled.
   - Callers that never set a ctx behave as before (`context.Background()`).
2. **Quit All waits at most 1 s for `daemonMu`** (`app.go`, `quitLockWait`). A call outside the ensure can hang on the daemon while holding the lock, for example a CreateSession. After that second, Quit All sends `ShutdownDaemon` without the lock and quits.
   - `ShutdownDaemon` already gives up after its 2 s per-attempt timeout when nothing answers. So against a hung daemon, Quit All takes about 2 to 3 s.
   - A 503 from a live daemon frozen for a handoff is still waited out, as the 09-CONTEXT decision requires: "after READY or COMMIT, Quit All waits for the handoff to finish, then stops the daemon normally". That daemon answers, so it is not the hung case. The wait is bounded by `frozenRetryBudget` (20 s; a real freeze lasts about 12 s at most).
3. **Nothing is killed.** No SIGKILL or SIGTERM goes to any daemon or takeover. The stopped old daemon keeps its shells. In V-05b, after `kill -CONT`, it handled the queued `/shutdown` and exited, and no fresh daemon was left. The next launch handles whatever is still running.
4. **The Quit dialog does not wait for the count** (`frontend/src/App.tsx`, `QuitConfirmModal.tsx`).
   - `app:quit-requested` starts `ListSessions()` and a 2 s timer, and the dialog opens on whichever finishes first.
   - On a timeout or an error, the count is unknown (`null`). The dialog then says `Portty couldn't check whether any sessions are running.` instead of `No active sessions.`. A late answer is ignored, because the Go binding turns an error into `[]`, which would wrongly read as zero.

The fix keeps the WR-07 startup guard, share tokens, the CSP and the 32 KiB limits as they were. No Wails binding changed, so the hand-maintained `frontend/src/wailsjs` stubs needed no edit.
