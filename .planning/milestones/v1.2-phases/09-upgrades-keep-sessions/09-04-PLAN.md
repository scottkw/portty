## Flagged decisions and assumptions

- **Depends on all three wave-1 plans.** Read their SUMMARYs first for the exact signatures: 09-01 (`HealthResponse.Handoff`, the 503 retry and `frozenRetryBudget`), 09-02 (`pty.Session.SetReadDeadline/Pid/HandoffFiles`, `NativePTYBackend.Adopt`, `pty.WatchExit`, `fdpass.Send/Recv/PeerUID/PeerPID`, `WebServer.Listener/StartOn`, `Config.APIVersion`), 09-03 (`Hub.Freeze/Thaw/Export/Digest/Start`, `RestartViewers` and its done channel, `ErrHubEnded`, `NewHubFromState`, `HubManager.AddStaged`, `Subscriber.Restart`).
- **Scope after the split (plan check W7).** This plan ends at an in-process `runTakeover(ctx, deps) int` that returns an outcome code. 09-05 adds the process around it (`RunTakeover`, the status pipe, `portty daemon --takeover`), `startDetachedTakeover`, the EnsureDaemon branch and the real launch check. This plan touches no file 09-05 owns except process.go (09-05 runs after it, in wave 3).
- **Wire format (planner's choice; reversible until the first release that ships it).**
  - `const HandoffVersion = 1`, advertised as `Handoff: HandoffVersion` in handleHealth once the route is registered.
  - Request: the takeover dials the socket and sends `POST /handoff HTTP/1.1` with `Upgrade: portty-handoff/1`; the handler checks the method and header, answers `101 Switching Protocols`, and hijacks the connection (the unix listener yields a `*net.UnixConn`; assert it, refuse otherwise).
  - Frames on the hijacked conn: 1 byte type, 4 bytes big-endian length, then a gob payload. fds never share a frame with a large payload: an fd frame is a small fixed header (type, session index, fd count) sent with fdpass.Send and read with fdpass.Recv for the expected count, so the unmeasured per-message fd limit (A3) never matters.
  - Messages in order: HELLO {HandoffVersion, BuildVersion, PID} → HELLO-OK or REFUSE {Code, Reason}; GLOBAL {session count, share server running, share records (session id → grantID, token)} + fd frame [lock, API listener, relay listener, share listener when running]; per session SESSION {ID, Name, WorkDir, CreatedAt, CLI, Pid, HubState} + fd frame [master, slave]; READY {Digests} or ABORT {Reason}; COMMIT; COMMITTED.
  - Caps: one frame at most 64 MiB; a SESSION frame at most `relay.DefaultScrollbackBytes + relay.HistoryMaxBytes + 1 MiB`; a session count at most 256. Anything larger aborts before import (Research Security Domain V5).
- **Timeouts (one block in handoff.go, each a var so tests can shorten it; plan check W3).** `freezeTimeout = 2 s` (09-03's Freeze wait; hubs freeze concurrently), `stateSendTimeout = 5 s` (one write deadline for the whole STATE send on the old side), `readyTimeout = 5 s` (old side, after the state is sent), `committedWatchdog = 5 s` (new side, COMMIT to COMMITTED), `takeoverStepTimeout = 10 s` (new side, the read deadline for each frame before COMMIT; dial 2 s). The longest the old daemon stays frozen is freezeTimeout + stateSendTimeout + readyTimeout + committedWatchdog = 17 s, which is below 09-01's 20 s `frozenRetryBudget`; TestHandoff_TimeoutsFitClientRetry fails if a later change breaks that. Comment the sum next to the block and name frozenRetryBudget.
- **Which sessions move.** Only live sessions: a stopped session has no shell and no fds, so it is not handed over and the new daemon does not list it (as after today's DEBT-08 restart). A session whose hub returns `relay.ErrHubEnded` from Freeze (its shell exited during the freeze) is treated as stopped the same way. Planner's choice, reversible: carrying stopped entries as metadata would add a hub-less session kind for no user-visible gain.
- **Old side (the handler).**
  1. HELLO: `fdpass.PeerUID(conn) == os.Getuid()`, HandoffVersion equal, not an older release (below); one handoff at a time (a second gets REFUSE busy). Read `fdpass.PeerPID(conn)` and register `pty.WatchExit(pid)` now (plan check B1): while this connection is open the pid can only be the takeover's, so a later reuse of the number cannot fool the watch. Both reads go through package seams (`peerUID`, `watchPeerExit`) for the tests, because in-process the peer is the test process itself. A refusal sends no fd and freezes nothing.
  2. FREEZE: set the freeze gate (below), then `Freeze()` every live hub concurrently. ErrHubEnded marks that session stopped. Any other Freeze error: Thaw the ones frozen, clear the gate, send ABORT, close.
  3. STATE: `Export()` each frozen hub (which re-seeds the old hub with its own export, 09-03), collect the session metadata and the share records of live sessions, send GLOBAL with the fds, then each SESSION with its fds, all under stateSendTimeout.
  4. Wait up to readyTimeout for READY; compare each digest with the old hub's `Digest()`. On a mismatch, timeout, ABORT, EOF or error: write ABORT first (best effort), then Thaw every hub, clear the gate, close the conn and log one line (step, reason, counts). ABORT goes out before any Thaw (threat I1, T-09-25): a takeover still waiting never proceeds on a snapshot the old daemon has since moved past.
  5. COMMIT. From here the old daemon never resumes reading on a timer.
  6. EOF or a read error before COMMITTED (plan check B1): do not Thaw yet. Wait until the takeover's exit watch fires, so the new process can no longer read; then Thaw (the hubs already hold their own export), clear the gate, keep serving, and log that any bytes the new daemon read in that window are lost. The takeover's committedWatchdog bounds this wait (it exits within 5 s of COMMIT whatever happens) except when the takeover process is stopped by a signal (threat I2, T-09-26). `shortcut:` comment (CONTEXT decision on the COMMIT-to-COMMITTED window, Research A6): the window is milliseconds and the shells survive either way.
  7. COMMITTED: set `handedOff`; `SetUnlinkOnClose(false)` on the API unix listener copy, then close it and the relay and share listener copies; call `RestartViewers()` on every hub (relay viewers via 09-03, browser viewers via this plan's one-line webserver change) and wait on all the returned channels or `restartDrain = 1 s`, whichever comes first (plan check W5), so the 1012 close handshakes finish; then the exit seam (`os.Exit(0)` in production). Never call api.Stop, Hub.Shutdown, HubManager.Shutdown, KillSession or a context cancel on this path (Research Anti-Patterns): each would unlink the socket, send 1000 session ended, or end shells.
  - Accepted overlap: between COMMIT and the old daemon's exit both processes may accept on the shared listeners. The old one answers reads from frozen state and 503 for writes, and its viewers get 1012 when it exits, so nothing is lost. Document it at the COMMIT step.
- **New side (`runTakeover`).**
  - Before dialing (plan check W4): when Tailscale reports a certificate domain, warm the share certificate with the `warmCert` seam (bounded 10 s; a failure is noted, not fatal yet) and log `handoff: cert warm took <ms>ms` (09-07 records it). This happens before HELLO, so it is outside the freeze and outside the old daemon's READY timer. Import never fetches a certificate: the share server is constructed from the records and serves from the warmed cache (the webserver's TLS config fetches through LocalAPI per handshake, and tailscaled caches it). If share records arrive but the warm failed, abort with "share certificate unavailable" before READY.
  - Takes no lock (it receives the lock fd; flock follows the open file description, 09-02 pin) and binds nothing. Every read before COMMIT has the takeoverStepTimeout deadline.
  - Imports into a staged engine: for each session, `backend.Adopt` from the received master and slave with the pid (its exit watcher is registered first), `relay.NewHubFromState(st, sess, sess, resizeFn)`, `manager.AddStaged`, the names and workDirs maps; share records into `a.shares`; the listeners through `net.FileListener`; settings and ct_disclosed reloaded from disk now (a settings PATCH was gated during the freeze, so the disk is current); the capability key reloaded with BootstrapCapabilityState (CONTEXT: "Reloaded from disk").
  - Any import error: send ABORT with the reason, close every received fd and every adopted session's files without signalling anything, return the import code.
  - A received ABORT: close everything and return 6 without reading.
  - READY with each hub's Digest; then wait for COMMIT.
  - EOF before COMMIT: poll the old pid (from HELLO-OK) with `kill(pid, 0)` for up to 500 ms through the `pidAlive` seam. Gone means proceed as committed (Research Pattern 8 extra rule: a dead old daemon cannot read); alive means return 6 without reading. If the EOF came during STATE and the old pid is gone, adopt every session whose SESSION frame and both fds arrived complete, proceed with those, and log the ones lost (they ended with the old daemon); with the old pid alive, abort as above.
  - On COMMIT: arm committedWatchdog, which exits the process through the exit seam if COMMITTED has not been written in time. Serve the API on the received unix listener, the relay on the received TCP listener, the share server with `StartOn` on its listener (grants from the records, Config.APIVersion = APIVersion), `Start()` every hub, re-arm each session's exit goroutine with the API's onExit cleanup, start the daemon log (rotation) and the socketLost watch, then write COMMITTED and stop the watchdog.
  - If the COMMITTED write fails (plan check B1): with the old pid alive, exit at once through the exit seam (`os.Exit(1)` in production, no cleanup), so the old daemon's wait on this process ends and two readers never coexist; with the old pid gone, keep serving as committed.
  - Outcome codes (one table in handoff.go, with `moveFailedReason(code int) string` for 09-05): 0 committed; 3 busy; 4 refused (uid, version, older release); 5 import failed (including "share certificate unavailable"); 6 timed out, aborted, or the old daemon went away alive before COMMIT; 1 anything else. Reasons: 3 "another update is already moving them", 4 "the running version refused", 5 "the new version could not load them", 6 "the handoff timed out", other "the new version exited".
- **Step names (canonical; 09-06 and 09-07 use exactly these).**
  - old: `after-hello`, `after-freeze`, `mid-state-send`, `after-state-sent`, `after-ready-before-commit`, `after-commit-before-committed`.
  - new: `after-hello`, `after-global`, `after-state`, `before-ready`, `after-commit-before-serve`, `after-serve-before-committed`, `committed-write-fails`.
  - `committed-write-fails` makes the COMMITTED write return an error while the process stays alive (in tests the exit seam records instead of exiting).
  - Note for the VM (plan check W2): killing the old daemon at `old:after-freeze` would end the shells, because no fd has left it yet; the old-dies save needs the fds sent, so its VM row pauses at `old:after-state-sent`.
- **Refusing an older release (CONTEXT deferred: a downgrade handoff stays unsupported; "Older-version daemons are refused, or go through DEBT-08").** `olderRelease(a, b string) bool` in handoff.go: both match `^v?\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$`; compare the numeric core, then a version without a suffix is newer than one with, then suffixes compare as strings. Unparseable versions ("dev") are never compared. The VM and integration builds use `v1.2.0-vmA`/`v1.2.0-vmB` and `v1.2.0-itA`/`v1.2.0-itB`, so a GUI A relaunched after an upgrade to B cannot pull the sessions back: its takeover is refused and it gets the DEBT-08 question, where Not Now keeps B (API compatible).
- **Freeze gate.** A middleware on a.mux: while frozen, POST/PUT/PATCH/DELETE (except the handoff route itself) answer 503 with `Retry-After: 1`. GET routes keep serving (health, list, tail, relay-port). /shutdown is POST, so Quit All and a DEBT-08 restart wait for the outcome (09-01's client retry), which is the CONTEXT rule "after READY or COMMIT, Quit All waits for the handoff to finish, then stops the daemon normally".
- **SIGTERM guard (Research Pitfall 4).** Extract runDaemonCore's serve tail into one function (runDaemonCore keeps its exact behaviour; 09-05's RunTakeover reuses it). When ctx ends while a handoff is in progress, wait for its outcome (bounded by the timeout sum above); `handedOff` means exit with no api.Stop, no unlink and no session teardown; rolled back means today's shutdown runs. The lost-socket branch is unchanged.
- **The route is only on the unix socket mux** (Research Security V4): registered on `a.mux` only, never in RelayHandler or the webserver mux. A test asserts the relay port and the share server answer 404 for it (a behaviour test, not a grep).
- **LaunchAgent (CONTEXT: "Portty doesn't install one (confirm). Hand off the same way").** Confirmed at planning time: `portty daemon install` (service.go, kardianos, RunAtLoad true, KeepAlive false) is opt-in and nothing in the GUI or CLI installs it. A launchd-started daemon hands off like any other; afterwards `portty daemon stop` (launchctl) no longer stops the takeover daemon, which launchd does not manage. Record it with a `shortcut:` comment in handoff.go; no special case.
- **Logging (Research Security V7).** Step names, session counts, pids, byte counts, durations and outcome codes only. Never a share token, capability, key or terminal content. A test captures the log output of a full handoff with a shared session and asserts the token string does not appear.
- **Fault seam (Research Pitfall 13).** One package var `handoffFault func(side, step string) error` (nil in release builds) called at every step on both sides; a non-nil error makes that side behave as failing or dying at that step. Tests set it directly. handoff_vmpreview.go (`//go:build vmpreview`, header copied from share_vmpreview.go) sets it from `PORTTY_VMPREVIEW_HANDOFF_FAULT=<side>:<step>:<action>`, where action is `exit` (os.Exit(1) at once, no cleanup) or `pause<N>` (log `handoff-fault: paused at <side>:<step> pid=<pid>` and sleep N seconds, so the VM run can `kill -9` the process at a known step). An old-side fault needs the old daemon itself to be a vmpreview build started with the variable. check-brand keeps the tag out of release scripts.
- **In-process tests.** Both daemons run in one test process: the old API on a temp socket under the TestMain /tmp HOME, a fresh engine and API for the new side calling runTakeover in a goroutine. fds sent over the socket arrive as duplicates in the same process, which is what the kernel does across processes. The exit seams record exits instead of exiting; a recorded new-side "exit" stops that side's hubs and closes its fds, standing in for the process dying. `watchPeerExit` returns a channel the test closes when it declares the takeover dead. Sessions use `/bin/sh` ticker scripts through SetSpawnCommandForTest; shares use SetShareSeamsForTest with the existing fake TLS server pattern from share_test.go.
