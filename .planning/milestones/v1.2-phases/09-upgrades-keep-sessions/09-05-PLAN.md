- **Status pipe (plan check B2: the decision comes from the takeover's outcome, not a clock).**
  - `startDetachedTakeover(exe string) (<-chan int, error)` in process_unix.go: `os.Pipe()`; the write end goes in `cmd.ExtraFiles[0]` (fd 3 in the child) with `PORTTY_TAKEOVER_STATUS_FD=3` in its environment; Setsid; stdout and stderr to daemon.log as startDetachedDaemon does; the parent closes its copy of the write end after Start. A goroutine reads one byte: a byte is the outcome code; EOF with no byte means the child died without reporting, so it waits for the exit and yields the exit code (1 when killed by a signal). It always reaps the child with cmd.Wait (for a committed takeover that is when the daemon eventually exits, as startDetachedDaemon already does for daemons). There is no kill func, on purpose.
  - `RunTakeover()` in process.go (the process entry): read `PORTTY_TAKEOVER_STATUS_FD` and then `os.Unsetenv` it, and set close-on-exec on that fd at once, so shells the daemon later starts never inherit the variable or the pipe. Run runTakeover under a signal context. On 0 (COMMITTED written, serving): write byte 0, close the pipe, then run the shared serve loop like runDaemonCore. On a non-zero code: write that byte, close, `os.Exit(code)`. Without the variable (run by hand) nothing is written. A write error (EPIPE when the spawner has gone) is ignored: Go returns it as an error on fds other than 1 and 2, it does not kill the process.
- **EnsureDaemon branch (Pattern 9; CONTEXT "EnsureDaemon in the new build starts `portty daemon --takeover`").**
  - In the stale-version path, before the DEBT-08 policy: when live sessions are not 0 (an unknown count, -1, also tries: a handoff ends nothing), `opts.NoHandoff` is false and `health.Handoff == HandoffVersion`, spawn the takeover through a package seam (`spawnTakeover func(exe string) (<-chan int, error)`, production startDetachedTakeover; refused from a test binary, like the fresh spawn) and wait for its outcome code or ctx. No wall clock decides. The takeover bounds itself (09-04: dial 2 s, each frame before COMMIT 10 s, the old daemon's READY timeout 5 s, the committed watchdog 5 s); the only unbounded case is a takeover stopped by a signal (09-04 threat I2). For diagnosis, EnsureDaemon prints one `EnsureDaemon: still waiting for the handoff (pid N)` line on stderr once readyTimeout + committedWatchdog + 5 s have passed without an outcome, and keeps waiting.
  - Outcome 0: wait for `daemonReady` (this build's version, Research "ready means the right version") up to daemonReadyWait (the takeover reports 0 only after COMMITTED, when it already serves). Ready returns nil with no question (UPGR-01). Not ready by then returns an error (the GUI shows its daemon error), but never the DEBT-08 question: the sessions are on the new daemon.
  - Outcome 3 (busy): another takeover may be winning; wait for daemonReady up to daemonReadyWait; ready returns nil, otherwise continue as a failure with the busy reason.
  - Any other non-zero outcome, or a spawn error: read /health once more; this build's version means success after all (nil, no question). Otherwise set `MoveFailed = moveFailedReason(code)` (spawn error: "the new version exited") and continue into the unchanged DEBT-08 flow with that question.
  - ctx cancelled (Quit All) while waiting: return ctx.Err() and never kill the takeover (CONTEXT: "It never kills a takeover daemon that might already own the sessions"). startDaemon's lock wait is not used on this path (the old daemon holds the lock by design).
  - Zero live sessions: today's plain restart (Research A9). `handoff` absent (v1.1) or a different HandoffVersion: no takeover, the plain DEBT-08 question (MoveFailed empty).
