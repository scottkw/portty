# 11-07 fix: Markdown parses in a Web Worker with a 3 s limit

## The problem

marked 18.1.3's inline tokenizer takes time that grows with the square of the unclosed emphasis delimiters in one paragraph. The parse ran on the main thread, so one hostile `.md` froze the viewer's whole window, terminal tabs included. The input that shows it is `'*a **b _c'` repeated with no separator; with a trailing space (`'*a **b _c '`) marked is linear (80 KB in 18 ms). Re-measured in a node worker thread: 10 KB 0.3 s, 20 KB 1.2 s, 40 KB killed at 3 s.

## The fix

- `frontend/src/lib/markdown.ts` is now parse only: `parseMarkdown(src)` returns marked's HTML, not yet safe. The marked configuration (raw HTML dropped, image placeholders, task glyphs, `MAX_DEPTH` 20) is unchanged.
- `frontend/src/lib/markdownWorker.ts` runs `parseMarkdown` in a module worker: one message in, one out.
- `frontend/src/lib/parseMarkdownInWorker.ts` starts a fresh worker per call and terminates it when the call settles: reply, worker error, abort, or `MARKDOWN_PARSE_TIMEOUT_MS` (3000, start-up included). A factory parameter is the test seam.
- `frontend/src/lib/markdownSanitize.ts` holds DOMPurify and the 11-07 configuration byte for byte, on the main thread, loaded through `import()`.
- `MarkdownPreview` runs `blob.text()`, then the worker parse and the lazy sanitizer import, then sets the sanitized string once. Any rejection, the timeout included, calls `onFail` ("Couldn't Show File"). Unmounting aborts, which terminates a running worker. Props (`{blob, name, webMode, onFail, autoFocus?}`) and the output DOM and classes are unchanged.
- Share page CSP: `worker-src 'self'` after img-src (`internal/webserver/csp_mw.go`, Amendment 3 addition in the package comment). `frame-ancestors 'none'` is unchanged and last. `TestCSPHeaders_PreviewDelta` pins the exact policy and `worker-src` exactly `'self'`.

## DOMPurify did not run in the worker

It can't. A worker has no `document`, so DOMPurify sets `isSupported = false`, and `sanitize()` then returns its input unchanged (`if (!DOMPurify.isSupported) return dirty` in purify.es.mjs 3.4.17). Sanitizing in the worker would have been a silent bypass. Sanitizing is linear, so it stays on the main thread.

## Build check

The standard `pnpm build` (to the scratchpad, not `frontend/dist`) has one entry chunk with no marked or DOMPurify code, because MarkdownPreview is not imported until 11-09. A throwaway build with a second entry importing MarkdownPreview (not committed) emitted `assets/markdownWorker-*.js` (49.5 KB, marked only, a self-contained IIFE with no imports) as a separate file. The URL is built with `new URL("markdownWorker-*.js", import.meta.url)`, so it is same-origin under both `/` (Wails) and `/app/` (share), never `blob:` or `data:`. DOMPurify sits in its own lazy `markdownSanitize-*.js`. The entry chunk has neither.
