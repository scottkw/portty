## Flagged decisions and assumptions

- **One host value per peer tab (planner's choice).** The host part of a peer tab's id is the same value its snapshot key already uses: `peerSnapshotHost(tab)` = `connectHost ?? peerHost` (lib/peerSnapshots.ts), i.e. the MagicDNS name when the peer has one, else its hostname. `handleOpenRemoteSession` computes `connectHost = session.peerDNSName || session.hostname` once and passes it in **both** the success and the connect-failed calls of `openWebSessionTab`, so a retry after a failure finds the same tab (today the failure path omits connectHost; with a host-keyed id that would open a second tab).
- **`webSessionTabId(sessionId, host?)` in lib/tabs.ts (pure, unit-tested).** With a host: `__websession__<host>/<sessionId>`; without one (the web-mode bootstrap tab): `__websession__<sessionId>`, unchanged, so the `activeId.slice('__websession__'.length)` fallback in the render branch still works for that tab. A `/` cannot appear in a DNS name or a hex session id, so no pair fakes another; DOM `id` attributes accept it.
- **Every caller (Research: 7 call sites).** `openWebSessionTab` (its signature gains the host through the existing `peer` argument; the `(sessionId: string, baseURL?: string, capToken?: string` prefix stays, a source pin in App.open-remote.test.tsx reads it), `handleOpenRemoteSession`'s existing-tab lookup, `dropPeerSession` (match `t.type === 'web-session' && t.peerHost === peerHost && t.sessionId === sessionId` instead of the id), the render branch, and `removeTabState` (already reads the tab by id; unchanged). Keep `connectingRef` keyed by host plus session too (two hosts can connect at once).
- **WebShareSessionView key.** Change the key to `${activeId}:${wsCapToken}` so switching between two tabs with equal session ids always remounts (the CR-03 rationale). Update the CR-03 source pin in App.open-remote.test.tsx to the new key text and keep its intent (keyed per tab, cap included).
- **Retry (Research "App harness retry").** Both `retryInit` entry points require zero tabs (the error banner, and `daemon:recovered` with `tabsRef.current.length === 0`), so an orphan arises only when a peer tab appears while `retryInit` awaits. When `retryInit` is about to `setTabs(restoredTabs)`, compute `peerTabsRemoved(tabsRef.current, restoredTabs)` (lib/tabs.ts: the `web-session` tabs with a `peerHost` whose id is not in the next list) and call `dropPeerSnapshot(peerSnapshotHost(tab), tab.sessionId)` for each, before setTabs (the updater stays side-effect free, as removeTabState's comment requires).
- **Sidebar highlight.** `activePeerId` (Sidebar.tsx ~81) compares session ids only, so two hosts' rows with equal ids would both show `aria-current`. Compare the active tab's `peerHost` with the row's peer `hostname` as well.
- **Out of scope (Research Pitfall 12, CONTEXT).** The daemon's `RemoteCapStore` and proxy route stay keyed by session id alone; recorded as a residual risk (T-10-03), no Go change.
