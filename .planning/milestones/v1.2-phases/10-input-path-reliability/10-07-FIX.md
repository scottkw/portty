# 10-07 fix: a resume exactly at geomEnd gets a delta (R-05)

## The failure

In R-05 everything held except the reconnect. After `kill -CONT` of the home daemon, the office logged `replay session=80d64cb5 conn=4 mode=full bytes=376 resume=true`. The plan needs a delta. A CLI viewer in the same spot clears and repaints (`ClearOnFull`), which writes the history into the real terminal's scrollback a second time. GUI and browser viewers repaint. It is the same kind of failure as Phase 9's V-02 FAIL (09-07-FIX2.md).

## The cause

- The paste counts as typing, so it claimed the grid (INPT-06): `grid … 100x30 -> 85x29 … why=input`. `applyGridLocked` (internal/relay/hub.go:615) calls `resizeLiveEmulator` with genuine = true, because the hub already had a real grid. That sets `geomEnd = scrollback.End()` (hub.go:1420).
- The receiver is a raw `-echo` reader and printed nothing after that. So the ring end did not move, and the tab resumed at exactly `geomEnd`.
- `joinLocked` sent a delta only for `resume > geomEnd` (hub.go:1802 before the fix). The tab therefore got the rendered full replay.
- This happens to any reconnect after a claim that moved the grid, as long as no output followed: a quiet shell, a raw reader, or an idle prompt whose SIGWINCH redraw printed nothing.

## The 05-08 analysis (Chesterton)

The strict `>` comes from 7c682489 ("fix(05-08): geometry-aware Join"). The 05-08 plan asked for `resume >= geomEnd`. The executor changed it to `>` (05-08-SUMMARY.md, deviation 1). The reason given: the plan's own `TestReplayFidelity_ResumeAcrossResizeIsFull` takes its offset just before the resize, with no output in between, so offset == geomEnd. Under `>=` that case got a delta. The summary adds: "the offset may predate the resize … a full replay is always safe". The hub.go comment ("A resume exactly at geomEnd may predate the resize") says the same thing.

Why `>=` is correct:

- `geomEnd` is the ring end at the moment of the resize, so every ring byte at or after it was written after the resize. A delta from `resume == geomEnd` holds no pre-resize bytes. The range [resume, geomEnd) is empty.
- The 05-08 jumble had one cause: replaying pre-resize bytes (Ink relative redraws laid out for 100 columns) into a viewer at the new width. The evidence is `IntactRingAcrossResizeRendered` in 05-08-SUMMARY.md: raw `ESC[1A` from before the resize, sitting in the full replay. `>=` never sends those bytes. `resume < geomEnd` still gets the full replay, and the full replay still takes the rendered path whenever `geomEnd > 0`.
- "May predate the resize" is true, but it does not matter. Take a viewer that stayed connected through the resize. It got the 0x02 grid frame (`broadcastResize`, hub.go:634), then the post-resize bytes. A viewer that reconnects at `geomEnd` gets the current grid frame first (relay/server.go: the grid is known after a genuine resize; webserver/server.go always sends it), then the same post-resize bytes as its delta. Both viewers start from the same pre-resize screen and receive the same sequence, so they end in the same state.
- The old `TestReplayFidelity_ResumeAcrossResizeIsFull` sent only post-resize output (a turn at 80 columns) after its offset. So its "full" assertion pinned the boundary, not a real jumble.
- "A full replay is always safe" turned out to be false. It duplicates CLI scrollback and repaints GUI viewers. That is R-05, and V-02 before it.
- Edge cases checked, and none changes between `>` and `>=`:
  - The app can write output between `resizeLiveEmulator` and `resizeFn` (before its SIGWINCH). Those bytes land after `geomEnd` but are laid out for the old grid. A connected viewer gets them too, and a `resume > geomEnd` delta could already contain them. This race is older than 05-08 and is not made worse here.
  - A handoff import restores `GeomEnd` with the same meaning.
  - `geomEnd == 0` keeps its meaning of "no resize".
  - `SnapshotFrom` must still succeed, so a resume the ring no longer covers still gets a full replay.

No case was found where `>=` is wrong, so the code was changed as intended.

## The fix

The fix is in `internal/relay/hub.go:1805`: `resume >= h.geomEnd`, replacing `resume > h.geomEnd`. The comment beside it now gives the reasoning. The `geomEnd` field comment and the `Join` doc say a delta may start at or past `geomEnd`.
