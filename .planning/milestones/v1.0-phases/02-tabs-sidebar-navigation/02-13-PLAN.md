## Phase Goal

Users navigate everything from tabs plus a sidebar: the Hub grid is gone, and the sidebar lists local sessions and tailnet peers' sessions, each opening in a tab. (ROADMAP Goal, verbatim.)

This plan delivers the user's 2026-11-15 amendment to THEM-01 and ROADMAP success criterion 7: the app still follows macOS light/dark by default, but Settings ▸ Appearance can override it with Light or Dark. It comes after plan 02-12 because it is a scope change made while the phase was executing. Plan 02-11 already owns the Settings sheet but cannot take this work without becoming too large. This plan re-runs the full phase gate at the end, because plan 02-12's gate is no longer the last one.

<objective>
Add an Automatic / Light / Dark appearance setting. It is stored in settings.json (`appearance`: system | light | dark), validated by the daemon, applied natively through NSApp.appearance at startup and live on change, so CSS `prefers-color-scheme`, the terminal palette hook and the sidebar vibrancy all follow one source. The key risk is whether WKWebView re-evaluates `prefers-color-scheme` when NSApp.appearance changes. Task 1 proves or disproves it in the built app, and Task 2 carries a ready fallback.

Purpose: REQUIREMENTS THEM-01 (amended: "Settings ▸ Appearance offers Automatic / Light / Dark to override it") and 02-CONTEXT.md Settings bullet (amended 2026-11-15: "The override sets the native app appearance … stored in settings.json (new `appearance` key: system|light|dark) so it applies before the window first paints, and applies live. The web share page keeps following the browser"). 02-UI-SPEC.md Deviations row "Appearance control (amended 2026-11-15)".
Output: the daemon setting and API, Wails bindings, a tiny cgo/Objective-C file, the Settings control, the hook override, tests, TESTING.md M-68, and a re-run of the full phase gate.
</objective>
