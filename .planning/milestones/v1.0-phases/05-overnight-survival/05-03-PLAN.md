<objective>
Make "restores scrollback" true after the raw ring wraps. The hub keeps its own ring of about 10,000 rendered lines, filled by draining the live emulator's scrollback after every write, cleared by ED3/RIS, and kept across emulator rebuilds. When the ring has wrapped, the full replay becomes history + the full-height screen + cursor position + mode restores, in a byte format xterm.js renders exactly like the host.

Purpose: CONTEXT scrollback decision (10,000 lines, memory only), with the mechanism amendment chosen after research: raising the emulator's scrollback in place measured 126.6 MiB per session, while rendered lines measured 1.1 MiB, and the emulator is thrown away on every resize. RESEARCH Patterns 4 and 5, Pitfalls 1, 2, 4, 5, 12.
Output: internal/relay/history.go, hub changes, tests. The resume protocol and Join (05-01) are unchanged; only the wrapped full-replay content changes.
</objective>

## Flagged decisions and assumptions

- [EDGE-UNCLASSIFIED SHAR-07] The spec-less edge probe could not classify SHAR-07 (status unresolved). Planner-authored edge assumptions pinned here: exactly 10,000 retained lines when more scrolled; the byte cap wins over the line cap for very long lines; a single line longer than the byte cap is dropped (history may be empty); empty history adds no leading CRLF; a main-screen TUI that never scrolls replays with no history part.
- [EDGE-UNCLASSIFIED VERF-01] The spec-less edge probe could not classify VERF-01 (status unresolved). Planner assumption: "the previous day's scrollback is intact" means the last 10,000 lines (or 4 MiB) of main-screen output survive any number of reconnects and host resizes while the host daemon runs; output cleared with `clear` is gone by design.
- Mechanism vs the literal decision wording: the decision text says "raise liveEmulatorScrollbackLines to ~10,000". The amendment in the same CONTEXT section moves the 10,000 lines into a hub-owned rendered ring; the emulator's own scrollback max is set to the same 10,000 only so a single large write is not truncated before the drain (it is drained after every write and stays near empty).
- Alt-screen scrollback inside the vt library grows unbounded (Pitfall 3, pre-existing, no public API to cap it). CONTEXT says add a heap soak test only if cheap, otherwise defer: deferred as a todo in 05-07; this plan does not touch it.
- Only DEC private modes are restored; ANSI modes (for example LNM) are not tracked. The vt callbacks report both, the replay emits DEC modes only.
- Mode restores emit each tracked DEC mode's current state in ascending mode-number order, so the format is deterministic and testable.
