## Flagged decisions and assumptions

- Version: `toolchain go1.26.11`, not the `go1.26.3` the todo suggests. go.mod's go line is already `go 1.26.4` (Portty's own; the highest dependency go line is tailscale.com's 1.26.3), and a toolchain line older than the go line is meaningless (planner check: `go mod tidy` keeps it but no toolchain switch happens). go1.26.11 is the newest Go 1.26 patch (go.dev/dl, 2026-11-17): same encoding/json behavior as 1.26.3, with the security fixes since. It is already in the module cache and `GOTOOLCHAIN=go1.26.11 go build ./...` succeeds on this tree.
- Enforcement (planner check, 2026-11-17): with the default `GOTOOLCHAIN=auto` and a local go1.27.4, a `toolchain go1.26.11` line does NOT downgrade (auto only switches to newer toolchains; a scratch module printed go1.27.4). So the pin needs three parts: the go.mod line (CI: setup-go v6 reads the toolchain directive, per its README; machines with an older default Go auto-upgrade to it), build.sh exporting GOTOOLCHAIN from go.mod (the normal app build), and a `//go:build go1.27` compile guard in package main so a direct `go build`/`wails build`/`go test .` under Go 1.27 fails loudly instead of producing a binary.
- The guard means every Go command on a Go 1.27 machine needs `GOTOOLCHAIN=go1.26.11` (all gap-closure plans already use it; 05-15 documents it in TESTING.md). The guard and the pin are removed together when tailscale.com is upgraded to a release that supports Go 1.27: run the canary under the new Go first.
- No user setting is changed (no `go env -w`, no shell profile edits). If the user wants plain `go` to work in this repo on their Mac, they can export GOTOOLCHAIN themselves; the SUMMARY says so.
- CI: build.yml is unchanged (its setup-go step already uses go-version-file: go.mod). CI is currently disabled.
