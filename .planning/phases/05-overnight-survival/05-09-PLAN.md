## Flagged decisions and assumptions

- Boundary placement (Claude's discretion): one boundary per terminal tab wrapper (keyed by the tab, so a throw in one terminal unmounts only that terminal) and one around the `__websession__` branch (reset when the active tab changes, via a `resetKey` prop rather than a `key`, so a reset never remounts healthy children). A root boundary in main.tsx is the last resort. No new dependency (no react-error-boundary).
- Fallback copy is fixed text in the existing banner style (`banner banner--warning`); it never renders `error.message` or the stack, because a WebSocket constructor error message contains the URL, and a remote tab's URL carries `?cap=`. The console log names only the error name and the boundary's label.
- The RelayClient constructor-throw hardening (a bad URL must not kill the reconnect loop) is in 05-13, which owns relayClient.ts in this gap run.
- VM evidence file (shared with 05-12, 05-13 and 05-14): `.planning/phases/05-overnight-survival/05-VM-MATRIX.md`. This plan creates it with a header (date, build commit, VM roles) and a `## Feature checks` table whose columns are `| Check | Result | What was checked | Evidence |`; Result is exactly `PASS` or `FAIL` (machine-read by the gates). Never write a share link or cap value into it.
- The VM check uses the two Tart VMs on the tailnet: `portty-test` (office role, tailnet `portty-vm-office-2`, 100.103.7.20) and `portty-test-2` (home role, `portty-vm-home-3`, 100.78.170.1). Helpers are in ~/.local/share/portty-vm-tools (copy vm.sh, vshot.sh, vdeploy.sh into your scratchpad, set the IP from `tart ip <vm>`; click is a prebuilt host binary to copy into the VM). Never click on the host (user rule).
