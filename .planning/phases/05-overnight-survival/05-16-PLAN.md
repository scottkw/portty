## Flagged decisions and assumptions

- **Hook point in the GUI.** The 5 s poller is `startTrayPoller` (app.go): it already calls `a.client.Health()` every tick through `refreshTrayState`. The respawn is a new method that runs on the same goroutine, before `refreshTrayState`, on the immediate refresh and on every tick. It is not inside `refreshTrayState`, because that returns early when `trayInit` is false, and tests never set `trayInit`. The extra Health call on a unix socket every 5 s costs nothing.
- **No client rebuild (deviation from the orchestrator brief).** `a.client` is a socket-path client that dials on every request, and it is deliberately never reassigned: the pollers read it without a lock (WR-05, `TestRetryDaemonSuccess_KeepsClientAndPollers`). Once a new daemon binds the same socket, the existing client reaches it. Replacing the client would add a data race and fix nothing.
- **Frontend unchanged.** Guest tabs re-auth through the ConnectPeer and GetRelayPort bindings and pick up the new relay port; 05-14's manual start proved this. Local tabs whose sessions died with the daemon are closed by the existing exit watcher (TERM-05). `daemon:error` feeds the existing banner ("Unable to connect to session daemon" plus Retry Connection). That banner only shows when no tabs are open. While the daemon is down, the tray icon shows its error state anyway. This is a known limit, and the frontend stays out of scope (smallest change).
- **Serialization.** A new `daemonMu sync.Mutex` guards every EnsureDaemon after startup, plus the respawn streak fields. RetryDaemon takes it with Lock, keeps its existing `awaitStartup`/`errStartupTimeout` guard, and now calls the ensure seam instead of `daemon.EnsureDaemon` directly (nil seam means EnsureDaemon, so `TestRetryDaemonFail` still exercises the real refusal). The poller takes it with TryLock and skips the tick if it is held. The respawn also skips while `startupDone` is still open, using a non-blocking select. In production the poller starts after `startDaemon` returns, but the check keeps the rule explicit. Startup's own `startDaemon` is unchanged apart from sharing the seam helper.
- **Rate limit (Claude's discretion: an inline doubling, not the attach package's unexported backoffDelay).** The first attempt runs on the first tick that finds the daemon down. The next attempt waits `min(10 s << (attempts-1), 2 min)` after the previous one. A successful EnsureDaemon does not end the streak. It ends only when a tick finds the daemon healthy at least 1 min after the last attempt, mirroring the attach loop's HealthyReset. So a daemon that starts and then crashes again is still spaced out, never respawned every 5 s. On the third attempt of a streak the app emits `daemon:error` once. The message is the EnsureDaemon error text, or "Portty restarted the daemon 3 times and it keeps stopping." when the last EnsureDaemon succeeded. After that it keeps trying at the 2 min cap, because the remote Mac case needs the app to recover by itself. A successful RetryDaemon resets the streak. The respawn does not write `a.daemonErr`, which stays the startup error that GetDaemonError reports. Each attempt writes one stderr line with the attempt number and its result.
- **CLI.** The fix is in cmd_attach.go only. The re-auth closure in `attachRemote` moves into `remoteReauth(client *daemon.DaemonClient, host, sid string, port *int) func(context.Context) attach.Verdict`, and the URL closure reads the same `port`. When `client.GetRelayPort()` fails, remoteReauth calls the package seam `var ensureLocalDaemon = daemon.EnsureDaemon` with `daemon.DefaultSocketPath()`, the same path runCLI uses. If that errors, it returns VerdictRetry. Otherwise it tries GetRelayPort once more, returns VerdictRetry if that still fails, and from there continues exactly as today (ConnectPeer, then peerVerdict). When the daemon is healthy, GetRelayPort succeeds, so EnsureDaemon is never called and the R7 path (ConnectPeer gives not_sharing or no_such_session, then VerdictShareStopped) is untouched. Re-auth runs once per redial attempt, so the loop's 1 s to 30 s backoff is the CLI rate limit. internal/attach/loop.go is not changed.
- **Spawn races.** A GUI and a CLI can respawn at the same moment, as in VM sub-run (c). The in-app mutex covers the GUI. Across processes, the new daemon's `api.Start` runs CleanupStaleSocket and exits with "daemon already running" when a live daemon answers. The VM gate checks that exactly one daemon process is left.
- **Daemon log rotation.** Every daemon start rotates daemon.log to daemon.log.1. After a respawn, the killed daemon's lines are in daemon.log.1. Look there for R6 evidence on the home VM.
- **Toolchain.** Every Go command runs with `GOTOOLCHAIN=go1.26.11`, because toolchain_guard.go deliberately fails go1.27 builds.
