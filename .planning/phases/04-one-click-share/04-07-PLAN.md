<objective>
Close UAT gap 1 (major, intermittent): the first `portty attach <office>:"shell 1"` from the home Mac blanked the home GUI tab and a browser on the same shared session (lone `-` top-left), the CLI bar read `4 viewers` / `[reconnecting]`, the office window kept working, and detaching restored the others within about 10 s. A second attach and a 3x loop did not reproduce, and no logs exist.

This plan leads with diagnosis. Task 1 builds an in-process reproduction harness of the exact attach path with fake local clients (no tailnet). Task 2 runs one variant per ranked hypothesis through it. Task 3 fixes, in shared code, every variant that goes red (each with its failing test), and writes down explicitly whether the UAT event's root cause is pinned. Nothing is fixed without a failing test first. Plan 04-08 adds the daemon-side diagnostic log for the live repro either way.

Ranked hypotheses (from reading the code for this plan; the executor confirms each in Task 2):

1. H-grid, host-local tiny grid push. Best fit for "guests blank, office fine, recovered without reconnecting": only guest viewers apply a server grid frame (MsgResize 0x02). TerminalPanel's guest onResize calls term.resize with the pushed size (floored at 1); the host panel ignores 0x02 and the CLI's WsOutputPump ignores it too. A 0x02 with tiny dimensions shows a lone character top-left on guests, and a later normal 0x02 restores them. Only Hub.ResizeClient can broadcast one, and only for an Origin "local" subscriber (min-among-local, which takes any positive size; xterm's fit floors at 2x1). The remote CLI is Origin "web" on the host, and handleWSSRelay drops its MsgResize2. So the CLI cannot trigger this directly, and the harness has no in-process trigger for it. 04-08 logs every grid change with origin and client.
2. H-net, first-contact path stall. Fits `[reconnecting]` (no frames for more than 5 s), first-attach-only (Tailscale paths often start on DERP and then go direct), office unaffected and recovery in about 10 s. It does not explain the blank, and it can't be reproduced in-process. 04-08 logs the proxy dial time and close, and M-83 records `tailscale ping`.
3. H-replies, replayed query replies typed into the shared shell. The CLI writes the catch-up preamble (raw scrollback ring) to the user's terminal. A real terminal answers the historic queries in it (DSR, DA2, DECRQM, XTVERSION, kitty keyboard query) on stdin. StdinPump forwards those answers as MsgInput, and InputAbsorber drops only OSC 10/11 and DA1 replies, so the rest reach the shared PTY as typed input. Every viewer sees that. This one is reproducible in-process and expected red.
4. H-resize, the CLI reports a tiny size. Refuted by code: handleWSSRelay drops MsgResize2 from web viewers, and ResizeClient ignores non-local origin. Expected green.
5. H-stuck, a slow or stuck CLI blocks fan-out. Refuted by code: broadcast, BroadcastMeta and broadcastResize use a non-blocking send plus CloseSlow (TestHubSlowSubscriberGetsDisconnected, TestBroadcastMeta_NonBlocking). Expected green end to end.

Side findings to record (code reading). `4 viewers` is SubscriberCount including the office's own local panel: 1 local + GUI tab + browser + CLI = 4, so it is normal and not a ghost connection. `[reconnecting]` shows on any idle remote attach after 5 s, because the host sends no heartbeat frame and cmd_attach.go's watcher keys on received frames. That indicator issue belongs to Phase 5 (reconnect/idle) and is recorded there, not fixed here.

Purpose: a CLI attach must never disturb the GUI tab or browser on the same share, and the next live occurrence must be diagnosable.
Output: internal/daemon/attach_viewers_test.go (harness, variants, verdict header), the fix for each red variant, and TESTING.md and STATE.md updates.
