## Flagged decisions and assumptions

- **DEBT-01: decision between the two CONTEXT options, checked against the pinned vt source** (`$(GOTOOLCHAIN=go1.26.11 go list -m -f '{{.Dir}}' github.com/charmbracelet/x/vt)`, version v0.0.0-20260615092313-b57e5e6d29bb).
  - **`SetScrollbackSize(0)` in the alt screen does not work. Ruled out.**
    - `Emulator.SetScrollbackSize` (emulator.go:477) calls `e.scrs[0].SetScrollbackSize`, the main screen only. `Scrollback()` (:451) and `ClearScrollback()` (:482) also use `scrs[0]`.
    - `Scrollback.SetMaxLines` (scrollback.go) returns early for `maxLines <= 0`, and `NewScrollback(<= 0)` falls back to `DefaultScrollbackSize`. So 0 is a no-op even on the main screen.
    - `NewEmulator` (emulator.go:77-82) builds both screens with `NewScreen`, and `NewScreen` (screen.go:23-29) gives each one a 10,000-line scrollback. The alt screen's scrollback is reachable only through the unexported `scrs` array.
  - **A periodic in-alt rebuild works, but it is the weaker option.**
    - vt exposes no length for the alt scrollback, so the "a few hundred lines" threshold cannot be observed.
    - Counting bytes or LFs is no substitute. An ED 2 under a background colour pushes a whole full-width screen from a few bytes (screen.go `ClearWithScrollback`, and blank cells with a background are not `EmptyCell`), so such a proxy does not give a bound that is independent of width.
    - A rebuild inside the alt screen would also have to re-create the alt screen's region, origin mode, saved cursor, pending wrap, pen and charset, plus the main screen behind it. The exit rebuild needed three review iterations for a smaller surface, and this one would run every few hundred lines.
  - **Chosen (departure from CONTEXT's two literal options; in the spirit of its "prefer the far smaller one"): disable the alt screen's scrollback once, at construction.**
    - Call the exported `Screen.SetScrollback(nil)` (screen.go:399-403, documented "Pass nil to disable scrollback") on the alt `Screen`.
    - The alt `Screen` is reached with `reflect`: Emulator field `scrs`, checked to be exactly `[2]xvt.Screen` before the cast, element 1, then `unsafe.Pointer(v.UnsafeAddr())` in one expression (unsafe.Pointer rule 5, accepted by vet).
    - Nothing reads the alt scrollback. `drainScrollbackLocked` reads the main one, `Render` reads the screen buffer, and `DeleteLine`, `ClearWithScrollback` and the ED 3 handler all nil-check it (screen.go:97-104, :359-367; handlers.go:560-566). `fullReset` (esc.go:24) calls `Screen.Reset`, and `Screen.Resize` (screen.go:74-82) does not touch the field, so one call lasts for the emulator's life.
    - **Measured at planning time** (scratch probe on the pinned modules: 200 main lines, then 20,000 alt lines, then RIS plus another 20,000):
      - growth 93.6 MiB → 0.0 MiB at 80 columns, and 268.6 MiB → 0.0 MiB at 220;
      - main scrollback the same (177 lines) with or without the call;
      - `go vet` clean.
    - **Not a vt fork:** no vendored copy and no source change. It couples to one unexported field of a pinned module, and `TestVTLayout_AltScreenScrollback` fails on any vt upgrade that renames or retypes that field.
    - **Runtime fallback:** if the lookup fails, `disableAltScreenScrollback` returns false. newLiveEmulator then logs once (sync.Once) and carries on with today's behaviour. The HARD-01 exit rebuild still frees the alt scrollback when the app exits. It does not panic, because a crash on the unattended remote Mac costs more than the memory does.
- **The alt-exit rebuild stays (Chesterton).** It is the runtime fallback above. SC2 pins its fidelity, and DEBT-02/03 build on it. Its doc comment changes: it no longer exists to free the alt scrollback in the normal case. Removing it is a separate user decision, not taken here.
- **DEBT-02: where the wrap flag is lost (checked at planning time). At the source: vt never records it.**
  - `uv.Line` is a plain `[]Cell`, and `uv.Cell` holds only Content, Style, Link and Width (ultraviolet cell.go:15-30).
  - `handleGrapheme`'s wrap (vt utf8.go:54-61) calls `index()`, and nothing marks the row.
  - `DeleteLineArea` copies cells (ultraviolet buffer.go:493-518), so a row has no identity the hub could follow.
  - So history push, `renderScreenLocked` and the history replay all join rows with CRLF, because they have nothing to go on.
- **Rejected: "a row that reaches the last column is wrapped".** It would also join every exactly-full row ended by CRLF: full-width rulers, Claude Code's box borders, and a p10k frame line that reaches the edge (the user runs p10k, see HARD-08). Every copy and every reflow would join such rows with the next line.
- **Chosen: detect the wrap as it happens, through vt's `CursorPosition` callback** (screen.go:157-171 and :178-205 fire it on every move).
  - **Signature.** A callback whose `old.X == W-1`, `new.Y == old.Y` and `new.X` is 1 or 2, where the previous callback ended at `old` and started at column W-1 on another row. That is index()'s down-move, or ScrollUp's restore move, then the print at column 0. The wrapped row is `new.Y-1` in both the plain and the scroll case.
  - **Verified in the scratch probe at 80 columns:** it fires for a 102-column command (plain wrap), for the same command wrapping on the bottom row (scroll case) and for a wide character at the edge. It does not fire for an exactly-80-column `=` line ended by CRLF.
  - Known false positive: an LF from column W-1, then CHA/CUP/DECRC to column 1-2 on the same row, with no move in between. It is very rare, and the full-row and hash checks below make it harmless.
  - **Storage.** A Hub-owned bounded multiset of 64-bit FNV-1a hashes of the wrapped row's `uv.Line.Render()`, which is the same string drainScrollbackLocked already pushes. It holds no text.
    - Cap: `wrapSetMax = 4096` keys, oldest evicted. One 32 KiB read can wrap about 400 rows at 80 columns, and all of them are drained after that read.
    - The Hub owns it, so it survives the alt-exit rebuild, whose seed re-renders the same rows to the same strings.
    - Cleared with h.history on RIS and on ED 3, and after a resize rebuild, which pushes the visible rows and starts empty.
  - **Join rule.** Emit row y without the CRLF to row y+1 only when all of these hold:
    1. main screen (never in the alt screen);
    2. autowrap on (`h.modes[7]` true or unset);
    3. row y is full: its last non-empty cell's x plus width reaches W. vt drops a wide character that does not fit at the edge (probe), so a non-full "wrapped" row stays a hard break, matching vt's own state;
    4. row y's hash is in the set;
    5. row y+1 renders non-empty. Without this, a blank continuation would make the next row's CR cancel the pending wrap and lose a row.
  - Detection runs only during the live feed write in recordFrameLocked (a Hub flag such as `trackWraps`), never during the rebuild's probes, seed or tail writes, so the probe 'x' and the seed's own joins record nothing.
  - **Residual (`shortcut:` comment):** a remote `portty attach` whose terminal is wider than the host grid sees joined screen rows reflow onto fewer rows. The CLI ignores the 0x02 grid, so a narrower one is already misaligned today. GUI and browser viewers run at the host grid (applyHostGrid), where the layout is identical.
- **History API.** `Push(line string, wrapped bool)`, where wrapped means "continues onto the next line". `Render` joins `lines[i]` to `lines[i+1]` with "" when lines[i] is wrapped and lines[i+1] is non-empty, otherwise with "\r\n". New `EndsWrapped()` tells joinLocked whether the history-to-screen boundary needs a CRLF.
  - The resize push forces wrapped=false on the last row it pushes (the cursor row), because the rows below the cursor are dropped.
  - Callers: drainScrollbackLocked, resizeLiveEmulator and tests. grep `history.Push(` and update each.
- **No IN-06 reorder here.** 08-02 moves the mode restores before the text and before the history. Its autowrap guard depends on this plan's rule 2, which is why the guard is stated here.
- **Fixture.** `softwrap-replay.json` is written by a new Go test behind the existing `-update-replay-fixture` flag (replay_fidelity_test.go:398). replayFidelity.test.ts feeds it to real xterm.js after `resetForFullReplay`, as it already does for ris-replay.json.
