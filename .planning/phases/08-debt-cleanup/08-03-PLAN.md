## Flagged decisions and assumptions

- **Key = host plus session (W1).**
  - App's peer tab carries `peerHost` (the tailnet HostName, which can repeat: WR-05 in App.open-remote.test.tsx) and `connectHost` (the MagicDNS name when the peer has one, App.tsx:851). The host part is `connectHost ?? peerHost`, the same expression App already uses to reconnect (App.tsx:1148).
  - App passes it as a new `snapshotHost` prop, through WebShareSessionView (a pass-through) to TerminalPanel.
  - `peerSnapshotKey(host, sessionId)` joins them with a NUL, so no host or id can fake another key.
  - A panel without a snapshotHost uses host `''`. That is how the existing TerminalPanel tests mount, and it is no worse than today's id-only key. Browser views (wsURL) never keep snapshots, as before.
- **Byte budget (IN-02, Claude's discretion within CONTEXT's "e.g. 8 MiB total").**
  - `PEER_SNAPSHOT_MAX_BYTES = 8 * 1024 * 1024`, counted as `2 * data.length` (JS strings are UTF-16 in memory).
  - Put evicts the oldest until the store fits both caps. `PEER_SNAPSHOT_MAX = 8` stays.
  - A snapshot larger than the whole budget is not stored. That tab gets a full replay, which is correct, only slower.
- **Close hook (CONTEXT: "find the tab-close path").**
  - `removeTabState` (App.tsx:530) is the one function every tab removal goes through: closeTab, endSession and the session:exit watcher. For a `web-session` tab with a peerHost, it calls `dropPeerSnapshot(host, sessionId)`.
  - Read the tab from a ref or from `prev` without side effects inside the `setTabs` updater, which React may call twice. If grep finds another path that removes peer tabs without removeTabState, add the call there too.
  - **The race:** closing the active peer tab runs removeTabState first, and React unmounts the panel afterwards. The unmount's `term.write('')` flush then lands after the drop and would store the snapshot again.
    - So dropPeerSnapshot also bumps a per-key generation. The panel reads the generation at mount and passes it to putPeerSnapshot, which stores nothing if it changed. A reopen of the same session reads the new generation, so it can save again later.
    - Generations are one number per key ever dropped in this app run, which is small.
- **W2: flush timeout.**
  - The cleanup races the `term.write('', cb)` callback against `PEER_FLUSH_TIMEOUT_MS = 1000`.
  - Whichever comes first wins, through a once-only finish. The callback path stores the snapshot (as today, subject to `peerWatch.suffix()`). The timeout path stores nothing, because the buffer may lag the offset.
  - Both paths dispose peerWatch, the serializer and the terminal, and settle the pending save.
- **IN-03: pending save (CONTEXT: "a pending-save promise that the next mount awaits, briefly (≤ 250 ms), before dialling").**
  - peerSnapshots.ts tracks one pending save per key. The cleanup begins it, and the finish above settles it either way.
  - On mount, if a save for the key is pending, the panel waits until it settles, capped at `PEER_SAVE_WAIT_MS = 250`. Then it takes the snapshot, restores it, constructs the RelayClient with `resume` and wires input. Without a pending save it does all of that synchronously, as today.
  - The mount effect therefore gets a `start()` step and a cancelled flag. The cleanup must cope with start() not having run: no client yet, nothing to save, but still dispose the terminal.
  - Keep every other cleanup step and its order, and keep the Phase 97 serializeAddonRef arm untouched.
- **DEBT-05: what "sent" means (CONTEXT: show "Paste interrupted: N of M KB sent", never queue or resend, frames already sent count as sent).**
  - `sendInput` keeps queueing every frame synchronously, exactly as HARD-02 verified. No flow control, no queue.
  - A browser WebSocket's `bufferedAmount` keeps the bytes it never transmitted after the socket closes (WHATWG WebSockets). So when a socket the client did not close dies (onclose in both modes, and `abandon()` for the stale-socket kill), the client computes how much of the last split paste left the browser.
    - Paste bytes still buffered = clamp(bufferedAmount − bytes queued after the paste, 0, the paste's wire bytes).
    - N counts only whole frames before that point, because the server's reader drops a partial frame. M is the paste's payload size. N rounds down to KB, M rounds up.
    - "Sent" means handed to the network by the browser. If the network died with data in flight, the shell may have received less. The notice tells the user the paste was cut short, which is what the requirement asks. A server ack would change the wire protocol and is out of scope.
  - Every `ws.send` (input, resize, ping, probe) goes through one private helper, so bytes queued after a paste are counted.
  - A second split paste on the same socket while the first may still be buffered is folded into one record. The notice then covers both, and bytes queued between them count toward the span but not toward N or M.
  - A user `close()` (tab switch, unmount) clears the record without a notice: the browser sends queued data before the close frame, and no panel is left to show it.
  - Single-frame input never triggers the notice. A typed key lost on a drop is today's behaviour and out of scope.
- **Notice UI (CONTEXT: house component over a new one).**
  - SessionEndedBanner gains `kind: 'paste-interrupted'` with numeric props for N and M, the copy `Paste interrupted: ${N} of ${M} KB sent`, and its dismiss button.
  - The numbers are computed on the client, never wire text, so the component's T-175-06-02 rule (never render wire text) holds.
  - TerminalPanel keeps the notice until it is dismissed or replaced by a newer interruption. It can show together with the reconnecting banner.
