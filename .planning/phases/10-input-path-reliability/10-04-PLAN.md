## Flagged decisions and assumptions

- **Wire (Research Pattern 3).** `const ResizeClaim byte = 0x01` (MsgResize2 payload[4], bit 0: a user-initiated size change) and `func ParseResize(payload []byte) (cols, rows int, claim, ok bool)`: fewer than 4 bytes is not ok; fewer than 5 is a report; other bits of byte 5 are ignored. `MakeResizeFrame` (server to client, 0x02) is untouched. No new frame type and no `/health` `api` bump: `APIVersion` stays 2 (Research Pattern 3 and A4: nothing reads the peer api field, and the claim degrades safely in all six sender/receiver directions).
- **Owner rules (Research Pattern 4, tightened by the plan check: no passive event moves a known grid).** Under `mu`: `owner *Subscriber` and the grid target `wantCols, wantRows`, which only a claim, the bootstrap and (10-06) typing set:
  1. Report (`ResizeClient`, plain frame): store the clamped size on the sub and nothing else, owner or not (an owner's sidebar toggle, a banner or a settle refit must not reflow the shell; the owner's typing applies its newest report in 10-06). **Bootstrap:** a `local` sub reporting while the grid was never known (`ptyCols == 0 || ptyRows == 0`) and no owner exists becomes the owner and sets the target (a fresh session adopts its first tab's fit; the many test helpers that set a first grid with ResizeClient keep working).
  2. Claim (`ClaimGrid`): store the size, `owner = sub`, target = that size, apply.
  3. Typing claims: 10-06 (not here).
  4. Never claim: join, replay, reconnect, output, and every plain report.
  5. `Unsubscribe(owner)` clears the owner under `mu` only; the target and the grid stay (D-01 freeze).
  6. Read-only subs (`sub.ReadOnly`) are ignored by both calls, in the hub as well as in the pumps (defense in depth, as VIEW-02 was). CONTEXT's safety paragraph says a guest has write access; the code also supports `read`-only caps (webserver/server.go derives `readonly` from the cap), and those must never move the shell's size.
  7. Frozen hub: record owner, size and target and return; `unfreeze` already re-runs `applyGridLocked`, so a claim lands at Thaw (a report during a freeze sets no target, so Thaw never applies a report).
  8. Clamp at intake for both calls: exported `MinGridCols = 20`, `MaxGridCols = 500`, `MinGridRows = 5`, `MaxGridRows = 200`; `cols <= 0 || rows <= 0` is ignored. Today a local viewer can ask for 65535x65535 and `resizeLiveEmulator` allocates an emulator of that size; with web claims allowed this must be bounded.
  - `applyGridLocked(why string)`: moves the PTY to the target (`wantCols, wantRows`) when it is set and differs; it never reads a sub's current reported size; the rest (needResize, broadcastResize to all subs, `resizeLiveEmulator(pc, pr, oldCols > 0 && oldRows > 0)`, resizeFn, unlocking `mu` before any IO) stays as is (Research Pitfall 8 lock order: gridMu then mu). Append ` conn=%d why=%s` (why is `bootstrap`, `claim` or `thaw`; 10-06 adds `input`) to the end of the existing `viewer-diag: grid session=%s %dx%d -> %dx%d by=%s client=%q` line, so `daemon_log_test.go` still matches its substrings and the VM checks can grep owner changes.
  - Implementation shape: Research "Hub grid owner" code example (`sizeClient(sub, cols, rows, claim)` behind `ResizeClient` and `ClaimGrid`), except that a plain report returns right after storing the size unless the bootstrap fired: the example's unconditional `applyGridLocked` at the end would let an owner's report move the grid.
  - **Chesterton's Fence, written into the new comments:** the VIEW-02 origin gate existed so a web guest could not drive or DoS the PTY grid (T-157-01); it is replaced by the write-cap gate, the clamp, and "reports never move a known grid". D-02 min-among-local existed so every host viewer saw all output; the user's decision replaces it (the viewer you use sets the size; the others scale).
  - `shortcut:` comment beside rule 4 (CONTEXT "Accepted limits"): a relaunched GUI shows the current grid, scaled, until its user types, zooms or resizes.
- **Pumps.** Both MsgResize2 cases call ParseResize and then ClaimGrid or ResizeClient, skipping read-only viewers. The share pump keeps logging the first resize per connection only (CR-01: any link holder can send resize frames at line rate) but with true wording: `viewer-diag: web resize session=%s conn=%d cols=%d rows=%d claim=%t`; the `resizes=` total in the input total line stays. Its VIEW-02 comment block is rewritten for INPT-06.
- **Settle window removal (after-research row; Research "The Phase 9 settle window: remove it").** Why it existed (09-07-FIX2.md): after a handoff, viewers rejoining one by one let min-among-local grow then shrink the imported grid, each change bumping geomEnd so later resumes were full replays. Why it can go: under the owner model a join or plain report never changes a known grid, and an imported hub has `ptyCols > 0`, so the bootstrap cannot fire. Delete `settleCols`, `settleRows`, `settleTimer`, `handoffSettle`, `endSettle`, the timer arm in `Start` (Start keeps `startOnce` and `go h.Run()`), the stop in `Shutdown`, and the assignment in NewHubFromState; replace them with a short comment at Start saying why no window is needed (the comment must not name the removed identifiers; Task 3's gate counts them in comments too). Phase 9's V-02 is re-run in the VMs by 10-07.
- **Rejoin test (Research).** Rename `settleHub` to `importedHub` (same fixture: imported 85x29 with `geomEnd > 0`). `TestHub_HandoffRejoinKeepsGrid`: the 100x30 attach then the 85x29 GUI tab join at the ring end and report; both get `ReplayDelta`, no grid frame, geomEnd unchanged, resizeFn never called; then `ClaimGrid` by the 100x30 viewer moves the grid to 100x30 with one resizeFn call and one grid frame to each viewer. `TestHub_HandoffFrozenClaimAppliedOnThaw` replaces the settle-skips-frozen test: a claim on the frozen imported hub calls no resizeFn and broadcasts nothing; Thaw applies it once.
- **Join push guard (Research Pattern 6, "Server guard").** `Hub.GridKnown()` (`ptyCols > 0 && ptyRows > 0`). The local relay pushes its join grid frame only when the grid is known, because `Cols()/Rows()` return the 220x50 fallback for a never-sized hub and a local tab that follows the server grid (10-05) would flash 220x50 on every new session. The share server keeps today's push (web guests keep the fallback, unchanged).
