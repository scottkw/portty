<objective>
Home (viewing) daemon side of DVWR-01: hold the peer's standing desktop token in memory, fetch it on demand from the 21-01 cap route, and open a loopback WebSocket proxy that lets the Wails web view reach the peer's /desktop/ws without ever seeing the token.

Purpose: the web view can only reach 127.0.0.1; this is the same pattern terminal peer tabs use, with the differences the desktop needs (keyed by host, status-mapped closes, one token refresh on rejection).
Output: store, two daemon routes, the proxy, client methods, tests including an in-process end-to-end test against a real office share server.
</objective>

## Decisions implemented

CONTEXT [Proxy] (GET /api/relay/remote-desktop/{host}/ws twin of handleRemoteSessionWS; signalling only; media goes UDP straight from the web view), [Proxy] store (sibling of RemoteCapStore keyed by host, memory only, no-disk grep test, refreshed through POST /peers/desktop on every connect), [Binding] (POST /peers/desktop twin of POST /peers/connect). Research Pattern 3, Pattern 4, Finding 8, Pitfall 5, Pitfall 6.

Planner notes (reversible, both ends ship in one binary):
- The one automatic token refresh happens in the proxy on a 401 from the peer, so Phase 19's client, which treats 4401 as final, shows the Refused card only after a fresh token also failed (UI-SPEC: "one automatic key re-fetch then the Refused card").
- 4403 is not a Phase 19 client code, so the client classifies it through its check hook, which in the app asks ConnectPeerDesktop and gets forbidden (21-05 connectVerdict).
- Both legs keep coder/websocket's 32768-byte default read limit: Phase 19 offers are about 5 KB and Phase 20 sizes clipboard frames at no more than 30000 bytes for exactly this limit.
