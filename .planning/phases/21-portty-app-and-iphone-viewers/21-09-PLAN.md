## Decisions implemented

CONTEXT control mode (every Portty menu chord goes to the remote Mac while on; the exits; release-all on every exit; no event tap), Cmd+V decision (home clipboard plain text through Phase 20's paste message, then the key), [Control] (the web view's key events go through Phase 20's key message unchanged; control mode only removes local interception), post-research (page-level first, a probe decides, fallbacks blank in place then rebuild; release chord Ctrl+Option+Cmd+Return; Cmd+V keeps the accepted decision in the app while browsers follow Phase 20's plain key). UI-SPEC Surface 3. Research Pattern 1, Pattern 2, Pitfall 1, Pitfall 2.

Planner notes:
- UI-SPEC refinement of the accepted Cmd+V decision (marked [default], adopted): when the home text equals the text last sent in this tab, Cmd+V sends only the key, so "copy on the Mac, then paste on the Mac" keeps working after a first paste; concealed, over 1 MB or failed sends nothing and no key, failing closed. The browser viewer keeps Phase 20's ruling (a typed Cmd+V there stays a plain key).
- Planner discretion (reversible): a refused home clipboard read (ReadDenied, or the bridge erroring) fails closed with "Couldn't send to the Mac. Try again." rather than sending a plain key, because pasting the Mac's own older clipboard instead of what the user copied would be a silent surprise.
- The V tap after a paste uses the modifier mask of the user's keydown, so Cmd already held on the remote (forwarded at its keydown) stays held and no extra Meta up is sent.
