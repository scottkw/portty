# Phase 21 — UI Design Contract

> Visual and interaction contract for Phase 21 (Portty App and iPhone Viewers: DVWR-01, DVWR-03, DVWR-04). Generated by gsd-ui-researcher in auto mode (the user delegated every product and UX choice), to be verified by gsd-ui-checker. Phase 21 **reuses** the Phase 19 `/desktop/` viewer and, where marked, the Phase 20 control layer. It adds no design system, no token and no npm package.

**Sources, in priority order:**
1. `21-CONTEXT.md`: the locked decisions (header-driven discovery, the cap route, Local Network prompt accepted on first open, control mode owns every Cmd chord until it ends, one release chord, Cmd+V pastes the home clipboard in the app) and the "Claude's Discretion" list that fixes the surfaces: a Desktop row first in each peer group, one tab per peer, the browser viewer's state wording, a thin accent ring plus a toolbar label, the Local Network line, the iPhone gesture set, 1x to 5x pinch, the soft keyboard with a key bar, the Tap to start overlay, full-bleed phone layout, plus the post-research items (the release chord; it shipped as Ctrl+Option+Cmd+Shift+Return because the system takes Ctrl+Option+Cmd+Return inside the app, 21-02 RELEASE_CHORD and c292ab30, hidden-window disconnect after about 2 minutes, no Wake Lock).
2. `19-UI-SPEC.md` (approved, and **built**: the real code is the source of truth) and the code it produced: `frontend/src/components/DesktopView.tsx` (state cards, chips, `CARDS` copy table, `videoContentRect`), `frontend/src/lib/desktopClient.ts` (injectable `transport`, `check`, `beforeRedial`, `wake('external')`, `RECONNECT`), and the `.desktop-*` CSS block in `frontend/src/style.css`. Inherited unchanged unless a section below says it supersedes one.
3. `20-UI-SPEC.md` (approved, **planned, not built**: `lib/desktopInput.ts`, `DesktopControlBar.tsx` and `DesktopSendKeysMenu.tsx` do not exist yet). Everything taken from it is marked **(assumes Phase 20 as planned)** and collected in "Dependencies on Phase 20" below.
4. `21-RESEARCH.md`: Pattern 1 (page-level key capture, probe first), Pattern 2 (Cmd-held keys are taps), Pattern 6 (mount model, hidden video), Pattern 7 to 9 (iPhone gestures, resume, soft keyboard), Pitfalls 7, 9, 11, 12, 14, and Open Questions 1 to 6 (all settled by the post-research CONTEXT items).
5. Existing app code, scanned 2026-11-26: `components/Sidebar.tsx` (peer groups, `PeerDot`, `.sidebar__muted`, `PEER_NOTHING_SHARED`), `components/TabBar.tsx` (`Tab.type`, `toolbar-chip` "On <host>", `peerTabParts`), `lib/sidebarPeers.ts`, `lib/tabs.ts`, `components/KeyBar.tsx` and the `.keybar*` CSS (Phase 14 look and firing rule), `lib/phoneQuery.ts` (`PHONE_QUERY`), `lib/visualViewportInset.ts`, `lib/touchScrollHandler.ts` (8 px tap threshold), `.toolbar-chip`, `.tab-bar` (52 px) and the token blocks in `style.css`.
6. Project memories: macOS-native look (system font, system accent, light and dark follow the system live), radical simplicity, rock-solid (nobody can get in to fix the office Mac: no key is ever left held and every failure is visible in words), colorblind user (color is never the only signal), no developer paths or real tailnet addresses in committed text.

**Scope.** Five surfaces: (1) the Desktop row in the sidebar; (2) the Desktop tab in the Portty app, including its tab-bar entry, states, the Local Network state and the hidden-window rule; (3) control mode, its ring, its toolbar label and its keyboard rules; (4) the iPhone viewer (layout, bottom bar, key bar, gestures, zoom, soft keyboard, Tap to start, resume); (5) the Help text. Out of scope and not designed here: the input, Send Keys, clipboard and display or window switch protocol and their DesktopView controls (Phase 20, upstream); click-to-share for other people (Phase 22); audio and unmute, adaptive quality, unlock (Phase 23); direct-touch mode and three-finger gestures on iPhone (deferred). Every item marked **[default]** is a detail CONTEXT did not fix; it is the simplest choice that fits the house style, and the planner may adjust it without asking.

**What "phone" means below:** the media query `(pointer: coarse) and (hover: none)`, the same as Phases 14, 19 and 20 (`lib/phoneQuery.ts`). Never the user agent. **"The app"** means the Portty Wails window (pointer UI, never matches the phone query). **"The Mac"** in copy means the remote Mac being shown; **"this Mac"** is never used for the viewer in this phase.

| `--space-xs` | 4px | Gap between the two lines of the toolbar label, phone bar padding top and bottom |

| `--space-md` | 12px | **Inherited exception, not a new value:** the horizontal padding of surfaces that already exist and are built (`.toolbar-chip`, `.button`, `.context-menu__item`, the Phase 19 chip). Used here only for the toolbar label, phone menu items and card buttons so they match them |
| `--space-lg` | 16px | Gap between card body and its first button (existing `.desktop-card__action` margin) |
| `--space-xl` | 24px | Card padding and side margin (inherited from Phase 19) |
| `--space-2xl` | 32px | not used (the pan margin on the phone is a dimension, below) |
| `--space-3xl` | 48px | not used |

### Component dimensions

| Element | Size |
|---------|------|
| Sidebar Desktop row | The existing `.sidebar__row`: 28px tall, padding `0 8px` (`0 8px 0 32px` nested), icon 16px, gap 8px, 13px text. The muted line under it is the existing `.sidebar__muted` (padding `4px 8px 4px 32px`, 12px) |
| Desktop tab entry | The existing peer tab, unchanged metrics |
| Desktop tab stage | Fills the content area under the 52px tab bar edge to edge, no padding (the safe-area insets are 0 in the app), opaque `--color-viewer-bg` |
| Capture ring | 2px inset ring around the stage (Phase 20 metric, same element) **(assumes Phase 20 as planned)** |
| Toolbar label (`.toolbar-chip--desktop`) | Fixed `width: 232px`, `height: 36px`, padding `0 12px`, radius 8px (`--hub-radius-sm`), two lines (line 1 18px, line 2 16px, vertically centered), `flex-shrink: 0`, in the existing chip slot at the end of the tab bar (centered vertically in the 52px bar). The host name on line 1 truncates with an end ellipsis; line 2 never truncates |
| Card buttons in the app | `min-height: 28px` (pointer UI, the Phase 20 bar metric), `padding: 0 12px`, radius 6px. Stacked, full card width, 8px gap. On the phone the Phase 19 `min-height: 44px` stays |
| Phone bottom bar and key bar | The Phase 14 `.keybar` box exactly: `box-sizing: content-box; height: 44px; padding: 4px env(safe-area-inset-right) calc(4px + env(safe-area-inset-bottom)) env(safe-area-inset-left)`, `--color-toolbar` background, 1px `--color-separator` on top. With the keyboard up the bottom inset is 0 (the existing `.keybar--kb-up`) |
| Phone bar items (bottom bar) | Equal flex, `min-width: 44px`, `height: 44px`, the visible pill inset 2px (the existing `.keybar__key::before`) |
| Phone key bar items | Equal flex, **`min-width: 36px`**, `height: 44px`. Ten items fit at 360pt and wider with no scrolling (see Exceptions) |
| Phone menus (Send Keys, display picker) | The Phase 20 `.context-menu` look opened upward from the bar item, `max-height: min(50vh, 360px)`, items **44px tall** (not the 24px pointer height), `padding: 0 12px`, `--shadow-popover` |
| Pointer ripple (long-press and drag start) | 24px ring, 2px stroke |
| Zoom | 1x to 5x. The view pans so the pointer stays at least 32px inside the stage edge |
| Hidden keyboard input | 1 x 1px, `opacity: 0`, `font-size: 16px`, inside the stage at its bottom edge |

Exceptions:
- **12px (`--space-md`) is outside the 4, 8, 16, 24, 32, 48, 64 set on purpose.** It is the house mid step set in Phases 4 and 14 and already built into `.toolbar-chip`, `.button`, `.context-menu__item` and the Phase 19 and 20 chips. Moving it to 8 or 16 here would make the new label, phone menu items and card buttons differ from the shipped Phase 19 and 20 UI beside them, which breaks macOS-native consistency. No new 12px use is introduced beyond matching those surfaces; all other padding in this phase is on the standard set.
- The 1 x 1px hidden keyboard input is a content size, not spacing: it must stay a real, focusable element (not `display: none`), and a size this small keeps it off the picture.
- The key bar's 36px minimum item width is below the 44px tap-target rule on purpose: the required ten keys (Esc, Tab, Ctrl, Opt, Cmd, four arrows, Send Keys) do not fit at 44px in 393pt (440px needed). Each item is still 44px tall and about 39px wide on an iPhone 15, and the bar never scrolls, so a key is never offscreen. The Phase 14 bar (eight keys) keeps its 44px minimum.
- The toolbar label is 36px tall in a 52px bar; the 232px width is fixed so entering or leaving control mode never reflows the tab strip.
- 1px (separator), 2px (ring, ripple stroke, and the existing `.keybar` pill inset) and 3px (focus ring) are stroke widths. 232px, 36px, 24px and 32px are dimensions, all multiples of 4.
- Safe-area insets come from the device and are not on the 4px grid.

## Typography

No new roles and no new size. This phase declares **3 sizes (12, 13, 17)** and 2 weights (400, 600). The 11px Label size exists in the house scale but nothing here uses it, so it is not declared. 12 and 13 are intentional, not an accident: they are the shipped macOS-native UI sizes (sidebar rows, tab bar, chips and buttons are 13px with 12px captions), and the 17px Display size is the Phase 19 card heading. Keeping them means the new label, row and cards match the built UI beside them.

| Role | Size | Weight | Line Height | Used in this phase |
|------|------|--------|-------------|--------------------|
| Caption | 12px | 400 | 16px | The muted sidebar line, toolbar label line 2, card bodies' secondary text, phone Fit/menu captions |
| Body | 13px | 400 / 600 | 18px | Sidebar row label (400), toolbar label line 1 (idle 400, controlling 600), phone bar and key bar labels (600, the existing `.keybar__key`), card bodies (400), card buttons (400), chip text (400) |
| Display | 17px | 600 | 22px | Card headings only (the existing `.desktop-card__heading`), including the Local Network heading |

Keys and shortcuts in copy are text ("Cmd+Q", "Ctrl+Option+Cmd+Shift+Return"), never a monospace face and never glyph chords. Phone key labels are the words Esc, Tab, Ctrl, Opt and Cmd.

## Color

All colors are existing tokens with light and dark values, repainting live with the system appearance. No token is added.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-viewer-bg` (`#000000`, both appearances) behind the video; `--color-window` and the vibrancy sidebar around it | The Desktop tab stage is **opaque** viewer-bg: the Portty window is transparent and translucent (`WebviewIsTransparent`, `WindowIsTranslucent`), so the letterbox must paint its own black or the desktop wallpaper would show through |
| Secondary (30%) | `--color-toolbar` (tab bar, phone bars), `--color-chip` (idle toolbar label), `--color-popover` with `--color-control-border` and `--shadow-popover` (chips, cards, phone menus), `--color-control-hover` (sidebar row hover, existing), `--color-separator` | Every overlay that carries text |
| Accent (10%) | `--color-selection-fill` (text on it `--color-on-accent`) | Reserved list below |
| Destructive | `--color-destructive` | Not used. Nothing in this phase is destructive-styled (Lock Screen keeps its Phase 20 default-button fill) |

Text colors: `--color-text`, `--color-text-secondary` (muted sidebar row, line 2 of the idle label), `--color-on-accent` on accent fills. Disabled phone items use `--opacity-disabled` with `aria-disabled="true"`, never `disabled`.

**No text is ever drawn directly on the video or on `--color-viewer-bg`** (Phase 19 rule, kept). In the app every word sits on the tab bar, a chip or a card; on the phone on a chip, a card or a bar.

Accent reserved for (nothing else):
- the current Desktop row in the sidebar (the existing `aria-current="page"` fill, same as any session row);
- the **capture ring** around the Desktop tab stage while control mode is on (Phase 20's ring, one element);
- the **toolbar label fill** while control mode is on (`.toolbar-chip--desktop[data-control="on"]`);
- the **Tap to Start** and **Click to Start** button fill (Phase 19 rule);
- an **armed** one-shot modifier on the phone key bar (the existing `.keybar__key--armed` fill with its corner dot);
- the focused or hovered row in a Phase 20 menu (the existing `.context-menu__item:focus` fill).

Not accent: the idle toolbar label, muted sidebar rows, Open System Settings, Open in Browser, Reconnect (all `.button--secondary`), bottom bar items, key bar keys that are not armed, chips, cards.

Color is never the only signal (the user is colorblind): the ring has the label with words beside it, the label always spells its state, a muted sidebar row always has its state line, an armed modifier has the corner dot plus `aria-pressed`, and every card and chip pairs an icon with words.

## Surface 1: Sidebar Desktop row (DVWR-01)

### Placement

```
OTHER MACS                                      (existing group header)
 ▭ office-air                              ●    (existing host row, reachable dot)
     ▭ Desktop                             ●    ← new, first row, peer's PeerDot at the end
       Display asleep                            ← muted line, only after an attempt found a non-ready state
     > build                               ●    (existing session rows, unchanged)
     > logs                                ●
```

The row is the first `li` in the peer's nested list, above that peer's sessions. It is a `button.sidebar__row` exactly like a session row: leading `ComputerDesktopIcon` (`.sidebar__row-icon`), `.sidebar__row-name` **Desktop**, trailing `PeerDot` (`hostname={g.key}`, the same dot the peer's session rows and tabs use). It has no context menu and no inline rename.

| Rule | Contract |
|------|----------|
| Shown when | The peer group is reachable **and** the peer's meta response carried `X-Portty-Desktop: always` (`peer.desktop === true`). A group that is not reachable shows only the existing "Can't reach this Mac" line, never a Desktop row |
| Hidden when | The header is absent (always-available is off, or a v1.x peer). The row disappears at the next poll after the peer turns the setting off |
| Order | First in the group, always, even when the peer shares no sessions |
| "Nothing shared" | `PEER_NOTHING_SHARED` shows only when the peer has **neither** sessions **nor** a desktop |
| Current | `aria-current="page"` (the accent pill) while that peer's Desktop tab is the active tab. A Desktop tab open but not active does not mark the row |
| Click | No Desktop tab for this peer: opens one at once (it shows Connecting while `ConnectPeerDesktop` runs). A tab is already open: focuses it. Never two tabs for one peer (tab id `desktop:<fullhost>`) |
| Keyboard | Tab to it, Enter or Space opens or focuses (a real `<button>`). No other key |
| Hover and focus | The existing row hover fill and 3px focus ring |
| Accessible name | "Desktop", inside the peer's list that is already labelled by the host name, so a screen reader reads "<host>, Desktop" like it reads "<host>, <session>" |

### Muted state (CONTEXT Claude's Discretion)

After an attempt, or while a tab is open, the sidebar remembers the last state that peer's desktop reported. When it is anything other than ready or streaming, the row is muted and a line under it says why:

| Last state (from the viewer's state message) | Muted line (`.sidebar__muted`, Caption) | Row |
|-----------------------------------------------|------------------------------------------|-----|
| Waiting for approval at the Mac | **Waiting for approval at the Mac** | muted |
| Display asleep | **Display asleep** | muted |
| Locked | **Locked** | muted |
| Needs permission **[default]** | **Needs permission** | muted |
| Desktop paused **[default]** | **Desktop paused** | muted |
| Ready, Streaming, or no attempt yet | no line | normal |

- Muted means the label and icon use `--color-text-secondary` and the line sits directly under the row. It does **not** disable the row: it stays a working button, because the state may have changed and a click is the retest. Locked in particular is still viewable.
- The state words are the browser viewer's (Phase 19) so the wording is the same everywhere. A **line of text carries the state, never the colour**, the same rule the sidebar already follows for "Can't reach this Mac".
- The row has `aria-describedby` pointing at the muted line, so the reason is read with the name.
- It clears when a later state message for that peer reports ready or streaming, or when the header disappears. It is in memory only: nothing is stored, and a launch starts with no muted rows. The planner may add a staleness timeout **[default]**.
- The Desktop tab does **not** drive the sidebar's amber "Reconnecting" dot (`reconnectingHost` is a single string shared with terminal peer tabs, research Pattern 6). The tab's own Reconnecting chip is the signal.

## Surface 2: Desktop tab (DVWR-01)

### The tab-bar entry

| Part | Contract |
|------|----------|
| Type and id | `Tab.type = 'desktop'`, id and `sessionId` `desktop:<fullhost>`, `peerHost` the full host, no token on the tab |
| Name | Stored as `<host> › Desktop`; displayed as **Desktop** then a secondary ` · <host>` (the same split a peer terminal tab uses, `peerTabParts` extended for this type) |
| Chrome | Leading `ComputerDesktopIcon` (`.tab__remote-icon`) in place of the peer terminal tab's globe, then the name, then the peer's `PeerDot`, then the close button. Tooltip: **Desktop · <host>**. The close button's name is **Close Desktop · <host>** |
| Menu | Right-click or the menu key opens a menu with **Close Tab** only (a non-local tab, as `TabBar` already does) |
| Rename | Not allowed (double-click does nothing, as for other peer tabs) |
| Close | Disconnects at once, sends release-all first if control mode is on, and removes the tab. No confirmation: it is not destructive and the row reopens it |

### The tab body

**Visual anchor:** the picture. The stage is one black field with the remote desktop letterboxed in it; everything else (the tab bar label, the Phase 20 bar, chips, cards) is quiet chrome around or over a small part of it, and the only accent in the stage is the 2px ring while control mode is on.

```
┌ tab bar (52px) ─────────────────────────────────────────────────────────────────────────┐
│ [Desktop · office-air ● ×] [build · office-air ●] [+]            [ On office-air          ]│
│                                                                    Click the picture to … │ ← toolbar label
├──────────────────────────────────────────────────────────────────────────────────────────┤
│  stage: opaque black, the picture letterboxed, nothing drawn on it                       │
│  (Phase 20 bar floats top-center, chips below it, cards centered)                        │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

| Rule | Contract |
|------|----------|
| Viewer | `DesktopView` reused (one `<video aria-label="Mac desktop">`, never replaced, `object-fit: contain`, no CSS transform, zoom, `image-rendering` or size attributes). The picture is fitted, letterboxed and Retina-sharp exactly as in the browser viewer (Phase 19 Sharpness rule) |
| Background | `--color-viewer-bg`, opaque, painted by the tab itself |
| Padding | none; no safe-area padding in the app |
| One tab per peer | Clicking the row again focuses the open tab |
| Connection lifetime | The tab stays connected while open, **including when another tab is in front**. Closing the tab disconnects. A tab behind another tab keeps decoding (see "Hidden behind another tab") |
| Window hidden | After the Portty window has been hidden (`document.visibilityState === 'hidden'`: closed to the Dock, minimized or occluded) for about **2 minutes**, the tab disconnects so the office display can sleep. When the window is shown again the tab reconnects: the Phase 19 **Reconnecting…** chip over the frozen last frame, then the picture. No new copy, no card. Briefly hiding the window (under 2 minutes) changes nothing |
| Hidden behind another tab | The panel stays mounted and connected. Hide it with `opacity: 0; pointer-events: none; position: absolute; inset: 0` and `inert`, **not** `display: none`, so the `<video>` keeps decoding (research Pattern 6; the VM row checks the frame counter after a tab round trip) |
| Light and dark | The stage is black in both. The label, chips and cards use their tokens and repaint live |
| Not a terminal | The panel loop must never mount a `TerminalPanel` for this type; it gets its own always-mounted branch |
| Phase 20 control bar | Rendered as Phase 20 specifies for a bar-capable viewer **(assumes Phase 20 as planned)**. In the app its **Full Screen** item is not rendered (the DOM fullscreen API is not offered in the web view, so Phase 20's own `document.fullscreenEnabled` rule hides it; the window's green button and View menu do the job). Every other item is as Phase 20 |

### Toolbar label (control state, always visible when the Desktop tab is active)

The label lives in the tab bar's existing trailing chip slot (where a peer terminal tab shows "On <host>" and a local tab shows Share). It is a `.toolbar-chip.toolbar-chip--desktop`, `role="status"` `aria-live="polite"`, so a change is announced. Two lines, fixed size (see dimensions). It is the persistent answer to "who owns my keyboard?" and the place the release chord is always spelled out. It is shown only while the Desktop tab is the active tab (like the "On <host>" chip).

| State | Line 1 (Body 13) | Line 2 (Caption 12) | Fill |
|-------|------------------|---------------------|------|
| Control mode on | **Controlling <host>** (600) | **Release: Ctrl+Option+Cmd+Shift+Return** | `--color-selection-fill`, text `--color-on-accent` |
| Streaming, keyboard not captured, control allowed | **On <host>** (400) | **Click the picture to control** | `--color-chip`, line 1 `--color-text`, line 2 `--color-text-secondary` |
| Locked, control not on | **On <host>** | **Locked** | `--color-chip` |
| View Only chosen in the Phase 20 bar | **On <host>** | **View only** | `--color-chip` |
| Connecting, Reconnecting, Local Network, refused, unreachable, off, or any state card | **On <host>** | **Not connected** | `--color-chip` |

- The label reflects who owns the keyboard, not whether control is possible: while the Mac is locked and the keyboard is still captured the label stays **Controlling <host>** (Phase 20's paused-with-focus case); the Locked chip says why nothing happens.
- Tooltip (`title`) on the label, and `aria-describedby` text: **While you control <host>, every key goes to that Mac, including Cmd+Q, Cmd+W and Cmd+C. Press Ctrl+Option+Cmd+Shift+Return to get Portty's shortcuts back.**
- `<host>` is the short host name (first DNS label, `shortHost`), set as text, never markup. Long names end with an ellipsis on line 1 only.
- Phase 20's two capture notice chips (**Typing goes to the Mac** and **Typing stays on this device**) are **not shown in the app**: this label is the persistent signal and a chip would repeat it. Phase 20's other notices (copy, paste, surface, held keys) stay. **(assumes Phase 20 as planned; DesktopView needs one prop to turn the two capture notices off.)**

### States in the app tab

Only the **words that mention a link, a page or a browser** change, because the app has none. The table is the whole difference.

| State | Where | Icon | Heading | Body | Action |
|-------|-------|------|---------|------|--------|
| Connecting (before the first frame) | Card, centered, no scrim | `ComputerDesktopIcon` | **Connecting…** | **Waiting for the first picture from the other Mac. If macOS asks to find devices on local networks, choose Allow.** | none |

## Surface 3: Control mode (DVWR-04)

Control mode **is** Phase 20's "Control, keyboard on" state, in the app: the stage has focus, the ring is on, every key goes to the Mac and the release chord is never forwarded **(assumes Phase 20 as planned)**. Phase 21 adds three things to it: Portty's own Cmd shortcuts are removed for its duration, the exits listed below, and the persistent label above. There is no separate control UI.

### Entering and leaving

| Event | Result |
|-------|--------|
| Click on the picture (the click is also forwarded, Phase 20) | Control mode on: ring on, label turns accent and reads **Controlling <host>**, Cmd chords go to the Mac |
| Tab or Enter onto the stage | Same |
| **Ctrl+Option+Cmd+Shift+Return** | Off. Never forwarded to the Mac. Focus moves to the Phase 20 Control segment and reveals the bar. The browser viewer names Ctrl+Option+Cmd+Return; the app adds Shift because the system takes the unshifted chord in the app (21-02 RELEASE_CHORD). Detected on physical codes (Control, Alt, Meta, Enter) with Shift ignored, so the same handler accepts both, before any Ctrl and Cmd swap |
| Click anywhere outside the picture (sidebar, tab bar, bar, a menu, a dialog, the label) | Off |
| Switch to another tab (click, or a tab-switch shortcut cannot fire because Cmd chords are forwarded) | Off |
| Portty stops being the active app (Cmd+Tab, clicking another app, Mission Control) or the window is hidden | Off. Returning to Portty does **not** restore it; one click does |
| The stream is not connected (Reconnecting, unreachable, closed) | Off. Portty's shortcuts return at once, so **Cmd+W closes a dead tab** |
| The Mac locks | **Stays on** (still connected; Phase 20 pauses input and keeps focus). The Locked chip explains; the chord or a click gives the keyboard back |
| Closing the tab | Release-all, then off |

**Every exit sends release-all first** (DCTL-02), so no remote key or button stays held on the unattended Mac. A "Held keys were released" notice appears only if something was held and the cause was not the user's own click or chord (Phase 20 rule).

### What goes to the Mac

| Rule | Contract |
|------|----------|
| Cmd chords | While control mode is on, every key chord Portty's menu owns goes to the Mac and **not** to Portty: Cmd+Q, Cmd+W, Cmd+C, Cmd+V, Cmd+X, Cmd+Z, Cmd+A, Cmd+T, Cmd+H, Cmd+M, Cmd+comma, Ctrl+Cmd+S and the rest. Cmd+W closes the remote window, Cmd+Q quits the remote app, Cmd+C copies on the remote Mac only |
| How | The first mechanism is page-level: the stage's key handler prevents the default for every forwarded key (nothing local changes, nothing can be left switched). If the Wave 0 VM probe shows a chord still reaches the menu, the fallbacks are, in order, blanking the menu key equivalents in place and then rebuilding the menu (CONTEXT, post-research). The fallbacks would blank the key hints shown in Portty's menus while control mode is on and restore them on exit; nothing else visible changes |
| Held-key safety | A non-modifier key pressed while Cmd is held is sent as a tap (press and release together), because macOS never delivers its key-up (research Pattern 2). The release-all on exit is the backstop **(assumes Phase 20 as planned: the Meta-chord tap rule lives in `lib/desktopInput.ts`)** |
| Stays with the viewer Mac | Anything the OS owns: Cmd+Tab, Cmd+Space, Cmd+Shift+3/4/5, Ctrl+Cmd+Q and other system shortcuts. Cmd+Tab and Cmd+Space reach the remote Mac only through Send Keys. There is no event tap and no new permission on the viewer Mac |
| Portty's own shortcuts while on | Off (new tab, tab switching, Settings, Hide, Quit all go to the Mac). The mouse still works for everything in Portty. The label spells the way back |

### Cmd+V in control mode (CONTEXT: the home clipboard is the paste)

A typed Cmd+V is the explicit paste action. Portty sends the viewer clipboard's **plain text** (never an item marked concealed) through Phase 20's paste message and then the key, so the text lands in the app the user is typing into **(assumes Phase 20 as planned)**.

| Home clipboard holds | Result | Notice (Phase 20 notice chip) |
|----------------------|--------|-------------------------------|
| Plain text, 1 MB or less, **different from the text last sent in this tab** | The text is sent, then Cmd+V is sent as a tap | none (the text appearing is the confirmation) |
| The same text as the last send in this tab **[default]** | Cmd+V is sent as a plain key only. This keeps "copy on the Mac, then paste on the Mac" working after a first paste | none |
| Nothing text (empty, an image, files) | Cmd+V is sent as a plain key only (the Mac pastes its own clipboard) | none |
| A concealed item (password manager) | **Nothing is sent, and the key is not sent.** Fails closed | **Your clipboard holds a hidden item (password manager); not sent** (`EyeSlashIcon`, 5 s) |
| Text over 1 MB | Nothing is sent, and the key is not sent | **Your clipboard text is too large to send (limit 1 MB)** (Phase 20 string, 5 s) |
| The send fails (channel error) | The key is not sent | **Couldn't send to the Mac. Try again.** (Phase 20 string, `role="alert"`) |

Cmd+C and every other chord are plain keys; **Cmd+C never copies to the viewer Mac.** Text comes back only through Phase 20's explicit **Copy from Mac** action. The browser viewer keeps Phase 20's plain Cmd+V (no sync), and the iPhone has no Cmd+V paste.

### The ring

Phase 20's 2px `--color-selection-fill` ring around the stage, one overlay element with `pointer-events: none`, appearing and disappearing at once (no animation) **(assumes Phase 20 as planned)**. It is on exactly while control mode is on. It is never drawn on the `<video>`.

Standard trackpad vocabulary on the stage only. Thresholds are defaults the planner may tune on the device (M-rows):

| Gesture | Result | Defaults |
|---------|--------|----------|
| One-finger drag | Moves the pointer **relatively**. | Two-finger drag | Scrolls the Mac: the content moves with the fingers, as on a Mac trackpad with natural scrolling. Pixel wheel deltas (Phase 20 wheel message). | Two-finger double-tap | Resets zoom to fit (1x) | Two two-finger taps within 300 ms |

## Decisions Made Here (Claude's discretion; the user may override)

| Decision | Choice | Why |
|----------|--------|-----|
| Where the control label lives | The tab bar's existing trailing chip slot, as a fixed-width two-line `.toolbar-chip--desktop`, not an overlay on the picture and not a new strip | The picture never carries text (Phase 19), a strip would cost picture height, the slot already carries "On <host>" for peer tabs, and a fixed width means entering or leaving control never reflows the tabs |
| Label content | Always shows the peer; line 2 changes with who owns the keyboard (**Click the picture to control** / **Release: Ctrl+Option+Cmd+Shift+Return** / **Locked** / **View only** / **Not connected**) | The user must always see who owns the keyboard and the way out; one element, five fixed strings |
| Label and ring together | Both accent while control is on | The ring is the quick glance, the label is the words (colorblind rule) |
| Capture notices in the app | Phase 20's two capture notice chips are not shown in the app | The persistent label already says it; chips would repeat it |
| Control mode versus Phase 20 capture | The same state, plus Cmd-chord interception, extra exits and the label | One state to learn and test; no second ring or second chord |
| Locked while controlling | Control mode stays on | The stream is connected and Phase 20 pauses input; the chord or a click always exits. CONTEXT ends it only when not connected |
| Cmd+V refinement | Send the home text unless it equals the last text sent in this tab; skip with no text; block the key on concealed, oversize or failure | Without the first rule a Cmd+V would overwrite the Mac's clipboard every time and break copy then paste on the Mac. The block rules fail closed. **[default]**, flagged for the user: if they want an unconditional send, delete the "same as last sent" row |
| Row glyph | `ComputerDesktopIcon`, per CONTEXT | No new icon; the host row above it uses the same glyph, so the word **Desktop** and the row's position carry the difference |
| Muted row | Stays a working button with a state line under it; extended to Needs permission and Desktop paused | The state may have changed and a click is the retest; the line, not the colour, carries the state |
| Muted memory | In memory only, cleared by the next ready state or the header going away | Nothing stored, nothing to go stale across launches |
| Desktop tab and the sidebar's amber dot | The Desktop tab does not drive it | The dot is one string shared with terminal tabs of the same host; the tab has its own Reconnecting chip |
| Local Network timeout | About 10 s of ICE `new` | Long enough for the prompt to be answered, short enough to show the fix |
| Local Network heading | The CONTEXT line verbatim as the heading, a how-to as the body | Keeps the exact approved wording and still tells the user the path |
| Open in Browser | Opened Go-side from the held key | The key never enters the web view, matching the decision that the web view URL never carries the token |
| Full Screen in the app | Not rendered | The DOM fullscreen API is not offered in the web view; the window's own full screen works with control mode |
| App card wording | Words that mention a link, page or browser are replaced (Connecting, Unreachable, Desktop off, Click to start); two new cards (Local Network, Refused) | The app has no link or page, and a wrong noun would send the user to the wrong fix |
| Hidden-window disconnect | `visibilityState` hidden for about 2 minutes, then Reconnecting… on return | CONTEXT post-research; no new copy |
| Hidden tab | `opacity: 0` and `inert`, not `display: none` | Research: keeps the `<video>` decoding |
| Opaque stage | The tab paints `--color-viewer-bg` itself | The Portty window is translucent; the letterbox must not show the wallpaper |
| iPhone bar model | One 44px slot: bottom bar while the keyboard is down, key bar while it is up | Two stacked bars would eat the picture; the Phase 14 key-bar slot already docks on the keyboard |
| iPhone keyboard dismiss | iOS's own ✓ Done | Phase 14 evidence (M-146): the form-assist bar appears for any web text field; no custom dismiss to build |
| Key bar width | 36px minimum, ten keys, no scrolling | The ten keys CONTEXT lists do not fit at 44px; a key offscreen is worse than a narrower one |
| Phone page zoom | Off in the stage; in-page 1x to 5x with a Fit control | Supersedes Phase 19's page pinch on the phone; the in-page zoom covers reading small text |
| Phone zoom reset | Reset on rotation | The coordinates change under it |
| Pointer ripple | A 24px ring on long-press and drag start only | The remote context menu takes a second to appear in the stream; the ring confirms the press at once, with no text on the picture |
| Phone clipboard | Not offered | Not in CONTEXT's iPhone list; one menu item can be added later with no layout change |
| First-use gesture hint | None; the gestures are in the README | The gestures are the standard trackpad set; cutting the chip and its storage key is the simpler choice |
| Help | README paragraphs plus the label and tooltip; no new in-app screen or menu item | Radical simplicity; the project site mirrors the README |
| Usage string | **Portty needs this to show your other Mac's desktop in a tab.** | Completes the macOS prompt's own title; no jargon |
