## Critical Issues

### CR-01: `build.sh --sign` ends with an `spctl --type install` assessment that rejects a correctly notarized .app

**File:** `build.sh:168`
**Issue:** Step 7 runs `spctl --assess --verbose=2 --type install "$APP"` under `set -e`. `--type install` is the installer-package context, not the app-execution context. I checked it against installed apps. For `/Applications/Firefox.app`, which is notarized and stapled, `spctl --assess --verbose=2 --type install` prints `rejected / source=Unnotarized Developer ID` and exits 3. `spctl -a -t exec -vv` on the same app prints `accepted / source=Notarized Developer ID` and exits 0. So a fully successful sign, notarize and staple run aborts at the last step with exit 3. The "macOS build signed and notarized" line is never printed, and `build/bin/portty-notarize.zip` is left behind because the `rm -f` cleanup is skipped. This phase added `verify-bundle.sh --notarized` with the correct `-t exec` check and the exact `source=Notarized Developer ID` match, which `release.yml` uses. `build.sh` was edited in this same function (steps 1-2) but still runs the old, wrong assessment. This only affects the local `--sign` path, not the CI release. It is still incorrect behaviour: the documented local signing flow cannot finish successfully, so I rate it a blocker.
**Fix:** Replace step 7 with the shared gate:
```bash
  # Step 7: Staple and Gatekeeper gate, the same one release.yml runs
  echo "==> Verifying notarization"
  bash "$(dirname "$0")/scripts/verify-bundle.sh" "$APP" --notarized

  rm -f "$ZIP"
```
Also move the `rm -f "$ZIP"` earlier (right after `notarytool submit`) or use a `trap` so a failed step does not leave the zip behind. Update `tests/build-script.test.sh` Section 10, which currently pins `spctl.*--assess` and would need to pin `verify-bundle.sh" "$APP" --notarized` instead.

## Warnings

### WR-01: The entitlements gate passes falsely when `jq` is not installed

**File:** `scripts/verify-bundle.sh:101-104`
**Issue:** `norm()` pipes into `jq`, and both `want` and `got` are captured with `2>&1`. If `jq` is absent, both strings become the identical shell error (`.../verify-bundle.sh: line 101: jq: command not found`). `[[ -n "$want" && "$got" == "$want" ]]` is then true, so the entitlements check reports success without comparing anything. I reproduced this with a PATH that has `plutil` and `codesign` but no `jq`: both variables hold the same error text and the check reaches the pass branch. Entitlements are one of the gates meant to protect the office Mac's grants. `jq` is a hard dependency that the script header does not mention, and nothing checks for it. GitHub's macOS runners ship `jq`, which is why CI does not hit this. A local `build.sh --sign` on a machine without `jq` would.
**Fix:** Fail closed on a missing dependency, and stop folding stderr into the compared values:
```bash
  command -v jq >/dev/null 2>&1 || fail "entitlements gate needs jq on PATH"
  norm() { plutil -convert json -o - - | jq -S .; }
  want="$(norm <"$ENTITLEMENTS" 2>/dev/null)"
  got="$(codesign -d --entitlements - --xml "$APP" 2>/dev/null | norm 2>/dev/null)"
  [[ -n "$want" && "$got" == "$want" ]] || fail "entitlements of the bundle differ from $ENTITLEMENTS"
```
Add `jq` to the header's dependency list, and add a fixture case with `jq` hidden from PATH.

### WR-02: Tests never discriminate the per-Mach-O signed gate or the `--notarized` branch

**File:** `tests/verify-bundle.test.sh:142-209` (fake codesign), `scripts/verify-bundle.sh:79-85,107-115`
**Issue:** The fake `codesign` answers every `-dvv` and `--verify` query identically, regardless of which path is asked about. So every `--signed` fixture case sees the main executable and the bundle with the same answer. No test has a nested Mach-O that is unsigned, lacks the runtime flag, or lacks a timestamp while the main executable is fine. The phase's central claim, that every Mach-O carries its own hardened-runtime signature and timestamp, is therefore not pinned. The per-file loop at lines 79-85 could be deleted and all 34 tests would still pass. The `--notarized` branch (`stapler validate`, `spctl` with `Notarized Developer ID`) has no test at all, not even with fake `xcrun` and `spctl` on PATH. The first time it runs is on a tag push. `release_workflow_test.go` only checks that the step ordering exists in the YAML.
**Fix:** Make the fake path-aware, for example a `FAKE_BAD_PATH_SUBSTR` variable under which `-dvv` and `--verify` degrade only when the path contains the substring. Add cases for an unsigned nested helper, a nested helper without the runtime flag and a nested helper without a timestamp. Each should expect `FAIL: unsigned|runtime|timestamp Contents/Helpers/...`. Add fake `xcrun` and `spctl` executables and cases for a missing staple, `source=Unnotarized Developer ID`, and the all-good path.

### WR-03: `sign-bundle.sh` exits silently when the plist lacks the identifier or executable key, so its explicit errors never fire

**File:** `scripts/sign-bundle.sh:31-39`
**Issue:** `plist_get` ends in `plutil -extract ... 2>/dev/null`, which exits 1 for a missing key. The script runs under `set -e`, so `GOT_ID="$(plist_get CFBundleIdentifier)"` terminates the script on the assignment. The friendly `ERROR: CFBundleIdentifier is '', want ...` branch on line 35 is unreachable for a missing key. `EXEC_NAME` on line 38 has the same problem. I confirmed this with a bundle whose plist is empty: the script exits 1 and prints nothing. The exit code is correct (nothing is signed), but a failed release step shows no cause, and `2>/dev/null` hides plutil's own message as well. `verify-bundle.sh` avoids this because it does not use `set -e`.
**Fix:** Make the getter non-fatal, as in the verify script, so the explicit messages are reached:
```bash
plist_get() { plutil -extract "$1" raw -o - "$PLIST" 2>/dev/null || true; }
...
EXEC_NAME="$(plist_get CFBundleExecutable)"
[[ -n "$EXEC_NAME" ]] || { echo "ERROR: CFBundleExecutable missing from $PLIST; nothing signed" >&2; exit 1; }
```

## Info

### IN-01: `release.yml` never gates the app inside the final DMG, and nothing asserts the 60 minute cap the timeout budget assumes

**File:** `.github/workflows/release.yml:245-301`, `internal/updater/release_workflow_test.go:197-208`
**Issue:** The DMG is built from the already-gated, stapled .app, and the DMG itself is verified like the updater does. Nothing checks that the bundle inside the shipped DMG still passes `verify-bundle.sh --notarized` (the updater's own Verify covers the DMG, not the contents). `TestReleaseWorkflow_SignTimeout` computes the budget as `60*(1+n)+20` on the premise that each `notarytool submit` carries `--timeout 60m`. No test asserts that flag is present on all submits. If someone drops it from one submit, notarytool waits unbounded and the job timeout becomes the only cap.
**Fix:** Add an assertion that every `notarytool submit` line in `sign-macos` contains `--timeout 60m`. Optionally, mount the first DMG with `hdiutil attach -readonly -nobrowse` and run `verify-bundle.sh <mount>/Portty.app --notarized` before upload.

### IN-02: Workflows do not declare least-privilege `permissions` for the jobs that need none

**File:** `.github/workflows/build.yml:1-20`, `.github/workflows/release.yml:16-19`
**Issue:** `build.yml` has no `permissions:` block, and neither does the `release.yml` `validate` job. They run with whatever default `GITHUB_TOKEN` scope the repository setting grants, on every push and pull request. `build.yml` builds code from pull requests. The `sign-macos` job correctly sets `contents: read`.
**Fix:** Add `permissions: { contents: read }` at the top level of `build.yml` and to the `validate` job.

### IN-03: The CI keychain is created with default lock settings before waits that can last up to 60 minutes

**File:** `.github/workflows/release.yml:212-221`
**Issue:** `build.keychain` is created and unlocked but no `security set-keychain-settings -lut <seconds>` is applied. The DMG `codesign` calls run after a .app notarization wait of up to 60 minutes. If the default keychain settings relock the keychain during that wait, the `codesign --identifier` calls could fail. I could not confirm the default timeout behaviour in this environment, so this is a hardening note, not a proven failure. GitHub's own keychain-import guidance includes the settings call.
**Fix:** After `security create-keychain`, add `security set-keychain-settings -lut 21600 build.keychain`, and re-run `security unlock-keychain` before the DMG signing step if you want it unconditional.
