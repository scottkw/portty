## Flagged decisions and assumptions

- **Routing first:** read the matrix `## Routing`. Run only the sub-checks routed to VM. When R00 routed frame sub-checks to host-run, still record attribution, registration and Settings here, and mark the frame part of R02 and R03 `ROUTED:host-run` in the matching sub-row.
- **Clean start:** the guest holds a Screen Recording grant for app.portty.spike from R00 and R10. Reset it first so the helper's own prompt and attribution are observed, not inherited. The reset is part of the experiment, not cleanup.
- **Grant restarts:** after a grant, TCC may only apply after the process restarts. Observe whether the running helper sees the grant on its next iteration, then restart it through the registrar (`unregister`, then `register`) rather than `kickstart`, which is the separate R07-A measurement.
- **SMAppService from a dev path (RESEARCH A2):** registering from `~/ptest` may report RequiresApproval or need `/Applications` in the guest. Record what happened; if `/Applications` is needed, copy Spike.app to the guest's /Applications (the VM's, never the host's) and record it.
- **Rig:** reuse or recreate the scratchpad copies `vm-office.sh` and `vshot-office.sh` (IP from `tart ip portty-test`). The executor drives every Settings click.

## Executor constraints (every Phase 17 plan carries these)

- Never run anything on the host that talks to the host's live tailscaled or a 100.x address (only exception: 17-11). Never open Spike.app on the host.
- Never touch `~/Downloads` or `/Applications` on the host. Never stop a Tart VM.
- Launch GUI-path probes only with `open` in the guest; the only SSH-executed launches in this plan are `launchctl` commands (R07-A is about exactly that).
- Evidence: tccd lines filtered to the probe pids, `/Users/<name>` replaced with `/Users/USER`, no tailnet addresses, frames at most 1280 px.
- Fail loudly; stage by explicit path only; never stage the root `.gitignore`, `.planning/state.json`, `.ignore`, `agenthub` or milestone `.gitkeep` files.
