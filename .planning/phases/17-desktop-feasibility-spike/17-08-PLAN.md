## Flagged decisions and assumptions

- **Chrome order (CONTEXT specifics, user answer):** Chrome in the VM first; if it will not install or run there, the host's Chrome opens only the spike's test page, which needs the host to reach a 100.x address, so it waits for the user-gated window in 17-11. This plan then marks R12 ROUTED:host-run with the reason.
- **Chrome download:** inside VM home only, from Google's official URL, verified with codesign (Team ID EQHXZ8M8AV) before use, installed into the VM's own /Applications. Launched with a throwaway profile (`--user-data-dir=/tmp/chrome-spike`).
- **Wails shell shape (Claude's discretion):** the page is viewer.html copied into the shell's embedded assets, so it runs in the wails:// origin like a Portty Desktop tab would. The shell's Go side proxies only POST /offer and POST /report to `--server` and appends the token, the way production plans to signal through a loopback proxy (milestone SUMMARY, Architecture). If WKWebView drops the POST body on the custom scheme, record it and try the fallback `--navigate` (the window loads the http viewer URL directly), recording both.
- **Wails versions:** reuse the root go.mod's wails v2.10.2 and its go.sum lines so the build works offline (RESEARCH: built in about 8 s). The shell is a nested module inside the spike module, so neither the root module nor the spike module's `./...` compiles it.
- **Generated files:** `wails build` may write frontend/wailsjs files (.js/.ts). The repo-walking release tests scan .js and .ts files anywhere on disk, so build.sh deletes that directory after the build.
- **Shape and token:** the pipeline runs in the provisional shape from `## FEAS-02 decision`, with a fresh token per run, stopped at the end.
