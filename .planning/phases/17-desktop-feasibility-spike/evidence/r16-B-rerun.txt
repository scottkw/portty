cause of the failure (try 3), from loginwindow's own log:
  On every success loginwindow logs exactly one keyPressed line, "View is hidden password field length = 0":
  the first key reveals the lock screen's password field, and the remaining keys go into the now-visible field;
  loginPressed and "Screensaver authorization succeeded" follow about 1 s later.
  On try 3 loginwindow logged that line for all six keys (the field stayed hidden through the whole sequence),
  then "return in secure textfield", loginPressed with an empty field, "Screensaver authorization failed: -60005"
  and "INCORRECT password". So every key event was delivered to loginwindow (no event was lost and the posting
  process had its grants); the keys arrived while the password field was still hidden, the reveal did not
  happen in time, and the password was submitted empty. This matches 17-06's failed attempt (B-type), whose
  frames showed an empty Enter Password field after the typing.
  It is a loginwindow UI race, not a property of the shape: the posting code is the same as the helper's.
