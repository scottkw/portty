# Phase 20 — UI Design Contract

> Visual and interaction contract for Phase 20 (Remote Control: DCTL-01/02/03/05/06, DESK-05/06). Generated by gsd-ui-researcher in auto mode (the user delegated every product and UX choice), to be verified by gsd-ui-checker. Phase 20 **extends** the Phase 19 `/desktop/` viewer. It adds no design system, no token and no npm package.

**Sources, in priority order:**
1. `20-CONTEXT.md`: the locked wire and security decisions (input on the `input` data channel, normalized coordinates plus epoch, `key` and `text` messages, lock gate, window-share gates, explicit-only clipboard) and the "Claude's Discretion" list that already fixes the surfaces: a slim auto-hiding top bar with Display/Window picker, Send keys menu, Copy from Mac, Paste to Mac, Ctrl→Cmd toggle and View only/Control toggle; control on by default and keyboard captured only while the video has focus; the local pointer dot; the "The shared window closed; showing the main display" notice; the Copy and Paste toasts; Fullscreen with Chrome Keyboard Lock; Locked greyed-out controls; plus the post-research items (Lock Screen confirm dialog, Ctrl and Cmd exchanged, Cmd+Tab and Cmd+Space off in window shares, topmost-window click check).
2. `19-UI-SPEC.md` (approved): every token, spacing step, type role, chip and card rule, the state wording, the copy voice. Inherited unchanged unless a section below says it supersedes one.
3. `20-RESEARCH.md`: R1 (window raise can fail, so a visible failure state), R8 (Lock Screen confirm), R9 (window share disables the chords), R10 (menus and pop-ups are not in a window share), R14 (paste-privacy alert may appear), R15 (Keyboard Lock can be refused), Pattern 8 (Safari needs the clipboard write inside the click handler; paste fallback textarea), Pattern 9 (surface list filter, epoch), Pitfalls 6, 7, 10.
4. `21-CONTEXT.md` and `22-CONTEXT.md`, only for what they ask of this surface: a Send-keys menu component the Desktop tab and the iPhone key bar can place; the display and window switch inside DesktopView; control and clipboard availability exposed as viewer capabilities; a thin accent ring when keyboard control is on; one release chord (Ctrl+Option+Cmd+Return); clipboard actions addressed per viewer; guests never pick the display.
5. Project memories: macOS-native look (system font, native menu look, light and dark follow the system), radical simplicity, rock-solid (nobody can get in to fix the office Mac, so no key is ever left held and every failure is visible in words), colorblind user (color is never the only signal), no developer paths or real tailnet addresses in committed text.
6. Existing code, scanned 2026-11-26: `frontend/src/style.css` (token blocks, `.context-menu*`, `.share-segbar`/`.share-seg*`, `.toolbar-share`, `.dialog-scrim`, `.dialog*`, `.button*`), `components/ContextMenu.tsx` (the `role="menu"` and `role="menuitem"` focus model), `components/RegenerateKeyModal.tsx` (confirm-dialog shell, safe button focused first), `lib/useDialogFocus.ts`, `components/KeyBar.tsx` and `lib/ctrlMap.ts` (closed key tables, one-shot Ctrl). `DesktopView.tsx` and `lib/desktopClient.ts` do not exist yet (Phase 19 is planned, not built); their planned DOM is taken from `19-06-PLAN.md`: one `<video aria-label="Mac desktop" class="desktop-view__video">`, `.desktop-chip`, `.desktop-card`, `.desktop-scrim`, `.visually-hidden`, and the exported `videoContentRect` helper.

**Scope.** Six surfaces: (A) the control layer on the viewer stage (pointer, keyboard focus, capture ring); (B) the auto-hiding control bar with its menus (display or window picker, Send Keys, Clipboard, swap toggle, View Only or Control, Full Screen); (C) state chips and notice chips; (D) three dialogs and popovers (Lock Screen confirm, Copy fallback box, Paste box); (E) the host side on the shared Mac (a Settings row, one tray suffix, four copy changes to Phase 19 strings, one conditional permission row); (F) the phone and forward-compatibility rules. Out of scope and not designed here: control arbitration and physical-input-wins (DCTL-04), admit, per-person grants, guest states and a host-side picker (Phase 22); the Wails Desktop tab, its control-mode ring and label, Cmd+W/Q/C forwarding, iPhone trackpad, touch scroll and soft keyboard (Phase 21); the unlock flow, audio, adaptive quality (Phase 23). Every item marked **[default]** is a detail CONTEXT did not fix; it is the simplest choice that fits the house style, and the planner may adjust it without asking.

**What "phone" means below:** the media query `(pointer: coarse) and (hover: none)`, the same as Phases 14 and 19 (`lib/phoneQuery.ts`). Never the user agent. Below, **bar-capable viewer** means "not phone, and the daemon's hello says this viewer may control". Today that is every own-account viewer on a desktop browser.

## Color

All colors are existing tokens with light and dark values, repainting live with the system appearance. No token is added.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-viewer-bg` behind the video (Phase 19), `--color-window` (the Lock Screen dialog) | The page and the letterbox stay black; the picture is the product |
| Secondary (30%) | `--color-popover` with `--color-control-border` and `--shadow-popover` (bar, menus, popovers, chips), `--color-segment-bg` and `--color-segment-selected` (View Only / Control), `--color-field` (textarea), `--color-separator` (dividers) | Every overlay that carries text |
| Accent (10%) | `--color-selection-fill` (text on it `--color-on-accent`) | Reserved list below |
| Destructive | `--color-destructive` | Not used. Lock Screen is consequential but not destructive; it uses the default button fill (see the dialog) |

Text colors: `--color-text`, `--color-text-secondary` (captions, the resolution beside a display, disabled-looking secondary text), `--color-error-text` (popover inline errors only). Disabled items use `--opacity-disabled` with `aria-disabled="true"`, never `disabled`, so focus and tooltips still work.

**No text is ever drawn directly on the video or on `--color-viewer-bg`** (Phase 19 rule, kept). Every word sits on a `--color-popover` surface: the bar, a menu, a popover or a chip.

**Local pointer dot** uses two existing tokens: fill `--color-on-accent` (white in both appearances) with a 1px border `--color-viewer-bg` (black in both), so it reads on any desktop picture. It is a shape cue, not a text surface.

Accent reserved for (nothing else):
- the switch track when on, the Done button, the Tap to Start button fill (Phase 19, unchanged);
- the **capture ring** (keyboard control is on);
- the focused or hovered row in a bar menu (the existing `.context-menu__item:focus` fill);
- the **Lock Screen** confirm button and the Paste popover's **Send to Mac** button (both `.button--primary`, the default-button fill);
- the Copy fallback popover's **Done** button (`.button--primary`).

Not accent: the bar, its buttons and dividers, the selected segment (`--color-segment-selected`), the pressed Swap toggle (it shows a check mark, see Surface B), chips, menus.

Color is never the only signal (the user is colorblind): the capture ring is a present-or-absent line, and every capture change also has a word notice; every toggle shows its state with a check mark or a selected-segment label; every chip pairs an icon with words.

## Surface A: Control layer on the viewer stage

This supersedes three Phase 19 Surface 5 rows for bar-capable viewers: "Chrome: None while streaming", "nothing is forwarded", and "Keys are not captured". Everything else in Phase 19 Surface 5 (page shell, safe areas, one `<video>`, `object-fit: contain`, sharpness rules, `touch-action: manipulation`, no text on the video) is unchanged. A phone, and any viewer whose hello does not allow control, gets exactly the Phase 19 page (see Surface F).

### Structure

```
<div class="desktop-view">                                 Phase 19 root, safe-area padding
  <div class="desktop-stage" tabindex=0 role="application"> the focus and pointer target
    <video class="desktop-view__video" aria-label="Mac desktop">   one element, never replaced
    <div class="desktop-ring" aria-hidden>                 2px accent ring, pointer-events: none
    <div class="desktop-dot"  aria-hidden>                 8px local pointer dot
  </div>
  <div class="desktop-overlay desktop-overlay--bar">       top-center column, pointer-events: none
    <DesktopControlBar/>                                   pointer-events: auto while shown
    <state chip/>  <notice chip/>                          Phase 19 chip, then the notice chip
  </div>
  <scrim, cards (Phase 19)/>   <dialogs, popovers/>
</div>
```

The stage fills the padded box and owns every pointer and keyboard listener. The overlay and its children never forward events to the Mac: a click on the bar, a menu, a chip or a popover stays in the viewer. The `<video>` keeps the Phase 19 rules (no transform, no zoom, no `width` or `height` attributes).

### Control state

| State | How it is entered | Pointer | Keyboard | Cursor over the picture | Ring |
|-------|-------------------|---------|----------|-------------------------|------|
| **View only** | The user picks View Only in the bar, or the viewer has no control right, or the page is a phone | Nothing forwarded | Nothing captured; stage has `tabindex="-1"` | The default arrow (Phase 19) | none |
| **Control, keyboard off** | The default for an own-account viewer on load; or Control chosen; or focus left the stage | Forwarded while over the picture | Not captured; keys go to the viewer's own computer | Local dot (the arrow is hidden), real Mac cursor visible in the frames | none |
| **Control, keyboard on** | The stage has focus: a click on the picture (that click is also forwarded), Tab onto the stage, or Enter on it | Forwarded | Captured: every key goes to the Mac; `keydown` default prevented except the release chord | Local dot | on |
| **Control paused** | Locked, Reconnecting, Control needs Accessibility, a surface switch in flight, or the window could not be raised | Dropped by the daemon; the viewer stops sending | The viewer sends nothing; the stage keeps focus so the user does not have to click again | Local dot hidden, default arrow | on if the stage still has focus (the user still owns the keyboard), with the reason in a chip |

Control starts on for own-account viewers and is not remembered between visits **[default]**: the Control choice is cheap and a stale "View Only" would only confuse. The keyboard never starts captured (CONTEXT).

### Pointer

| Rule | Contract |
|------|----------|
| Mapping | `x` and `y` are normalized 0..1 inside `videoContentRect(...)`, the displayed video rectangle inside the letterbox, recomputed on the `<video>` element's `resize` event, on window resize and on rotation. The viewer never uses device pixel ratio |
| Inside the picture | Moves, button down and up, wheel are forwarded. Right button is index 2, middle is 1, left is 0. Buttons 3 and 4 (back, forward) are dropped **[default]**. The browser context menu is suppressed over the picture while control is on |
| Letterbox bars | Not part of the Mac. A press that starts in a bar is not forwarded. Moves in a bar are not forwarded unless a button is already held |
| Drag | Pointer capture on press, so a drag that leaves the picture, the stage or the window keeps going and the release always arrives. While a button is held, positions clamp to the picture edge |
| Wheel | Pixel deltas. A wheel event with `ctrlKey` (a trackpad pinch) is swallowed and never zooms the page, in Chrome and Safari. Nothing scrolls the viewer page |
| Local dot | An 8px dot at the pointer while control is on, status is streaming and the pointer is over the picture. It is drawn at the pointer on the same animation frame as the move, so it has no round-trip lag. It is hidden while locked, paused, in View Only, over a bar, and on pointer leave |
| Coalescing | One move per animation frame; presses, releases and wheel are never dropped or merged (CONTEXT) |
| Stale epoch | After a surface or size change the viewer stops sending pointer and key events until it has the new epoch; events in flight are dropped by the daemon. This is silent, and the picker shows Switching… meanwhile |

### Keyboard focus and capture

| Rule | Contract |
|------|----------|
| Focus target | The stage (`tabindex="0"`, `role="application"`, `aria-label="Mac desktop"`, `aria-describedby` a visually hidden line, see Accessibility). A visually hidden text input inside it receives the keys and the input-method composition, and is positioned at the last pointer position so the system candidate window appears beside the pointer |
| Capture on | Focus entering the stage. Draws the ring, hides nothing else. Shows the notice "Typing goes to the Mac" (first time in this browser: with the release chord, see Copywriting; the "seen" flag is one `localStorage` key, `portty:desktop-release-hint-seen`, set when that first notice shows, the same storage as the Swap setting) |
| Capture off, user action | Clicking the bar or a menu, choosing View Only, opening a dialog, or the release chord. Releases every held key and button, removes the ring, shows the notice "Typing stays on this device" |
| Capture off, not a user action | Window blur, `visibilitychange` to hidden, `pagehide`, a closed channel. Releases everything, removes the ring, shows no notice (nobody is looking). When the user returns, the page is in "Control, keyboard off" and one click restores it |
| Release chord | **Ctrl+Option+Cmd+Return**, detected on the physical codes (Control, Alt, Meta and Enter) before the Ctrl and Cmd swap, never forwarded to the Mac. It gives the keyboard back and moves focus to the Control segment, which reveals the bar. This is the same chord Phase 21 uses, so a learned escape works in both viewers. Without it, a keyboard-only user would be trapped, because Tab is forwarded to the Mac while the stage has focus **[default]** |
| Keys the browser keeps | Cmd+Tab, Cmd+W, Cmd+Q and similar browser or OS chords cannot be captured, in Chrome or Safari. There is no workaround beyond the Send Keys menu and Full Screen (CONTEXT). The viewer does not try to detect these, and no copy promises them |
| After a menu action | Choosing a Send Keys item, or a clipboard action that sent keys, returns focus to the stage if the stage had focus before the menu opened; otherwise to the menu's button |

### Capture ring

A 2px ring in `--color-selection-fill`, drawn inside the safe-area box on its own overlay element (`pointer-events: none`), never on the `<video>`. It shows only in "keyboard on" and "paused with focus". It appears and disappears at once (no animation), so there is nothing to reduce. It is the same cue Phase 21 specifies for its control mode.

## Surface B: The control bar and its menus

### Placement and visibility

A floating bar, **top-center**, not a full-width strip: a full-width bar would cover the Mac's own menu bar, which a remote user needs. At the center it covers only the empty part of the menu bar and, on a notched MacBook, nothing useful.

Rendered only when the viewer is bar-capable and the status is streaming, locked or reconnecting. It is not rendered under any card (Needs permission, Waiting for approval, Display asleep, Desktop paused, Tap to start, the three errors, Connecting).

| Rule | Contract |
|------|----------|
| Hidden look | `opacity: 0`, `translateY(-8px)`, `pointer-events: none`. It stays in the DOM and in the tab order |
| Reveal | Pointer enters the reveal zone (top 16px, middle 50 percent of the width); keyboard focus enters the bar (`:focus-within`); a menu or popover is open; for 5 seconds after the first frame; for 3 seconds when the lock state, control availability or the surface changes |
| Hide | 1.5 seconds after the pointer leaves both the bar and the zone, if no focus is inside, no menu or popover is open and no dialog is open |
| Motion | Opacity and translate, 150 ms. Instant under `prefers-reduced-motion: reduce` |
| Z-order | Above the stage and chips, below the menus, popovers and the dialog scrim |
| Chips | The chip column sits below the reserved 44px bar row, so a revealed bar never moves a chip |

### Layout

```
┌────────────────────────────────────────────────────────────────────────────────────────────────┐
│ [▭ Main Display ▾] │ [🔑 Send Keys ▾] [📋 Clipboard ▾] │ [⇄ Swap Ctrl and Cmd] [View Only|Control] │ [⤢ Full Screen] │
└────────────────────────────────────────────────────────────────────────────────────────────────┘
   group 1: what is shown     group 2: send to the Mac          group 3: how typing maps       group 4
```

Left to right, with 1px dividers between groups:

| # | Item | Control | Icon (16px) | Label |
|---|------|---------|-------------|-------|
| 1 | Shared screen | Button opening the picker menu, `aria-haspopup="menu"` | `ComputerDesktopIcon` for a display, `WindowIcon` for a window, then `ChevronDownIcon` | The current surface name, truncated at 160px (full name in `title` and in the accessible name) |
| 2 | Send Keys | Button opening the Send Keys menu | `KeyIcon`, `ChevronDownIcon` | **Send Keys** |
| 3 | Clipboard | Button opening the Clipboard menu | `ClipboardDocumentIcon`, `ChevronDownIcon` | **Clipboard** |
| 4 | Swap | Toggle button, `aria-pressed` | `ArrowsRightLeftIcon`; `CheckIcon` replaces it while pressed | **Swap Ctrl and Cmd** |
| 5 | Control | The `.share-segbar` with two segments, a `role="radiogroup"` | none | **View Only** and **Control** (the selected one is 600) |
| 6 | Full Screen | Toggle button | `ArrowsPointingOutIcon` / `ArrowsPointingInIcon` | **Full Screen** / **Exit Full Screen** |

Clipboard is one menu, not two buttons, so the bar stays slim and so Phase 22 can gate clipboard rights per viewer by hiding one item **[default]**.

**Density.** Full density (icon and label) at a viewport width of 880px or more. Below 880px every item except the picker and the Control segmented control becomes icon-only (`padding: 0 8px`); each keeps its full name as `aria-label` and `title`. The picker keeps its truncated name at any width. This is a CSS media query on viewport width, not a user-agent test **[default]**; the planner may tune 880.

### Item availability

An item is **hidden** when this viewer can never use it (a capability the hello did not grant). An item is **greyed** (`aria-disabled="true"`, `--opacity-disabled`, tooltip names the reason) when it is temporarily unusable. This keeps Phase 22 guests and Phase 21 surfaces forward-compatible: they hide what they lack and the bar closes up.

| Condition | Picker | Send Keys | Clipboard | Swap | View Only / Control | Full Screen |
|-----------|--------|-----------|-----------|------|---------------------|-------------|
| Streaming, control OK | enabled | enabled | enabled | enabled | enabled | enabled |
| **Locked** | greyed, tooltip "Locked" | greyed | greyed | enabled (local only) | greyed, both segments | enabled (local only) |
| **Reconnecting** | greyed, tooltip "Reconnecting" | greyed | greyed | enabled | greyed | enabled |
| **Control needs Accessibility** | enabled | greyed (keys cannot post) | enabled (not input) | enabled | Control segment greyed with the reason as its description; View Only still selectable | enabled |
| **Window share** | enabled | Cmd+Tab, Cmd+Space and Lock Screen greyed with a caption | enabled | enabled | enabled | enabled |
| **Switch in flight** | label reads Switching…, greyed | enabled | enabled | enabled | enabled | enabled |
| **View Only** | enabled | greyed, tooltip "Turn on Control first" | enabled | enabled | enabled | enabled |

The rule while locked is: every item that sends something to the Mac is greyed; items that only change this viewer (Swap, Full Screen) stay live. This fails closed, matching the lock gate (CONTEXT), and means nothing in the bar can be read as "unlock from here".

### Picker menu (DESK-05, DESK-06)

Opens below the picker button. Built on the `.context-menu` look and focus model with `role="menu"`; each choice is `role="menuitemradio"` with `aria-checked`. The list is requested from the daemon each time the menu opens and is not refreshed while open **[default]**.

WINDOWS
   Terminal — zsh
   Safari — Release notes
   Portty — Settings
   …
Menus and pop-ups don't appear in a window share. Share the display to see them.   (caption row)

### Clipboard menu (DCTL-06)

```
 Copy from Mac
 Paste to Mac
─────────────────────
 Cmd+C and Cmd+V in the picture use the Mac's own clipboard.
 Use these to move text between the two.            (caption row)
```

Both actions are explicit: nothing is read or written until the item is chosen, and nothing is polled. The Safari rule (research Pattern 8) is part of the contract: the viewer starts the clipboard write inside the click handler, with a promise that resolves when the Mac answers.

**Copy from Mac**

| Outcome | What the user sees |
|---------|--------------------|
| Waiting (more than 400 ms) | Notice **Copying from the Mac…** (persistent until the result) |
| Text arrived, browser accepted the write | Notice **Copied from Mac** |
| Text arrived, browser refused the write | The Copy popover (Surface D) with the text selected |
| Concealed or transient item on the Mac | Notice **The Mac's clipboard holds a hidden item (password manager); not copied** (5 seconds). The text is never requested |
| No text on the Mac's clipboard (empty, or an image or file) | Notice **The Mac's clipboard has no text** |
| macOS would ask for approval at the Mac | Notice **Waiting for approval at the Mac. macOS is asking before Portty reads its clipboard.** (5 seconds) |
| More than 1 MB | Notice **The Mac's clipboard text is too large to copy (limit 1 MB)** |
| Channel or daemon error | Notice **Couldn't copy from the Mac. Try again.** |

**Paste to Mac**

1. The click handler reads the viewer's clipboard (`readText`). Chrome asks permission the first time; Safari shows its own Paste prompt.
2. Text found: it is sent at once, and the notice **Sent to the Mac's clipboard; press ⌘V** shows (5 seconds). Portty never presses Cmd+V itself, so the text cannot land in an app the user did not choose (CONTEXT).
3. The browser refuses or has no `readText`: the Paste popover opens (Surface D) with an empty textarea.
4. The clipboard is empty: notice **Your clipboard has no text**.
5. Over 1 MB: notice **Your clipboard text is too large to send (limit 1 MB)**.
6. Sending takes more than 400 ms: notice **Sending to the Mac…** until done. A failure or a disconnect mid-transfer discards the partial text and shows **Couldn't send to the Mac. Try again.**

Both menu items are greyed while a transfer is in flight, so two transfers never overlap. Typing Cmd+C or Cmd+V on the picture acts on the Mac's clipboard only and never touches this one (CONTEXT); the caption row says so.

### Swap Ctrl and Cmd (DCTL-03)

A toggle button. **Off by default**, remembered per browser in `localStorage` **[default]**. Pressed state is shown by `aria-pressed="true"` and the `CheckIcon` in place of the arrows icon, with a `--color-segment-selected` fill and the 1px border kept, so it never relies on color. It exchanges the two keys: Ctrl sends Cmd and Cmd sends Ctrl (CONTEXT, after research). Toggling shows the notice **Ctrl and Cmd are swapped** or **Ctrl and Cmd are back to normal**. The mapped code is fixed when a key goes down, so toggling while a key is held strands nothing (research Pitfall 6). The toggle is visible to every bar-capable viewer, Mac or not: detecting the keyboard by user agent is brittle, and a visible toggle is predictable **[default]**.

### View Only / Control

A two-segment `.share-segbar` (`role="radiogroup"`, each segment `role="radio"`, `aria-checked`). Choosing **View Only** releases everything held, removes the ring and the dot, and shows the notice "Typing stays on this device" if the stage had focus. Choosing **Control** returns to "Control, keyboard off". The segment tooltip carries the release chord: **Control: click the picture to type. To give the keyboard back, press Ctrl+Option+Cmd+Return.**

### Full Screen

Enters fullscreen on the stage and, where the browser has the API, requests Keyboard Lock so Cmd and Esc chords reach the Mac. Focus moves to the stage once fullscreen starts, because the click on the button blurred it and Keyboard Lock only helps a focused page. A rejected lock is never an error. The button is hidden when the browser reports fullscreen unavailable (`document.fullscreenEnabled` false). Phones never show it, because they have no bar (Surface F).

| Result | Notice |
|--------|--------|
| Chrome, lock granted | **Cmd and Esc shortcuts now go to the Mac. Hold Esc to leave full screen.** (5 seconds) |
| Safari, or lock refused | **Full screen is on. This browser keeps Cmd shortcuts; use Send Keys for Cmd+Tab and Cmd+Space.** (5 seconds) |

The bar works the same in fullscreen. Exiting fullscreen (button, Esc long-press, or the browser) releases the lock and every held key.

## Surface C: State chips and notice chips

The viewer keeps Phase 19's rule that messages sit on `--color-popover` and never on the video. Phase 20 adds one stacked slot.

| Slot | Meaning | Position | Behaviour |
|------|---------|----------|-----------|
| **State chip** (Phase 19) | A condition that lasts: Streaming N viewers (3 s), Locked, Reconnecting…, and the three conditions below | First in the overlay column, below the reserved bar row (`top: calc(52px + env(safe-area-inset-top))` on bar-capable viewers; `calc(8px + env(...))` elsewhere, exactly as Phase 19) | One at a time. Priority: Reconnecting, Locked, a window problem, Control needs Accessibility, Streaming |
| **Notice chip** (new) | A thing that just happened: a copy result, a switch, a toggle | Directly below the state chip, 8px gap | One at a time, newest replaces older. Fades after its dwell. `Copying…` and `Sending…` stay until the result |

Dwell: 3 seconds by default; 5 seconds when the text explains or gives a next step. The fade is 150 ms and instant under `prefers-reduced-motion: reduce`. State chips are `role="status"` (Phase 19). Notice chips are `role="status"`, except a failure, which is `role="alert"`. A chip never takes focus.

### New state chips (persist while the condition holds)

| Condition | Icon | Text | Clears when |
|-----------|------|------|-------------|
| Control needs Accessibility (the daemon found that posted moves have no effect) | `ExclamationTriangleIcon` | **Control needs Accessibility. On the Mac, allow Portty in Privacy & Security.** | The daemon reports control working again |
| Window could not be raised (window share, research R1: focus not confirmed in about 300 ms; input stays dropped) | `ExclamationTriangleIcon` | **Couldn't bring the window to the front. Click the picture to try again.** | A raise succeeds |
| Shared window minimized (window share) | `WindowIcon` | **The shared window is minimized. Click the picture to bring it back.** | The window is back on screen |

The click that triggers a raise or an unminimize is itself not delivered to the Mac (CONTEXT: the triggering event is dropped), so the next click lands. This is the one place the viewer teaches that, in the Interaction Contract and the Decisions table, not in copy. Whether the daemon can report "minimized" is the planner's to confirm; if it cannot, the frozen frame is the only sign and this chip is omitted **[default]**.

| Event | Icon | Text | Dwell | Role |

## Accessibility Contract

| Element | Contract |
|---------|----------|
| Stage | `tabindex="0"` while Control is on, `-1` in View Only; `role="application"`; `aria-label="Mac desktop"`; `aria-describedby` a visually hidden line: **While this has focus, your keyboard and pointer control the Mac. To give the keyboard back, press Control, Option, Command and Return together.** |
| No keyboard trap | The release chord always exits capture and moves focus to the Control segment. The same words are in the Control segment's tooltip and the first-capture notice. Tab and Shift+Tab are forwarded to the Mac while captured, and that is the reason the chord exists |
| Bar | A `role="toolbar"` with `aria-label="Desktop controls"` and arrow-key movement between items optional; every item is also reachable by Tab. `:focus-within` reveals it, so a hidden bar is never unreachable. Icon-only items keep a full `aria-label` |
| Menus | `role="menu"`, items `menuitem` or `menuitemradio` with `aria-checked`; trigger `aria-haspopup="menu"` and `aria-expanded`; ArrowUp, ArrowDown, Home, End, Enter, Esc as `ContextMenu.tsx`; focus returns to the trigger. Caption rows are plain text with `role="presentation"` and are linked from the menu by `aria-describedby` |
| Greyed items | `aria-disabled="true"`, not `disabled`, so they stay focusable and their tooltip and `aria-describedby` reason are read. The reason is real text, never only a tooltip on hover |
| Toggles | Swap is a `<button aria-pressed>`; View Only / Control is a `radiogroup` of two `radio`s. The Full Screen button's name changes with its state |
| Chips | State chips `role="status"` `aria-live="polite"` (Phase 19 region, extended); notice chips `role="status"`; failures `role="alert"`. A chip never takes focus. The Phase 19 visually hidden "Streaming" stays |
| Dialog and popovers | `role="dialog"` with `aria-labelledby`; the Lock Screen confirm is `aria-modal="true"` with Don't Lock focused first and Tab trapped; popovers are non-modal, Tab wraps inside, Esc closes. Inline errors `role="alert"` |
| Color | Never the only signal: the ring is present or absent, plus a word notice; toggles use a check mark or a selected, bold label; every chip has an icon and words; Granted and Needs permission are words (Phase 19) |
| Contrast | Text on `--color-popover`, `--color-window` or `--color-segment-selected` uses the existing token pairs; the dot and the ring are shapes, not text; `--color-on-accent` on `--color-selection-fill` for the focused menu row and primary buttons |
| Focus ring | The existing 3px `--color-focus-ring` on every bar item, segment and button |
| Motion | The bar and chip fades are 150 ms and instant under `prefers-reduced-motion: reduce`; the ring and dot never animate; no icon rotates |
| Pointer size | Bar items are 28px tall (pointer UI only); the phone has none of them |
| Screen readers | The picture is not made operable by a screen reader. The bar, menus, dialogs and notices are fully operable and announced; the hidden description names the limit honestly |

## Decisions Made Here (Claude's discretion; the user may override)

| Decision | Choice | Why |
|----------|--------|-----|
| Bar shape | A floating, top-center bar, not a full-width strip | A full-width strip would cover the Mac's menu bar, which a remote user needs |
| Bar visibility | Auto-hide, revealed by the top-center zone, focus, an open menu, the first frame (5 s) and state changes (3 s) | The picture stays uncluttered; the bar is still reachable by mouse and by keyboard |
| Bar placement of chips | Chips sit below a reserved 44px bar row on bar-capable viewers | A revealed bar never moves a chip |
| Chip slots | Phase 19's state chip plus one new notice chip below it | A copy result must stay visible while a state chip such as Locked persists |
| Clipboard grouping | One Clipboard menu | Keeps the bar slim; Phase 22 can gate clipboard per viewer by hiding one control |
| Ctrl→Cmd swap | A visible toggle with a check mark when on; off by default; remembered per browser | Predictable for Mac viewers, one click for others; state shown without color |
| Control on load | On for own-account viewers; not remembered; the keyboard is never captured until a click | CONTEXT: they are the user's own devices; focus-gating stops stray typing |
| Click that focuses | Forwarded, as well as focusing | The user is already in Control mode; swallowing it would feel broken |
| Release chord | Ctrl+Option+Cmd+Return, on physical codes, never forwarded | Avoids a keyboard trap; matches Phase 21 so the escape is learned once |
| Locked | Everything that sends something to the Mac is greyed; Swap and Full Screen stay | Fails closed with the lock gate; local-only items are harmless |
| Lock Screen | Behind a confirm; primary fill, Don't Lock focused; greyed in window shares | It strands an unattended Mac; a window share must not grant more than a window |
| Window-share chords | Cmd+Tab, Cmd+Space and Lock Screen greyed with a caption, not hidden | Research R9; the menu keeps its shape |
| Surface names | Main Display, Display N, "App — Title" | Plain; matches the CONTEXT notice wording |
| Notice dwell | 3 s; 5 s when the text explains or gives a next step | Quick for confirmations, enough time to read advice |
| Held-key notice | Shown only when something was actually held and the cause was not the user's own blur | Honest feedback without noise |
| Minimized chip | Shown only if the daemon can report it; otherwise omitted | CONTEXT does not say the daemon reports it |
| Paste behavior | Read and send at once on the click; popover only if the browser refuses | Fewest steps for the common case; research Pattern 8 |
| Over-size clipboard | Refused with a message at 1 MB, not truncated | A silent cut would paste partial text into a command line |
| Host display | A Showing row while viewers are connected; tray suffix only for a window share | Shows what is shared without leaking into a line that has to stay short |
| Four Phase 19 strings change | Switch description, Link description, setup intro, Accessibility how-to | Turning the switch on now grants control; the consent copy must say it |
| Phone | View only, no new touch controls | CONTEXT scope; Phase 21 owns touch |
| Toasts become notice chips | CONTEXT's "Copied from Mac" and "Sent to the Mac's clipboard; press ⌘V" toasts render as notice chips in the stacked slot under the state chip, with the CONTEXT text unchanged | Phase 19 has no toast component and forbids text on the video; a chip is the viewer's one message surface, and the second slot lets a notice show while a state chip persists |
| "Done" on the Copy popover | Kept as a single-word button | Inherited from Phase 19: it matches the Settings sheet's Done and the house dialog convention, and the popover has exactly one way out besides Esc, so the label names the only outcome |
| Dismiss labels | Lock This Mac uses Don't Lock; the Paste popover uses Discard Text; neither says Cancel | Checker revision 1: labels name what happens. Focus order and Esc behavior are unchanged from the house confirm pattern |
| Settings Row 4 button | Follows Phase 19: Set Up Permissions… while either permission (including a failing Accessibility) is missing, Review Permissions… when all is granted | One rule; revision 1 removed a contradiction with 19-UI-SPEC Row 4 |
| Storage | Two `localStorage` keys: Swap (`portty:desktop-swap-ctrl-cmd`) and the first-capture hint flag (`portty:desktop-release-hint-seen`) | Per browser, nothing sent to the server, no new persistence on the Mac |
