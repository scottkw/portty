## Flagged decisions and evidence

- **Planner probe (2026-11-21, at 81ada526, not committed; the temporary file was deleted).** A real `@xterm/xterm` 6.0.0 `Terminal` opened in this repo's vitest jsdom, with the rig below, showed both suspected mechanisms exactly:
  - Resize: after a hover and a Cmd-click that activated once, `term.resize(60, 10)` then a Cmd-click at the same cell activated nothing, and a mousemove to the same cell plus a click activated nothing; only a move to a different cell brought the link back. Cause in xterm: `Linkifier.ts` clears the current link on resize (lines 47-50) and re-hovers only when the pointer reaches a cell different from `_lastBufferCell` (line 83); `_lastBufferCell` is never reset.
  - Reconnect: with the pointer resting on a link, a provider that answers nothing while "disabled", and `term.options.disableStdin` set true (TerminalPanel does this when the RelayClient enters `reconnecting`, TerminalPanel.tsx:572-577), one render ran, the Linkifier asked the row again while disabled and cached the empty answer, and dropped the current link. After re-enabling and setting `disableStdin` false, neither a same-cell click nor another cell on the same row activated. Cause: any option change makes xterm's RenderService refresh every row (RenderService `_handleOptionsChanged`), the render listener of the hovered link re-asks the providers (`Linkifier.ts` 301-317), and later hovers on that row read the cached empty reply (`Linkifier.ts` 93-105, 124-133). This is the U-01 symptom (the cursor stayed `text` on 12 x positions of the same row).
  - Fix shape: in a microtask, setting the Linkifier's `_lastBufferCell` to undefined and `_activeLine` to -1, then dispatching one non-bubbling `mousemove` on `.xterm-screen` with the last pointer's coordinates and modifier keys, made the same-cell click activate after both the resize and the drop. With `\x1b[?1003h\x1b[?1006h` (any-motion tracking, SGR) on, a real bubbling move produced 1 `onData` report and the synthetic move produced 0.
  - The committed reproduction is still required (Tasks 1 and 2): the probe is planning evidence, the RED commit is the record.
- **Real-xterm rig (jsdom; record it in the new test file's header).** Before `term.open`, define getters for `offsetWidth` and `offsetHeight` on `HTMLElement.prototype` that return `8 * 32` and `16` for an element with class `xterm-char-measure-element` and 0 otherwise (xterm's DomMeasureStrategy; jsdom has no OffscreenCanvas), and restore the saved descriptors in `afterEach`. After `open`, set the `.xterm-screen` element's `style.padding = '0px'` (jsdom leaves padding empty and xterm's `getCoords` would read NaN). jsdom's `getBoundingClientRect` is all zeros, so the cell at column c, row r has its centre at `clientX (c - 0.5) * 8`, `clientY (r - 0.5) * 16`. Dispatch `MouseEvent` `mousemove`, `mousedown`, `mouseup` with `bubbles: true` and `metaKey: true` on `.xterm-screen` (the Linkifier listens there, CoreBrowserTerminal.ts:491). Set `navigator.platform` to `MacIntel` (as TerminalPanel.pathClick.test.tsx does) so the `'platform'` modifier is Cmd. Use real timers for xterm's renders; after an option change or a write, wait at least 50 ms (the probe used 100 ms) and assert that `term.onRender` fired, so a poisoning step cannot be skipped silently. Assert the rig in every test (`(term as any)._core._charSizeService.hasValidSize` true, css cell 8 x 16): a broken rig must fail loudly, never pass.
- **Fix design for Gap 2 (reversible; one file plus one call site).** `registerPathLinks` returns `PathLinksHandle` (`IDisposable & { invalidate(): void }`). `invalidate()` drops xterm's cached link state and, if the pointer is inside the terminal, re-hovers at its last position. Why each part:
  - Deferred with `queueMicrotask`: the public `term.onResize` fires before the Linkifier's own resize listener (CoreTerminal.ts:130 forwards the buffer's resize event at construction; the Linkifier subscribes at `open`), so synchronous work would be undone by the Linkifier's clear.
  - Private fields `_lastBufferCell` and `_activeLine` on `(term as any)._core.linkifier` (a public getter on xterm's core): xterm 6 has no public way to drop the per-row reply cache or the last-cell memory. The repo already reads `_core._renderService` in production (TerminalPanel `recomputeScale`). Production code checks that both fields exist and otherwise does nothing (a hover refresh must never throw inside a resize handler); the test `xterm 6 still has the Linkifier fields the refresh resets` fails if an xterm upgrade renames them, so the regression cannot come back silently.
  - Non-bubbling `mousemove` on `.xterm-screen`: the Linkifier receives it; xterm's mouse-report listener is a bubble-phase listener on `term.element` (CoreBrowserTerminal.ts:747), so a program with mouse tracking gets no report and nothing is typed into the session.
  - The provider is unchanged: it still answers nothing while the capability is false, so read-only viewers and the time before the host's bit stay exactly as 12-06 built them; the existing tests "offers nothing while disabled" (pathLinks.test.ts) and "offers no links until the host says path clicks are available" (TerminalPanel.pathClick.test.tsx) stay green unchanged.
  - URL links share the Linkifier, so the resize refresh covers them too (the verifier asked for this).
- **Fix design for Gap 1: this Mac's own link settings for peer tabs (reversible; the smallest safe route).**
  - Why the current code gives a peer tab nothing: App.tsx line 1311 hands a remote tab no config so that WebShareSessionView self-fetches the host's `/api/plugin-config` (commit 98ac41ba, upstream Phase 168: "instead of applying this daemon's own plugin config to a different peer's session"). From the app's `wails://` origin that request is cross-origin and the share server sends no CORS header, so the read always failed, silently (WebShareSessionView.tsx:172-175), and the EventSource on the stream retried forever. `git log -S` shows no CORS header was ever in `internal/webserver`, so this never worked in the desktop app; build A had no URL links in peer tabs either.
  - Routes considered: (a) a deliberate CORS allowance for the app origin on the share server: rejected, it widens the token-gated share server's surface (project constraint: keep the token gate, tailnet-only listener and CSP intact); (b) fetch the host's config through Go (a Wails binding, a daemon route, a cap-bearing request to the peer, plus a replacement for the live stream): rejected as larger than the gap and a new daemon-originated network path; (c) chosen: a peer tab uses this Mac's own `webLinks` and `webLinksConfig` (Cmd versus Ctrl, the URL confirm switches) and nothing else. It adds no route, no header, no request; it removes a failing cap-bearing cross-origin request and its retry loop. In a desktop app the web-links toggle the user sees is this Mac's Settings, so "path links follow the web-links toggle" (UI-SPEC) reads naturally as this Mac's toggle.
  - Narrow on purpose: only the two link fields cross over. Every other addon in a peer tab stays as today (`webgl`, `clipboard`, `search`, `serialize`, `progress` off; `unicode11` and `image` at TerminalPanel's built-in defaults), so this gap turns on no OSC 52 clipboard and no WebGL in peer tabs. Build the object with the generated `daemon.PluginSettings.createFrom({ webLinks, webLinksConfig })`, memoized on App's `pluginConfig` state.
  - WebShareSessionView self-fetches only when it is not a remote peer tab, so no future caller can bring back the silent cross-origin request; the browser viewer at `/app/` (not remote) still reads the host's config from its own origin, as before.
