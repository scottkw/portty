<objective>
The daemon-to-daemon handoff (CONTEXT "Locked by research and roadmap: Mechanism"), its failure semantics, and its entry from EnsureDaemon:

1. The protocol: `portty daemon --takeover` connects to the old daemon's `/handoff`; HELLO, FREEZE, STATE plus fds, staged import, READY, COMMIT, serve, COMMITTED; the old daemon exits without unlinking the socket and without sending 1000 (Research Patterns 7 and 8).

3. The entry: EnsureDaemon hands off when it can and falls back to the DEBT-08 question with a couldn't-move reason when it cannot (Pattern 9).

## Flagged decisions and assumptions

- **Depends on all three wave-1 plans.** Read their SUMMARYs first for the exact signatures: 09-01 (`EnsureDaemon(ctx, socketPath, EnsureOptions)`, `RestartQuestion.MoveFailed`, `EnsureOptions.NoHandoff`, `HealthResponse.Handoff`, startDetachedDaemon's shape, the 503 retry), 09-02 (`pty.Session.SetReadDeadline/Pid/HandoffFiles`, `NativePTYBackend.Adopt`, `fdpass.Send/Recv/PeerUID`, `WebServer.Listener/StartOn`, `Config.APIVersion`), 09-03 (`Hub.Freeze/Thaw/Export/Digest/Start/RestartViewers`, `NewHubFromState`, `HubManager.AddStaged`, `Subscriber.Restart`).
- **Wire format (planner's choice; reversible until the first release that ships it).**
  - `const HandoffVersion = 1`, advertised as `Handoff: HandoffVersion` in handleHealth once the route is registered.
  - Request: the takeover dials the socket and sends `POST /handoff HTTP/1.1` with `Upgrade: portty-handoff/1`; the handler checks the method and header, answers `101 Switching Protocols`, and hijacks the connection (the unix listener yields a `*net.UnixConn`; assert it, refuse otherwise).
  - Frames on the hijacked conn: 1 byte type, 4 bytes big-endian length, then a gob payload. fds never share a frame with a large payload: an fd frame is a small fixed header (type, session index, fd count) sent with fdpass.Send and read with fdpass.Recv for the expected count, so the unmeasured per-message fd limit (A3) never matters.
  - Messages in order: HELLO {HandoffVersion, BuildVersion, PID} → HELLO-OK or REFUSE {Code, Reason}; GLOBAL {session count, share server running, share records (session id → grantID, token)} + fd frame [lock, API listener, relay listener, share listener when running]; per session SESSION {ID, Name, WorkDir, CreatedAt, CLI, Pid, HubState} + fd frame [master, slave]; READY {Digests} or ABORT {Reason}; COMMIT; COMMITTED.
  - Caps: one frame at most 64 MiB; a SESSION frame at most `relay.DefaultScrollbackBytes + relay.HistoryMaxBytes + 1 MiB`; a session count at most 256. Anything larger aborts before import (Research Security Domain V5).
- **Which sessions move.** Only live sessions: a stopped session has no shell and no fds, so it is not handed over and the new daemon does not list it (as after today's DEBT-08 restart). A session whose hub returns `relay.ErrHubEnded` from Freeze (its shell exited during the freeze) is treated as stopped the same way. Planner's choice, reversible: carrying stopped entries as metadata would add a hub-less session kind for no user-visible gain.
- **Old side (the handler).**
  1. HELLO: `fdpass.PeerUID(conn) == os.Getuid()` (through a package seam for the refusal test), HandoffVersion equal, and not an older release (below); one handoff at a time (a second gets REFUSE busy). A refusal sends no fd and freezes nothing.
  2. FREEZE: set the freeze gate (mutating routes answer 503 with `Retry-After: 1`, see below), then `Freeze()` every hub whose session is not stopped. Any Freeze error: Thaw the ones frozen, clear the gate, send ABORT, close.
  3. STATE: `Export()` each frozen hub (which re-seeds the old hub with its own export, 09-03), collect the session metadata and the share records of live sessions, send GLOBAL with the fds, then each SESSION with its fds.
  4. Wait up to 5 s (`readyTimeout`, a var for tests) for READY. Compare each digest with the old hub's `Digest()`. Any mismatch, timeout, ABORT, EOF or error: Thaw every hub, clear the gate, close the conn, log one line (step, reason, counts), keep serving.
  5. COMMIT. From here the old daemon never resumes reading on a timeout (the new one may already be reading). It waits for COMMITTED or EOF with no timeout of its own; the takeover's watchdog (below) bounds the wait.
  6. EOF before COMMITTED: the new daemon died. Kill nothing, Thaw (the hubs already hold their own export), clear the gate, keep serving, and log that any bytes the new daemon read in that window are lost. `shortcut:` comment (CONTEXT decision on the COMMIT-to-COMMITTED window, Research A6): the window is milliseconds and the shells survive either way.
  7. COMMITTED: mark handedOff; `SetUnlinkOnClose(false)` on the API unix listener copy, then close it and the relay and share listener copies; `RestartViewers()` on every hub (relay viewers get 1012 from 09-03; browser viewers get 1012 from this plan's one-line webserver change); then the exit seam (`os.Exit(0)` in production). Never call api.Stop, Hub.Shutdown, HubManager.Shutdown, KillSession or a context cancel on this path (Research Anti-Patterns): each would unlink the socket, send 1000 session ended, or end shells.
  - Accepted overlap: between COMMIT and the old daemon's exit both processes may accept on the shared listeners. The old one answers reads from frozen state and 503 for writes, and its viewers get 1012 when it exits, so nothing is lost. Document it at the COMMIT step.
- **New side (`RunTakeover`, entered by `portty daemon --takeover`).**
  - Takes no lock (it receives the lock fd; flock follows the open file description, 09-02 pin) and binds nothing.
  - Imports into a staged engine: for each session, `backend.Adopt` from the received master and slave with the pid (its exit watcher is registered first), `relay.NewHubFromState(st, sess, sess, resizeFn)`, `manager.AddStaged`, the names and workDirs maps; share records into `a.shares`; the listeners through `net.FileListener`; settings and ct_disclosed reloaded from disk now, not at process start (a settings PATCH was gated during the freeze, so the disk is current); the capability key reloaded with BootstrapCapabilityState (CONTEXT: "Reloaded from disk"). When share records exist, construct the share server and warm its certificate now, so a certificate failure aborts before COMMIT.
  - Any import error: send ABORT with the reason, close every received fd and every adopted session's files without signalling anything, exit with the import code.
  - READY with each hub's Digest; then wait for COMMIT. EOF before COMMIT: poll the old pid with `kill(pid, 0)` for up to 500 ms (through a seam); gone means proceed as committed (Research Pattern 8 extra rule: a dead old daemon cannot read), alive means exit with the timeout code without reading.
  - On COMMIT: arm a 5 s watchdog (`committedWatchdog`, a var) that exits the process if COMMITTED has not been written by then, turning a hang into the old daemon's EOF path. Serve the API on the received unix listener, the relay on the received TCP listener, the share server with `StartOn` on its listener (grants from the records, Config.APIVersion = APIVersion), `Start()` every hub, re-arm each session's exit goroutine with the API's onExit cleanup, start the daemon log (rotation) and the socketLost watch, then write COMMITTED and stop the watchdog.
  - Then it runs the same serve loop as runDaemonCore (extract the tail of runDaemonCore into one function both call).
  - Exit codes (one table in handoff.go, also used by EnsureDaemon): 0 committed; 3 busy; 4 refused (uid, version, older release); 5 import failed; 6 timed out or the old daemon went away alive before COMMIT; 1 anything else.
- **Refusing an older release (CONTEXT deferred: a downgrade handoff stays unsupported; "Older-version daemons are refused, or go through DEBT-08").** `olderRelease(a, b string) bool` in handoff.go: both match `^v?\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$`; compare the numeric core, then a version without a suffix is newer than one with, then suffixes compare as strings. Unparseable versions ("dev") are never compared. The VM and integration builds use `v1.2.0-vmA`/`v1.2.0-vmB` and `v1.2.0-itA`/`v1.2.0-itB`, so a GUI A relaunched after an upgrade to B cannot pull the sessions back: its takeover is refused and it gets the DEBT-08 question, where Not Now keeps B (API compatible).
- **Freeze gate.** A middleware on a.mux: while frozen, POST/PUT/PATCH/DELETE (except the handoff route itself) answer 503 with `Retry-After: 1`. GET routes keep serving (health, list, tail, relay-port). /shutdown is POST, so Quit All and a DEBT-08 restart wait for the outcome (09-01's client retry), which is the CONTEXT rule "after READY or COMMIT, Quit All waits for the handoff to finish, then stops the daemon normally".
- **SIGTERM guard (Research Pitfall 4).** In the shared serve loop: when ctx ends while a handoff is in progress, wait for its outcome (bounded by readyTimeout plus the watchdog); handed off means exit with no api.Stop, no unlink and no session teardown; rolled back means today's shutdown runs. The lost-socket branch is unchanged.
- **The route is only on the unix socket mux** (Research Security V4): registered on `a.mux` only, never in RelayHandler or the webserver mux. A test asserts the relay port and the share server answer 404 for it (a behaviour test, not a grep).
- **EnsureDaemon branch (Pattern 9).**
  - In the stale-version path, before the DEBT-08 policy: when live sessions are not 0 (an unknown count, -1, also tries: a handoff ends nothing), `opts.NoHandoff` is false and `health.Handoff == HandoffVersion`, call `takeover(ctx, client, spawn)`: spawn `exe daemon --takeover` (refused from a test binary, like the fresh spawn), then poll every 50 ms for `daemonReady` (this build's version, Research "ready means the right version") until ready, ctx ends, or 10 s pass (`takeoverWait`, inside daemonReadyWait, Pitfall 11). A busy exit (3) keeps polling: another takeover may be winning.
  - Success returns nil with no question (UPGR-01: no dialog). After a failure, read /health once more: this build's version means success after all. Otherwise set `MoveFailed` from the exit-code table: 3 "another update is already moving them", 4 "the running version refused", 5 "the new version could not load them", 6 "the handoff timed out", spawn error or any other code "the new version exited", and continue into the unchanged DEBT-08 flow with that question.
  - ctx cancelled (Quit All) during a takeover: return ctx.Err() and never kill the takeover child (CONTEXT: "It never kills a takeover daemon that might already own the sessions"). startDaemon's lock wait is not used on this path (the old daemon holds the lock by design).
  - Zero live sessions: today's plain restart (Research A9). `handoff` absent (v1.1) or a different HandoffVersion: no takeover, the plain DEBT-08 question (MoveFailed empty).
  - `startDetachedTakeover(exe)` in process_unix.go: Setsid, daemon.log for stdout/stderr like startDetachedDaemon, returns a channel that yields the exit code. It has no kill func on purpose.
- **LaunchAgent (CONTEXT: "Portty doesn't install one (confirm). Hand off the same way").** Confirmed at planning time: `portty daemon install` (service.go, kardianos, RunAtLoad true, KeepAlive false) is opt-in and nothing in the GUI or CLI installs it. A launchd-started daemon hands off like any other; afterwards `portty daemon stop` (launchctl) no longer stops the takeover daemon, which launchd does not manage. Record it with a `shortcut:` comment in handoff.go; no special case.
- **Logging (Research Security V7).** Step names, session counts, pids, byte counts and exit codes only. Never a share token, capability, key or terminal content. A test captures the log output of a full handoff with a shared session and asserts the token string does not appear.
- **Fault seam (Research Pitfall 13).** One package var `handoffFault func(side, step string) error` (nil in release builds) called at every step on both sides; a non-nil error makes that side behave as failing or dying at that step. Tests set it directly. handoff_vmpreview.go (`//go:build vmpreview`, header copied from share_vmpreview.go) sets it from `PORTTY_VMPREVIEW_HANDOFF_FAULT=<side>:<step>:<action>`, where action is `exit` (os.Exit(1) at once, no cleanup) or `pause<N>` (log `handoff-fault: paused at <step> pid=<pid>` and sleep N seconds, so the VM run can `kill -9` the process at a known step). check-brand keeps the tag out of release scripts.
- **In-process tests.** Both daemons run in one test process: the old API on a temp socket under the TestMain /tmp HOME, a fresh engine and API for the new side calling the takeover function in a goroutine. fds sent over the socket arrive as duplicates in the same process, which is exactly what the kernel does across processes. The exit seam records the old daemon's exit instead of exiting. Sessions use `/bin/sh` ticker scripts through SetSpawnCommandForTest; shares use SetShareSeamsForTest with the existing fake TLS server pattern from share_test.go.
- **Real launch check (v1.1 lesson dcbe999d).** `daemon --takeover` is new argument routing. On the host, with a temp HOME (no daemon there, so nothing binds and nothing reaches the network): `portty daemon --takeover` must exit non-zero within 3 s with one stderr line saying no daemon answered; `portty daemon bogus` keeps its usage error (`unknown daemon subcommand "bogus"`). The two-binary run with real daemons is 09-05's (integration test in the VM, rows I-01..I-03).
