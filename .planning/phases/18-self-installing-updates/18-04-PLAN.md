## Flagged decisions and assumptions

- **No new binding:** DownloadUpdate keeps its name (the binding and the Wails JS stay), only its behaviour widened in 18-01. Renaming it would touch generated bindings for no user benefit.
- **Copy:** button "Update" matches CONTEXT wording ("Clicking Update installs the new Portty"). The relaunching message says "Restarting" because the user sees the app quit and come back.
- This plan does not use the VM; banner states are read through axdump in 18-07.
- **Generated-file rule (checker round 2):** `frontend/src/wailsjs/go/main/App.d.ts` carries an "AUTO-GENERATED by Wails, DO NOT edit" header, so this plan does not edit it. Evidence for where the union can live: wails.json sets `wailsjsdir` to `./frontend/src/wailsjs`, and Wails writes its generated bindings into the `wailsjs` folder inside that dir (`frontend/src/wailsjs/wailsjs/go/main/App.d.ts`, ignored by .gitignore line 30), where GetUpdateStatus returns `updater.Status` and its state is a plain `string`. A Go string field generates a TS `string`, never a literal union, so the Go type cannot drive the union. The banner's widened `UpdateStatus` is therefore declared in UpdateBanner.tsx, a plain component module that App.tsx (line 63) and UpdateBanner.test.tsx (line 6) already import `UpdateStatus` from; the stub's narrower type stays assignable to it (GetUpdateStatus's result flows into it unchanged). Deviation from 18-PATTERNS.md, which listed App.d.ts as modified. Side effect: no same-wave plan edits anything under frontend/src/wailsjs, so 18-08's rig build guard never trips on this plan.
