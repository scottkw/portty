## Flagged decisions and assumptions

- **Plan-check residual (final round, force-proceeded 2026-11-25, W1/W3):** R4-smoke PASS must cite an `evidence/ROW.state` capture. Truths 1 and 5 name the detection method and check order; read them as outcomes: a disk-image launch is detected and nothing else is, and the copied app is never un-quarantined, shown or launched unless it passes the same checks as an update (failure shows the reason and reveals the app). Mechanism stays in the task action.
- **O3 (same or newer copy installed), resolved (checker context_compliance, UPD-08):** do not replace; eject the volume, open the installed copy, then move the downloaded DMG to the Trash exactly as the other install paths do. This follows UPD-08 literally ("ejects the DMG, and moves the downloaded DMG to the Trash") and is reversible because the Trash is recoverable by hand, so no requirement amendment and no user confirmation are needed. 18-RESEARCH.md O3 is marked RESOLVED with this choice; the final mover rows R4-d and R4-g (now in 18-09) expect the DMG in the Trash.
- **Empty staging folder after a first install (checker round 2, info):** with no existing copy, Swap is a plain rename that leaves the `.Portty-update-*` folder empty; the move kind removes it with os.Remove (never RemoveAll) right after that Swap, so no hidden folder waits for the sweep's 1 hour floor. R4-smoke here and R4-a and R4-e in 18-09 check that no such folder is left.
- **Cancel on the Replace question:** opens the installed copy and quits, leaving the DMG mounted and untouched (research Pattern 7). This is the user declining the move at the question CONTEXT requires before replacing an older copy, so keeping their download is the user-confirmed outcome, not a departure from UPD-08.
- **Failure paths keep the DMG:** a staging failure (alert, Reveal of the app on the volume) and a first install that never gets healthy leave the DMG in place, because UPD-09's fallback is to show the user that download; trashing it would remove the fallback.
- **No DMG-level Verify in mover mode, decision:** the user chose this DMG; its app gets the full app-level chain (deep strict codesign, Team, identifier, notarized exec assessment, plist version, minimum macOS, smoke run) before its quarantine is cleared. Running Verify on the user's DMG would rewrite its quarantine flag, a needless change to a user file.
- **First install that never gets healthy:** there is no older copy to restore, so the new copy stays installed (a complete verified bundle), the result is failed and the DMG is not trashed.
- **Mover never SIGKILLs the DMG-run GUI:** it has no daemon or sessions and already quit itself; if it is still alive after QuitWait the installer stops with nothing changed.
- **P4 (Replace dialog frontmost for an agent app):** mover mode calls setDockVisible(true) before any dialog or alert so it appears in front (Pitfall 10); P4 records whether that was needed.
- **P5 (translocation):** if P5 shows a DMG launch is translocated, detection uses statfs's mount-from name; if statfs gives no usable origin, mover mode does nothing and logs it (no guessing).
- **Installer for the mover kinds runs from a whole-bundle copy (revision 2026-11-25, 18-10):** a.startInstaller copies the running bundle, which in mover mode is the app on the mounted volume (or its translocated path), as a whole with ditto into the job's run folder, checks the copy's signature and Team, removes the copy's quarantine flag (a quarantined DMG's flag would otherwise follow it) and starts install-update from that copy's Contents/MacOS/Portty. So the installer is the DMG's version, the version that wrote the job, and it never runs from the volume it detaches. Nothing in this plan copies a lone executable. The installer's ps line (`.../update/run-*/Portty.app/Contents/MacOS/Portty install-update ...`) is never counted as a GUI. Every Open of a Portty in the move kinds goes through 18-03's relaunch retry helper (row A9).
- **Unclassified edge item for UPD-08, flagged assumption (reviewed, not a test):** covered cases are no copy, older copy (ask), same or newer copy, unwritable /Applications, translocated launch; a Portty launched from a writable volume, a network share or a zip extraction is not a disk-image launch and starts normally.
