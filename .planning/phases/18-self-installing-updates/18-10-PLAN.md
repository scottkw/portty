## Flagged decisions and assumptions

- **Source of this plan (orchestrator, 2026-11-25):** P2d CONTRADICTED A1 (18-VM-CHECKS.md row P2d, `evidence/P2d-amfi.log`: `Code=-420`, the Developer ID signature binds Info.plist, so a lone executable outside its bundle fails validation). The decision is CONTEXT [Installer], revision 2026-11-25, option (b); (a) the staged new bundle and (c) an embedded Info.plist are rejected there and are not reopened here. P2d's hand test already showed a ditto copy of the whole bundle in another folder runs.
- **Copy source is runningBundle(), not j.Target:** for the update kind they are the same bundle; for 18-06's move kinds j.Target is the Applications path and the running bundle is the app on the mounted volume (or its translocated path). The source is resolved through `runningBundleFunc` so tests can point it at a fake bundle.
- **Check, then unquarantine the copy (planner choice, reversible):** ditto keeps every extended attribute, including `com.apple.quarantine` (P1 showed the flag propagating from a DMG into a copy). 18-01's lone copy carried no attributes at all, so without this step the whole-bundle copy would bring a new risk: a quarantined copy (a user-dragged install, or 18-06's mover running from a quarantined DMG) meeting a Gatekeeper assessment at exec with nobody at the Mac (an ad-hoc rig build in 18-09's R4-f would be refused outright). copyBundle therefore runs `updater.VerifyApp` (deep strict codesign plus Team, and 18-02's identifier check once it lands) on the copy, then `updater.ClearQuarantine` on the copy only. The copy is the code that is already running; the check makes the UPD-09 rule (never unquarantine or start an unchecked copy) hold for it too and also proves the signature survived the copy before anything is started. The running bundle is never touched. Cost: one codesign verify of the bundle before the spawn, while the banner already says it is restarting.
- **Start deadline (orchestrator: named constant, measured in Task 2):** `installerStartWait` bounds spawn to started marker only; download, verify, staging and the copy all happen before the clock starts. So Task 2 records click-to-marker as asked, and applies the raise rule to spawn-to-marker, the interval the deadline actually bounds (raise when spawn-to-marker is more than half of the deadline). A first exec of a freshly copied signed bundle may be slower than R1-lite's ad-hoc runs (AMFI validation, syspolicyd), which is what the measurement checks.
- **GUI lines in update.log:** a LaunchServices-launched GUI's stderr goes nowhere, so 18-01's start failures were invisible on an unattended Mac. startInstaller writes its outcome (step name or the two durations, never a path) to update.log by appending without rotating; only spawnInstaller rotates, before the child opens the file. Task 2 reads spawn-to-marker from this line.
- **Run folder removed while the installer runs from it:** runInstallUpdate's final RemoveAll of RUN now deletes the bundle the installer process runs from. That is fine on macOS: unlinking a running executable only removes the name; the process keeps its mapped vnode until it exits, and the removal is the last step before exit. runInstallUpdate is not changed.
- **GUI-pid safety:** the installer copy runs at a different path with `install-update` as its first argument. The rig's GUI filter (Portty.app executable with no argument) and 18-03's ParseGUIPids (exact installed executable path, first argument not daemon or install-update) both exclude it; 18-03 adds the installer's own ps line to its fixture.
- **Disk space, accepted residual:** the copy needs one more app size on the config dir's volume; 18-02's CheckSpace covers the staging volume only. A copy that runs out of space fails at step `copy` and falls back to Reveal with the installer-start text, which is not silent.
- **A9 is not this plan's fix:** a relaunch `open` that fails with -600 procNotFound is 18-03's (CONTEXT relaunch note). Here it is recorded, the new version is opened by hand to confirm it runs, and the run is repeated up to 3 times to get one run where the installer relaunched by itself.
- **STOP rule (RULE 0):** P2d-bundle CONTRADICTED (the copy is killed, or the swap is refused under Developer ID), `identity=none`, or any other unexplained outcome stops the plan after the row is written; the executor reports to the orchestrator with the options in Task 2 and does not work around it. 18-03 depends on this plan and does not start.
- **No new test file:** cmd_install_update_test.go already holds the app_install.go tests (TestBundleFromExecutable, TestSpawnInstaller_RefusesUnderTest), so the new tests go there; 18-09's count of eight new Go test files and its TESTING.md ownership (Category BI) are unchanged, and this plan does not edit TESTING.md.
- **LaunchServices and the copy (observation, not a gate):** the copy is started with exec, not through LaunchServices; Task 2 records whether `lsregister -dump` lists any `update/run-` path after the run.
- Test helper names added here start with `bc` (bundle copy) so they never collide with 18-03's `rb` helpers in package main.
