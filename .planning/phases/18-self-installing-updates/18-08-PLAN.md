## Flagged decisions and assumptions

- **Why a separate plan:** these two tasks were 18-01 Tasks 2 and 3; they moved here so 18-01 fits the per-plan context budget (checker scope_sanity). Nothing in them changed except the rig build guard and the corrected guard gate below. 18-02 and 18-03 depend on this plan because they read its P7, P8 and P2 verdicts; 18-04 runs alongside it because no probe outcome changes the banner states.
- **A3 / Pattern 8 (quarantined mount):** Stage always clears the DMG's quarantine after Verify passed and before attach, and every fallback writes it back before Reveal. P1 only confirms. If P1 shows a dialog even with the quarantine cleared, STOP: the mount approach must change.
- **A1 (installer copy runs):** the installer is a copy of the running binary (CONTEXT, Decided autonomously). If P2d shows macOS kills a Developer-ID-signed copy at exec, STOP and report the two alternatives (run the installer from the staged new bundle; ship NSUpdateSecurityPolicy); do not switch silently.
- **O5 (rig feed seam), resolved:** the rig reuses the existing `vmpreview` tag (fake update feed on 127.0.0.1:8788, loopback fake Tailscale and share). The share link in VM rows is checked with `curl` on loopback; the real tailnet share link is part of the office-Mac item M-169 (written into TESTING.md by 18-09). The verify bypass lives in `updates_vmpreview.go` itself, so any binary carrying it also carries the `127.0.0.1:8788` string that release.yml already refuses.
- **Rig build guard (new):** `build` patches wails.json and lets Wails regenerate frontend/src/wailsjs, then restores both with git checkout. It refuses to start when either has uncommitted changes, so the restore can never throw away someone else's edit. No same-wave plan edits those paths (18-04 declares its widened type in UpdateBanner.tsx and leaves frontend/src/wailsjs untouched, checker round 2), so the guard's precondition holds without ordering 18-04 before this plan.
- **No grant behind a no-dialog verdict (checker round 2):** a PASS after granting App Management by hand says nothing about an unattended Mac. Before R1-lite and before P2d the VM must show no App Management grant to Portty (axdump of System Settings > Privacy & Security > App Management; revoke with the click helper, or `tccutil reset SystemPolicyAppBundles` in the VM, if one is there). R1-lite's verdict and P2d's verdict each come only from their un-granted run. A granted ad-hoc re-run is recorded as its own row R1-lite-granted and never sets a no-dialog verdict; if it was needed, later plans' ad-hoc rows grant it again at their start, say so in their evidence, and revoke it before any Developer ID row (P2d here, R3 in 18-07).
- **Saved state captures (checker round 2, for 18-07 and 18-09):** a row's verdict text is written by the executor, so every row that later plans gate on cites a capture the rig wrote from the VM. `state ROW` writes the raw output to `evidence/ROW.state` with the VM's home path shown as `~`; no hand edits.
- **Developer ID identity at planning time (checker round 2, info):** on 2026-11-25 `security find-identity -v -p codesigning` on this host listed one identity for team S2K7P43927, so P2d (and R3 in 18-07) is expected to run for real; the P2d row records the count the executor sees (`identity=found` or `identity=none`), and BLOCKED is allowed only with `identity=none`.
- **Guard gate corrected (checker verify_command_format):** `updates_vmpreview.go` carries `127.0.0.1:8788` 3 times at HEAD c714c8ef, not 2. The old count gate passed at HEAD and could not catch the mutation it named (moving the bypass to another file leaves the count at 3). It is replaced by a check that `updates_vmpreview.go` is the only root Go file mentioning `p18/verify-mode`, plus the count at its measured baseline.
