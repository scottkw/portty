## Flagged decisions and assumptions

- **HARD-04 root cause: not found by code reading at planning time.**
  - `startup` runs `startDaemon` synchronously. `EnsureDaemon` (process.go) returns nil only after `/health` and `/relay-port` both answer on its own fresh client. `startupDone` is closed before `startTrayPoller` starts. Yet the poller's immediate `a.client.Health()` failed on every VM launch (05-VM-MATRIX iteration 3: daemons 512 and 21210, healthy for minutes and not replaced). Its `EnsureDaemon` then found the daemon up at once ("attempt 1: ok").
  - So the failure is specific to the App's long-lived client right after launch. Its error text was never logged.
  - This plan does two things. (a) It puts the health error into the log lines, so 07-05's VM launches reveal the cause. (b) It adds a gate that makes launch-time health blips harmless whatever the cause.
  - If the executor finds the cause on the way (for example something that uses `a.client` before the poller and leaves a broken pooled connection), fix it too and record it. The gate still stays.
- **HARD-04 gate: a bounded version of the CONTEXT decision ("the respawn path does nothing until the first healthy observation after startup").**
  - Taken literally, that rule would stop the poller from ever recovering a daemon that dies before the first healthy tick, or after a failed startup. That is a regression against Phase 5 R6 and the user's rock-solid priority (nobody can click Retry on the remote Mac).
  - So, refinement: new fields `seenHealthy bool` (guarded by daemonMu) and `launchedAt time.Time` (set by `startDaemon` only when the ensure succeeded; written before `startupDone` closes and read only after, so the channel close orders it), and a const `respawnLaunchGrace = 10 * time.Second` (same as respawnBaseDelay; the first two 5 s ticks).
  - In `respawnDaemonIfDown`, after taking daemonMu:
    - a healthy result sets `seenHealthy`;
    - an unhealthy result with `!seenHealthy`, a non-zero `launchedAt` and `now.Sub(launchedAt) < respawnLaunchGrace` returns at once: no ensure call, no attempt count, no `lastRespawn` change, no event;
    - the first such skip logs one diagnostic line (wording below).
  - Everything else is unchanged:
    - failed startup: `launchedAt` stays zero, so the poller retries as today;
    - existing tests construct App without `launchedAt`, so they keep today's behaviour;
    - after the first healthy tick, a dead daemon is respawned on the next tick (R6).
- **Log wording (a VM check greps these):**
  - the respawn line becomes `portty: daemon unreachable (<health error>), respawn attempt N: <result>`; the `respawn attempt` text stays;
  - the one-time launch line is `portty: daemon not answering right after launch (<health error>); waiting up to 10s before any respawn`. It must not contain the words "respawn attempt".
  - The health error contains only the socket path and the dial or HTTP error, never user content.
- **HARD-06 isolation, two layers (CONTEXT HARD-06: temp dir for settings and socket; ConfigDirForTest exists):**
  - (1) A package `TestMain` in internal/daemon/testmain_test.go, mirroring the root package's testmain_test.go. It records the original HOME in a package var for the guard test, sets HOME and XDG_CONFIG_HOME to a fresh dir made with `os.MkdirTemp("/tmp", "pdh-")` before `m.Run()`, then removes it and exits with m.Run's code.
    - Why /tmp and not the default TMPDIR: `DefaultSocketPath()` under a long macOS TMPDIR exceeds the 103-char sun_path limit, and `TestRunDaemonCore_CancelledContext` should exercise the same full startup path it gets on CI (app_respawn_test.go's respawnHome uses /tmp for the same reason).
    - This covers every test in the binary, including the external `daemon_test` package files and the 17 direct `NewSessionEngine()` calls.
  - (2) `testDaemon` (api_test.go) calls `t.Setenv("HOME", t.TempDir())` and the same for XDG_CONFIG_HOME before `NewSessionEngine()`, so even a settings.json that another test wrote into the TestMain HOME cannot leak in. That leak is what the new guard test reproduces deterministically.
    - No internal/daemon test calls `t.Parallel()` (checked at planning time), so t.Setenv is allowed.
    - The old reset block (configDir, startMinimized, pluginSettings) becomes redundant; Chesterton: it existed only because the engine read real settings. Remove it and replace its comment with a short why for the HOME isolation. Keep `engine.configDir = t.TempDir()` and `SetSpawnCommandForTest`.
  - No change to engine.go, which 07-01 edits in the same wave.
- **No `-skip` left to remove:** at planning time no gate, script, CI workflow or TESTING.md carries one (`git grep` found matches only under .planning). 07-05 re-confirms and runs the full gate without it.
- **HARD-08 placement:** README.md is the user doc. Add a `## Known Issues` section directly above `## License`, with the content from the todo:
  - narrowing (not widening, taller or shorter) can leave copies of a multi-line prompt's top line in the scrollback;
  - the cause is zsh redrawing a wrapped multi-line prompt on each resize (each resize sends SIGWINCH);
  - it is cosmetic;
  - remedies: `clear` or Ctrl-L, or a one-line prompt, for Powerlevel10k via `p10k configure` (one-line style) or `~/.p10k.zsh`.
  - Keep it to a few lines in the README's plain style.
  - Do not mention any macOS package manager. The brand gate (tests/check-brand.sh) flags it.
