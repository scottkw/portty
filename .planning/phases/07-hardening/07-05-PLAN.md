- **Large-paste method:**
  - The payload is exactly 100,000 bytes of base64 characters with no newline (xterm.js turns pasted LF into CR, and canonical tty mode caps a line at 1024 bytes). Generate it in the home VM: `head -c 75000 /dev/urandom | base64 | tr -d '\n' | head -c 100000`.
  - The receiving shell runs `stty raw -echo; head -c 100000 > /tmp/<file>; stty sane`, which reads exactly that many bytes.
  - PASS means the office file's `shasum -a 256` equals the payload's, and the size is 100000.
- **Alt-screen memory method:** RSS alone is unreliable for a Go process (freed pages return to the OS slowly). So run the office daemon with `GODEBUG=gctrace=1`:
  - quit the office GUI and its daemon;
  - start `GODEBUG=gctrace=1 nohup ~/ptest/Portty.app/Contents/MacOS/Portty daemon > /tmp/gctrace.log 2>&1 &` (the same `daemon` argv the GUI spawns, internal/daemon/process_unix.go);
  - relaunch the GUI, which attaches to the running daemon.
  - In a session, run a TUI-like script: enter the alt screen with `printf '\e[?1049h'`, print 30,000 numbered lines, then leave with `printf '\e[?1049l'`.
  - Read the live heap (the last number of each `gc N ...: A->B->C MB` line) at baseline, during and after.
  - The runtime forces a GC at least every 2 minutes, so wait for at least two GCs after the exit.
  - PASS means the live heap after the exit is within 20 MB of the baseline and a second run does not raise it. Record RSS (`ps -o rss=`) alongside for information.
  - Restore the normal GUI-spawned daemon afterwards.
