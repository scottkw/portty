# Phase 23 — UI Design Contract

> Visual and interaction contract for Phase 23 (Audio, Adaptive Quality, Unlock and Release: DCTL-07, DESK-07, UNLK-01). Generated by gsd-ui-researcher in auto mode (the user delegated every product and UX choice), to be verified by gsd-ui-checker. Phase 23 **extends** the shared `DesktopView` that Phases 19 to 22 define. It adds no design system, no token, no npm package and no new page. The release work (REL-01) moved to Phase 18.1 and has no UI.

**Sources, in priority order:**
1. `23-CONTEXT.md`: the locked decisions (Unlock field only for own-account viewers, password as one message on the encrypted control data channel and never kept, the lock-time input drop for every viewer, audio starts muted on every viewer with the choice not remembered, guests hear audio like the picture, no quality setting, "sharp when still" and automatic adaptation) and the Claude's Discretion list: speaker button plus a one-time "Tap to unmute" hint, `Mac password` field and `Unlock` button, the failed-unlock sentence, the same Unlock field in browser, iPhone and Portty app, re-lock after the last own-account viewer leaves, one try about every 5 s, 3 failures pause unlock for about 15 minutes, clicks blocked while locked, the share sheet says audio reaches guests.
2. `23-RESEARCH.md`: Pattern 2 (unmute only inside a gesture; if `play()` rejects, mute again and show the hint), Pattern 6 (the unlock sequence and what can be refused before anything is typed), Pitfalls 8 and 10 (stereo, audio reaches muted viewers and guests), 11 (lock gate), 13 (Caps Lock and layout), 14 (a Go string cannot be zeroed, so the password travels as bytes), 15 (throttle and pause), 16 (re-lock signal), Open Questions 1 to 4.
3. `19-UI-SPEC.md`, `20-UI-SPEC.md`, `21-UI-SPEC.md`, `22-UI-SPEC.md` (all approved; 19 built, 20 to 22 planned): every token, chip, card, bar, menu, popover, notice and copy rule. Inherited unchanged unless a section below says it supersedes one (see "What this supersedes").
4. Existing code, scanned 2026-11-26: `frontend/src/components/DesktopView.tsx` (the `<video muted>` element with the `muted` attribute set for Safari, the `locked` flag, the Locked chip, `releaseAll('lock')`), `frontend/src/lib/desktopClient.ts`, the `.desktop-chip*`, `.desktop-card*` and `.button*` blocks in `frontend/src/style.css`.
5. Project memories: macOS-native look (system font, system accent, light and dark follow the system live), radical simplicity, rock-solid (nobody can get in to fix the office Mac: every failure is visible in words, the Mac is never left unlocked by accident), colorblind user (color is never the only signal), no developer paths or real tailnet addresses in committed text.

**Scope.** Five surfaces: (1) the Sound control (bar item, iPhone bar item, the one-time hint, the app tab's playing indicator, failures); (2) the Unlock panel and its eleven states; (3) the rest of the Locked experience (input-blocked notice, guest wording, bar and phone changes, the Lock This Mac dialog text that said "Remote unlock isn't available yet"); (4) one connection-quality chip; (5) host-side and help copy (five pinned strings that must now mention sound, and the README paragraph). Out of scope and not designed here: release packaging and the updater (Phase 18.1), the wire protocol, encoder, bitrate policy, throttle constants and re-lock timer (daemon work; this contract names only what the viewer must be told), any user-facing quality setting (none, by decision), volume (the viewer's own system volume), the audit log (it has no UI), and unlock at the login window, after a reboot or with FileVault (out of scope). Every item marked **[default]** is a detail CONTEXT did not fix; it is the simplest choice that fits the house style, and the planner may adjust it without asking.

**What "phone" means below:** the media query `(pointer: coarse) and (hover: none)`, the same as Phases 14 and 19 to 21 (`lib/phoneQuery.ts`). Never the user agent. **"The app"** is the Portty Wails window (Phase 21's Desktop tab). **"Own-account viewer"** is a viewer whose hello carries the `unlock` capability (a grant of the always-available kind). **"Guest"** is a Phase 22 click-to-share viewer. **"The Mac"** in copy is the remote Mac being shown; the headings follow the Phase 20 precedent **Lock This Mac** and use **Unlock This Mac**.

## Surface 1: Sound (DCTL-07)

**Visual anchor:** the bar's **Unmute** item, the only sound control on the page. It looks like its neighbors and says one word.

### One control, four homes

| Viewer | Where the control lives | Form |
|--------|-------------------------|------|
| Desktop browser, own-account viewer, and the app tab | The Phase 20 bar, **group 4**, before Full Screen (the app has no Full Screen, so group 4 holds Sound alone) | Bar item, icon and label at 880px or more, icon only below |
| Desktop browser, view-only guest, and any viewer whose hello grants no control but has audio | A **sound-only bar**: the same floating bar with one item. It uses the same reveal, hide, reserved 44px row and motion as Phase 20 | Bar item |
| Controlling guest | The Phase 22 guest bar, group 4, before Full Screen | Bar item |
| iPhone (own account, and a guest on a phone) | The Phase 21 bottom bar, **last item**. A phone with no other bar items shows a bottom bar holding Sound alone. The key bar (keyboard up) has no Sound item | 44px icon-only item |

A viewer whose hello says audio is not negotiated (an older daemon) gets no Sound item at all. A viewer with audio gets the item whatever else it lacks, so no one can be left unable to unmute. This supersedes Phase 22's "None" bar row for a view-only guest.

### The item

| Property | Contract |
|----------|----------|
| Muted (the start state, every page load) | Icon `SpeakerXMarkIcon`, label **Unmute**, accessible name **Unmute**, tooltip **Unmute: hear this Mac's sound** |
| Sound on | Icon `SpeakerWaveIcon`, label **Mute**, accessible name **Mute**, tooltip **Mute** |
| Toggle semantics | A plain button whose name changes with the state, like Full Screen (not `aria-pressed`). A visually hidden `role="status"` line says **Sound on** or **Sound off** after each change, so the change is announced even though focus stays on the button |
| Not remembered | The choice lives in the element and in memory only. A reload, a new visit and a new tab all start muted (CONTEXT: remembering would break "starts muted"). There is no `localStorage` key and no cookie. A reconnect inside the same page keeps what the user chose |
| Where it fires | On `click` only, never on `pointerdown`. iOS Safari counts a completed tap, not a touch start, as the user activation that allows audio, so the Phase 14 and 21 pointerdown firing rule is **not** used for this item **[ASSUMED]**; a real-iPhone row decides. A hardware keyboard or VoiceOver activation arrives as a `click` and works |
| What it does | Unmuting sets `video.muted = false` and calls `video.play()` inside the same click handler. If `play()` rejects, the video is muted again, the item returns to **Unmute**, and the notice **Couldn't turn sound on** appears (below). Muting sets `video.muted = true` |
| Volume | None. No slider, no level meter. The viewer's own system volume is the volume. Radical simplicity |
| Audio only, never video | The control never touches the picture. Mute is viewer-only: the Mac keeps sending (CONTEXT), so the host and the wire do not change |
| Availability | Hidden when audio was never negotiated. **Greyed** (`aria-disabled="true"`, `--opacity-disabled`, tooltip **Sound isn't available from this Mac right now**) while the daemon reports the audio failed. Stays live while Locked, Reconnecting and in View Only, because it only changes this viewer (the Phase 20 rule for Swap and Full Screen) |
| Window share and guests | Same as a display share. Audio goes to every viewer that sees the picture, muted or not (CONTEXT); there is no per-viewer gate |

### Hint (one time per page load)

| Rule | Contract |
|------|----------|
| What | A notice chip with `SpeakerXMarkIcon`. Pointer viewers: **Sound is off. Click Unmute in the bar to hear this Mac.** Phone: **Sound is off. Tap Unmute to hear this Mac.** |
| When | Once per page load, 5 seconds, starting at the first frame, only when audio is negotiated and the viewer is muted. It never shows under a card (Tap to start, Needs permission and the others), so on an iPhone it appears after the Tap to Start tap, once the picture runs. It shows together with the bar's 5-second first-frame reveal, so the item it names is on screen |
| Memory | In memory only. A reconnect does not repeat it. The same notice slot, role and fade as every Phase 20 notice. Unmuting removes it |
| Why not gated on the Mac making sound | Reading audio levels needs a stats poll; one fixed hint is simpler and costs nothing when the Mac is silent **[default]** |

### Failures and notices

| Event | Icon | Text | Dwell | Role |
|-------|------|------|-------|------|
| The viewer clicks a greyed Sound item, or audio fails while the viewer has sound on | `ExclamationTriangleIcon` | **Sound isn't available from this Mac right now. The picture is not affected.** | 5 s | alert |
| `play()` rejected after Unmute (autoplay policy) | `ExclamationTriangleIcon` | **Couldn't turn sound on. Choose Unmute to try again.** (phone: **Tap Unmute to try again.**) | 5 s | alert |
| Audio returns | none | none. The item quietly goes live again | | |

Audio failure never touches the picture, the chips or the bar (Phase 19 crash containment): the item is greyed and the notice appears only when the viewer tries it or loses sound it was hearing.

### The app tab's playing indicator

While the Desktop tab has sound on, the tab entry shows `SpeakerWaveIcon` (16px) between the name and the peer dot, and the tab's accessible name gains **, playing sound**. It is a shape cue, not a button. Reason: the Desktop tab stays connected and decoding behind another tab (Phase 21), so remote sound keeps playing while a terminal is in front; without a mark nobody could tell which tab is making the noise. It goes away on mute, on disconnect (including the 2-minute hidden-window disconnect) and on close **[default]**; this is the one touch Phase 23 makes to the Phase 21 tab strip.

## Surface 2: Unlock panel (UNLK-01)

**Visual anchor:** the 17px heading **Unlock This Mac** above one input row whose default button is the only accent on the stage while the Mac is locked.

### Placement and visibility

The panel is a layer of the viewer stage, bottom-centered, never over the middle of the picture, where a lock screen puts its own password field. It is a child of the same overlay layer as the bar and the chips, with `pointer-events: auto`. It sits above the stage and the chips, below menus, popovers and dialogs.

| Rule | Contract |
|------|----------|
| Rendered when | The Mac is **Locked** (the Phase 19 state) **and** the hello carries the `unlock` capability. The capability is the only gate in the viewer: a guest page, and an own-account viewer whose hello lacks it, never get the component in the DOM at all (not hidden by CSS). The daemon checks the grant kind again before it reads a password (CONTEXT: the UI is a convenience only) |
| Not rendered | Under any Phase 19 card, while Display asleep, Needs permission, Waiting for approval, Desktop paused, the three error cards; for any guest; when the Mac is not locked. During Reconnecting it stays and goes inert (state 10) |
| Appears and goes | At once, no animation (nothing to reduce). It appears when the lock chip appears and is removed when the Mac unlocks |
| View Only | Unlock stays available in View Only. It is a deliberate typed action in its own box, not forwarded input |
| Focus | **Never moved onto the field automatically.** The panel appears without taking focus. Reason: a stray key meant for the Mac, then Return, would submit a wrong password and count toward the Mac's own failed-attempt limit. The user clicks or taps the field, or Tabs to it (Tab order: the bar, then the field, then the Unlock button). Focusing or clicking in the panel ends keyboard capture exactly as the bar does (Phase 20, and in the app Phase 21: it counts as outside the picture, so control mode ends and Cmd+V pastes into the field normally) |
| Where in the DOM | A sibling of the stage's pointer target, never a child of the `<video>` or of the stage element that owns the key listener, so nothing typed in it reaches the input path |

### Structure

```
┌──────────────────────────────────────────────┐
│ Unlock This Mac                      (17/600) │
│ [ Mac password                 ] [ Unlock ]  │
│ status line (12/400)                         │
│ second line, only for a countdown or warning │
└──────────────────────────────────────────────┘
```

| Part | Contract |
|------|----------|
| Panel | `role="group"` with `aria-labelledby` the heading |
| Heading | **Unlock This Mac** (17/600) |
| Input | `<input type="password">`, placeholder **Mac password**, `aria-label="Mac password"`, `aria-describedby` the status line. Uncontrolled (a ref, not React state), so the typed text is never held in component state or props. `autocomplete="off"`, `autocapitalize="off"`, `autocorrect="off"`, `spellcheck="false"`, `enterkeyhint="go"`, `maxlength="256"` **[default]**, plus the opt-out attributes the common password managers read (`data-1p-ignore`, `data-lpignore="true"`, `data-bwignore`). It is not inside a `<form>` and has no `name`, so the browser has no form to offer to save. Paste is allowed (a viewer's own password manager is a legitimate source). There is no show-password toggle: a remote password is typed once, and nothing on the page should render it |
| Unlock button | **Unlock**, `.button--primary`, the panel's default button. `aria-disabled="true"` and dimmed while the field is empty, while an attempt runs, during a cooldown or a pause, and while Reconnecting |
| Submit | The Unlock button, or Return in a non-empty field (not while an input-method composition is open). Esc clears the field and keeps focus **[default]** |
| Status line | A `role="status"` `aria-live="polite"` region under the row, one message at a time from the state table. Failures use `role="alert"`. Its second line, when present, is the countdown or the pause warning |

### Password handling in the viewer (security boundary)

| Rule | Contract |
|------|----------|
| Cleared on submit | On Unlock or Return the viewer reads the text, builds the message bytes (a type byte, then UTF-8) in a `Uint8Array`, sends it as one binary message on the encrypted control data channel (never the signalling socket, never a URL, never `fetch`), and **sets the input's value to empty in the same synchronous step**. After the send, the byte array is filled with zeros. Plain JavaScript strings cannot be erased; this is best effort and the contract says so (research Pitfall 14) |
| Kept nowhere | Not in React state, not in a context, not in `localStorage`, `sessionStorage`, a cookie, a query string, history, an error message, a thrown value, `console.*`, or any log or analytics call. A sentinel-password test greps the page's console output and DOM text after a submit |
| Also cleared when | The page becomes hidden (`visibilitychange` to hidden, `pagehide`), the panel unmounts, the Mac leaves Locked, or Esc is pressed. Not cleared on a plain blur, so a misplaced click does not cost the user their typing |
| Not mirrored | No length hint, no dot count beyond the browser's own password mask, no echo in a chip, notice or status line |
| Never a stored password | No "remember this password", no autofill suggestion, no saved unlock (stored-password unlock is out of scope) |

### States

The viewer holds no counters. The daemon owns the failure count, the cooldown and the pause and reports them in the state message, so a reload, a second viewer or a reconnect shows the same truth. Every row below replaces the previous status line (one message at a time; the second line only where listed).

| # | State | When | Input | Unlock button | Status line (12/400) | Role |
|---|-------|------|-------|---------------|----------------------|------|
| 1 | **Waiting** | Locked, field empty, no attempt running | enabled, empty | dimmed (`aria-disabled`) | **Portty never saves it. Wrong tries count toward the Mac's own limit.** (secondary) | status |
| 2 | **Typing** | The field has text | enabled | live (full fill) | unchanged from the state before | |
| 3 | **Unlocking** | Submitted; the daemon is waking the screen and typing | emptied, `aria-disabled` | dimmed | `ClockIcon` **Unlocking…** | status |
| 4 | **Trying once more** | The Mac was still locked about 3 s after Return and the daemon is retyping once from its held buffer | emptied, `aria-disabled` | dimmed | `ClockIcon` **Trying once more…** | status |
| 5 | **Success** | The Mac reports unlocked | panel removed | | none. A notice chip appears (below) and the Locked chip clears | |
| 6 | **Wrong password** | Both tries ended still locked | enabled, empty, **focused** (the user just acted, so focus is safe) | dimmed until typing | `ExclamationTriangleIcon` **Unlock didn't work. Check the password and try again.** (`--color-error-text`). After the second failure in a row a second line adds **If the next try fails, Unlock pauses for 15 minutes.** | alert |
| 7 | **Rate limited** | A submit arrived inside the daemon's spacing window of about 5 s (from this viewer, another viewer or a fast second try) | enabled | dimmed | `ClockIcon` **Try again in N s** as the second line (or the only line if nothing else is showing). N counts down once a second, rounded up, minimum 1. It clears at zero and the button goes live. The pause belongs to the daemon, so it survives a reload and applies to every viewer | alert on entry, then status |
| 9 | **Refused before typing** | The daemon declined to type anything | enabled, empty | dimmed until typing | Caps Lock on: `ExclamationTriangleIcon` **Caps Lock is on at the Mac. Turn it off there, then try again.** A character with no key on the Mac's layout: `ExclamationTriangleIcon` **This password has a character Portty can't type.
