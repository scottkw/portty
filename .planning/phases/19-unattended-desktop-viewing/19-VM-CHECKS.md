## Findings for 19-02 and 19-17

- **A3 confirmed:** plain `launchctl kickstart gui/UID/label` (no flag) starts an idle job and is a no-op on a running one (V2 a, b). **A4 confirmed:** the launchd-started daemon has `XPC_SERVICE_NAME` equal to the label, and a GUI-spawned fallback daemon has `application.app.portty.Portty.<n>.<n>` instead. **A5 confirmed for the re-home:** shells survived the launchd job taking over from an unmanaged daemon (V2 d); the upgrade handoff out of a launchd-managed daemon is row V3.
- **Real formats the parsers assume:** `launchctl print` lines are `state = running|not running|spawn scheduled`, `pid = N`, `runs = N`, `last exit code = 0|1|(never exited)`, `last terminating signal = Killed: 9`; `print-disabled` lines are `"label" => enabled|disabled`; an unknown job prints `Could not find service "label" in domain for user gui: 501`.
- **`ppid 1` does not prove launchd.** A daemon spawned detached by a CLI run (C1, agent removed) also has ppid 1. L1's ppid check is necessary, not sufficient; the managed signals are `/health launchd:true`, the launchctl pid and XPC_SERVICE_NAME.
- **LG1: a loaded legacy job outlives its plist and revives a daemon.** The legacy plist has `KeepAlive true`. Until a GUI start boots the job out, Quit All is not final: after Quit All the legacy job started a legacy daemon within 15 s and it took the lock (`LG1-quitall.state`, pid 21567, XPC_SERVICE_NAME `portty-daemon`), and while it is loaded its respawn loop runs every 10 s (runs 8 by the second start). Each GUI start while the legacy daemon holds the lock defers the cleanup (log line above) and re-homes; the job is booted out at the first start that finds the launchd job holding the lock. This is bounded (two GUI starts) and the shells survive each re-home, so it is recorded, not a failure. A one-off Quit All inside that window is the only way to see it.

## Notes

- **No daemon log line names the branch.** The plan expects a daemon log line from 19-02 that says which `ManagedByLaunchd` branch fired; 19-02 writes none, so V4 is read from the process environment and launchctl instead (same two facts the function tests).
- **A launchd-started daemon has no `daemon.log`.** The plist has no StandardOutPath/StandardErrorPath, and only the detached spawner opens `daemon.log` (`openDaemonLog` in `process_unix.go`); `startDaemonLog` rotates the file only when stderr already is that file. After L1, `daemon.log` stayed empty (0 bytes) and the daemon's stderr goes to /dev/null under launchd. Rows that quote daemon log lines for a launchd daemon cannot, so they are decided from `/health`, `launchctl print`, `ps` and the session ticks.
- **Not checked here:** that the Login Items URL (`x-apple.systempreferences:com.apple.LoginItems-Settings.extension`) opens the right pane on macOS 27.2, and the Settings needs-repair row; both need the Settings UI and are 19-13 / 19-15 F1 work (the plan scopes them out of 19-07).
- Tick gaps are measured in whole epoch seconds from a 1 s sleep loop, so an undisturbed shell reads a max gap of 1 to 2.
- The GUI's stderr is captured by starting it with `open --stderr` (rig `start-gui`), from row V2 on.

## Findings from 19-12

- **The screen is mostly still, frames arrive every 3 to 6 s.** On the idle VM display Safari's `framesDecoded` rose by one about every 3.7 s (about 118 KB each, then 169 KB), not 30 per second; the cursor and clock are the only changes. Frames do arrive after the watchdog's stall handling, so a still screen does not read as frozen. The open question from 19-05 (does ScreenCaptureKit emit a frame after `Rebuild` on a still screen) was not exercised separately; a joining viewer did get a picture on a still screen (16 frames by the 4th poll of the first connect), so the keyframe-from-cache path produces a frame for a new viewer.
- **`nudge: the pointer did not move and return` on the VM.** With Accessibility granted the daemon logged `WARN desktop: nudge failed err="the pointer did not move and return"` and `GET /desktop` carries it as `reason` while viewers are 0 (`nudge: the pointer did not move and return`). The VM has no real HID pointer; streaming was not affected. Whether the nudge works on a real display is the office-Mac M-row (19-16), where the same line appearing would be a defect.
- **No capture size in the daemon log.** The plan compares `frameWidth` with a width the daemon logged; nothing logs it. The display's native size (2560 x 1440 from `screencapture`) was used.
- **The macOS 27.2 permission flow, as driven:** the daemon's first Test Capture raised `"Portty" would like to record this computer's screen and audio` (Open System Settings, Deny); the pane lists Portty after that prompt; toggling it asks for the admin password and then offers `Quit & Reopen` or `Later` (Later was chosen and the fresh probe read `sr:true` straight away, so a quit is not needed for the daemon's reads). The second real capture raised `"Portty" is requesting to bypass the system private window picker and directly access your screen and audio` with Allow and Open System Settings. The Accessibility pane's title on 27.2 is `Device Control and Data Access`, not `Accessibility`.
- **An old Portty in portty-test-2 talks to the office share server.** The home guest has a pre-existing `~/ptest/Portty.app` (GUI plus daemon, up for more than a day) with 13 established and 4 connecting TCP sockets to office:7444; these are not the desktop viewer and appear in `B1.lsof` as `100.x.x.N` peers. It is ambient test state, left running.
